# Observability

Three layers, each opt-in: raw query events (`$on`), aggregated metrics persisted to Postgres (`$observe`), and a local dashboard over those metrics (`npx turbine observe`). No agent, no external service, no extra dependency.

## Query events, `db.$on('query')`

Every query emits an event after execution, success or failure. Subscribe with `$on`, unsubscribe with `$off`:

```ts
db.$on('query', (event) => {
  if (event.duration > 200) {
    console.warn(`slow: ${event.model}.${event.action} took ${event.duration.toFixed(1)}ms`);
  }
});
```

The event shape:

```ts
interface QueryEvent {
  sql: string;        // the generated SQL text
  params: unknown[];  // bound parameter values (redacted by default, see below)
  duration: number;   // wall-clock ms (performance.now)
  model: string;      // table name, e.g. 'users'
  action: string;     // operation, e.g. 'findMany'
  rows: number;       // rows returned / affected
  timestamp: Date;
  error?: Error;      // present when the query failed
  strategy?: 'auto-batched';            // the 'auto' relation strategy re-planned this query
  tag?: string;                         // the enclosing db.$tag() label, see below
  batch?: 'pipeline' | 'transaction';   // ran inside pipeline() or $transaction([...])
}
```

A listener that throws never breaks the query; the error is swallowed (logged when `logging: true`).

### What emits an event

Every statement the client sends on your behalf:

| Entry point | `model` | `action` |
|---|---|---|
| `db.users.findMany()` and every other model method | the table, e.g. `'users'` | the method, e.g. `'findMany'` |
| `db.raw` and `tx.raw` tagged templates | `'$raw'` | `'raw'` |
| `db.sql` tagged template (`await`, `.one()`, `.scalar()`) | `'$raw'` | `'sql'` |
| `tx.rawQuery(text, params)` | `'$raw'` | `'rawQuery'` |
| prisma-compat `$queryRaw`, `$executeRaw` and the `Unsafe` forms | `'$raw'` | the method name, e.g. `'$queryRaw'` |
| each statement of `db.pipeline(...)` | the statement's table | its method, with `batch: 'pipeline'` |
| each statement of `db.$transaction([...])` | the statement's table | its method, with `batch: 'transaction'` |

`'$raw'` is exported as `RAW_QUERY_MODEL`. A pipeline sends all of its statements in one round trip, so each pipeline event's `duration` is the batch's wall time split evenly across its statements: the total is exact, the per-statement split is not. Statements in `$transaction([...])` are timed one by one. Transaction control statements (`BEGIN`, `COMMIT`, savepoints) are not reported.

### Attributing queries to a feature, `db.$tag()`

`model` and `action` say what ran, not why: `orders.findMany` may be called from a dozen places. Wrap a code path in `$tag` and every event it causes carries that label:

```ts
const order = await db.$tag('checkout', async () => {
  const cart = await db.carts.findUnique({ where: { id: cartId } });
  await db.raw`SELECT pg_advisory_xact_lock(${cart.id})`;
  return db.orders.create({ data: { cartId: cart.id } });
});
// all three events carry tag: 'checkout'
```

The scope follows async context, so queries in awaited helpers, transactions, pipelines and raw SQL inside the callback are all tagged, and concurrent requests keep their own tags. An inner `$tag` replaces an outer one for its own duration. `$tag` returns whatever the callback returns. A label must be 1 to 128 characters (`MAX_QUERY_TAG_LENGTH`); anything else throws `ValidationError` (E003) before the callback runs. The tag is event metadata only and never reaches SQL, so keep request data such as user ids out of it.

`$on` differs from [middleware](/queries#middleware): middleware wraps the call and can transform results; `$on` is a passive tap that fires after execution with the final SQL, timing, and outcome.

### Seeing the parameter values, `logQueryParams`

**Params are redacted by default.** Every entry of `event.params` is replaced with `'[REDACTED]'` before any listener sees it, so a query log cannot leak the values you bind into a `where`.

```ts
db.$on('query', (e) => console.log(e.sql, e.params));

await db.users.findUnique({ where: { email: 'alice@example.com' } });
// SELECT * FROM "users" WHERE "email" = $1 LIMIT 1   [ '[REDACTED]' ]
```

Opt in to real values with `logQueryParams: true` on the client:

```ts
const db = turbine({
  connectionString: process.env.DATABASE_URL,
  logQueryParams: process.env.NODE_ENV !== 'production',
});

// SELECT * FROM "users" WHERE "email" = $1 LIMIT 1   [ 'alice@example.com' ]
```

Only `event.params` changes; SQL, timing, model, action, and row count are identical either way.

<Callout type="note" title="Relationship to `errorMessages`">
[`errorMessages: 'verbose'`](/errors#safe-error-messages) also reveals params, and still works. The two resolve to a single value: when `logQueryParams` is set it decides; when unset, `errorMessages` decides. `logQueryParams: true` with the default `errorMessages: 'safe'` gives real values in query events while error messages stay redacted.
</Callout>

## Metrics, `db.$observe()`

`$observe` turns the event stream into per-minute aggregates persisted to a `_turbine_metrics` table, typically in a *separate* database so metrics writes never touch your application data:

```ts
const handle = await db.$observe({
  connectionString: process.env.TURBINE_OBSERVE_URL!, // metrics DB
  flushIntervalMs: 60_000, // default: 60s
  retentionDays: 30,       // default: 30
});

// on shutdown
await handle.stop(); // final flush, then closes the metrics pool
```

What it does:

- Buffers events in memory, keyed by `model:action` per minute bucket.
- On each flush, computes **count, avg, p50, p95, p99, and error count** per key and upserts a row into `_turbine_metrics` (`ON CONFLICT` merges additively, so multiple app instances can flush into the same bucket).
- Uses its own **1-connection pool** against the metrics database; metric writes never contend with your application pool.
- **Fire-and-forget**: flush errors are swallowed, the flush timer is `unref()`ed so it never keeps the process alive, and a failing metrics database cannot fail a query.
- Creates the table on init (`CREATE TABLE IF NOT EXISTS _turbine_metrics`) and prunes rows older than `retentionDays` on each flush.

The table schema, if you want to query it yourself:

```sql
CREATE TABLE IF NOT EXISTS _turbine_metrics (
  id          BIGSERIAL PRIMARY KEY,
  bucket      TIMESTAMPTZ NOT NULL,  -- minute bucket
  model       TEXT NOT NULL,
  action      TEXT NOT NULL,
  count       INTEGER NOT NULL DEFAULT 0,
  avg_ms      REAL NOT NULL DEFAULT 0,
  p50_ms      REAL NOT NULL DEFAULT 0,
  p95_ms      REAL NOT NULL DEFAULT 0,
  p99_ms      REAL NOT NULL DEFAULT 0,
  error_count INTEGER NOT NULL DEFAULT 0,
  UNIQUE(bucket, model, action)
);
```

Calling `$observe` again replaces the previous engine (the old one is stopped and unsubscribed first).

## Custom sinks: where the aggregates go

The flush target is pluggable: pass a `sink` and the same per-minute aggregates flow wherever you point them.

```ts
interface MetricsFlushBatch {
  rows: Array<{
    bucket: Date;   // the minute bucket
    model: string;  // table name
    action: string; // operation
    count: number;
    avg: number;
    p50: number;
    p95: number;
    p99: number;
    errors: number;
  }>;
}

interface ObserveSink {
  init?(): Promise<void>;                     // once at startup
  flush(batch: MetricsFlushBatch): Promise<void>; // each aggregate batch
  stop?(): Promise<void>;                     // on shutdown
}
```

With a `sink` supplied, `connectionString` becomes optional (at least one of the two is required). With no sink, the default Postgres writer is used.

### `HttpJsonSink`

A generic sink that POSTs each batch as JSON, for Grafana, a self-hosted collector, or any HTTP endpoint:

```ts
import { HttpJsonSink } from 'turbine-orm';

const handle = await db.$observe({
  sink: new HttpJsonSink({
    url: 'https://metrics.internal/ingest',
    headers: { authorization: `Bearer ${process.env.METRICS_TOKEN}` },
    // fetchFunction: customFetch, // optional override
  }),
});
```

It is fire-and-forget: a failed request is swallowed and never throws, and there are no retries beyond the engine's next scheduled flush, so a down collector can never affect a query. The request body carries the aggregate batch and nothing else.

### Privacy posture

A batch (to any sink, HTTP or Postgres) contains **only**:

- the model (table) name and the action (`findMany`, `create`, …);
- the count of queries and the count of errors;
- latency aggregates (avg, p50, p95, p99).

It carries **no SQL text and no parameter values**; those never leave the app process. Observability is off by default: nothing is collected until you call `$observe`.

## Dashboard, `npx turbine observe`

A local, read-only dashboard over `_turbine_metrics`: latency over time and a per-`model.action` breakdown.

```bash
TURBINE_OBSERVE_URL=postgres://... npx turbine observe
npx turbine observe --port 5000 --no-open
```

It binds `127.0.0.1:4984` by default and shares [Studio's security model](/studio#security-model): loopback by default, non-loopback refused without `--allow-remote`, a one-time ticket in the printed URL exchanged for a session cookie, `403` for a `Host` that is not loopback or the bound host, and security headers on every response. It reads metrics only; it never connects to your application database.

## OpenTelemetry

Turbine imports nothing from `@opentelemetry/*` and adds no dependency. Two hooks you already have are enough: [`$use`](/queries#middleware) opens a span for each operation, and `$on('query')` records a span for each SQL statement. Install `@opentelemetry/api` and an SDK yourself; the recipe needs OpenTelemetry's context manager (without one, `context.active()` is always the root context), which the SDK normally provides.

```ts
import { context, trace, SpanKind, SpanStatusCode } from '@opentelemetry/api';
import { RAW_QUERY_MODEL } from 'turbine-orm';
import { db } from './db';

const DB_SYSTEM = 'postgresql'; // 'mysql', 'sqlite' or 'microsoft.sql_server' on the other engines
const tracer = trace.getTracer('turbine-orm');

// One span per Turbine operation. The statements it runs become its children.
db.$use((params, next) =>
  tracer.startActiveSpan(`${params.model}.${params.action}`, { kind: SpanKind.INTERNAL }, async (span) => {
    try {
      return await next(params);
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR });
      throw err;
    } finally {
      span.end();
    }
  }),
);

// One span per SQL statement, back-dated from the event's duration.
db.$on('query', (e) => {
  const end = e.timestamp.getTime();
  const table = e.model === RAW_QUERY_MODEL ? undefined : e.model;
  const span = tracer.startSpan(
    table ? `${e.action} ${table}` : e.action,
    {
      kind: SpanKind.CLIENT,
      startTime: end - e.duration,
      attributes: {
        'db.system.name': DB_SYSTEM,
        'db.operation.name': e.action,
        'db.query.text': e.sql,
        ...(table ? { 'db.collection.name': table } : {}),
        ...(e.tag ? { 'turbine.tag': e.tag } : {}),
        ...(e.batch ? { 'turbine.batch': e.batch } : {}),
        ...(e.retried ? { 'turbine.retried': true } : {}),
      },
    },
    context.active(),
  );
  if (e.error) {
    span.setAttribute('error.type', e.error.name);
    span.setStatus({ code: SpanStatusCode.ERROR, message: e.error.message });
  }
  span.end(end);
});
```

A request that creates an order produces this tree, with your own span at the top:

```
POST /orders                 your span
  orders.create              INTERNAL, from $use
    create orders            CLIENT, from $on('query')
```

The operation span is `INTERNAL` and the statement span is `CLIENT`, so a backend that counts database calls counts each statement once. The operation span is wider than its statements: it also covers SQL generation and turning rows into objects.

### Why the tree comes out right

A query event is delivered in the async context of the code that awaited the statement. `context.active()` inside the listener is therefore the span that was active at that `await`: the operation span for a model call, or your own span for a statement that has no operation span. Nothing has to be passed through Turbine for this to work.

`$use` wraps model methods only, so these statements get no operation span. They appear as statement spans directly under whichever span is active where you await them:

| Statement | `db.operation.name` | `turbine.batch` |
|---|---|---|
| `db.pipeline(...)` | each statement's method | `pipeline` |
| `db.$transaction([...])` | each statement's method | `transaction` |
| `findManyStream`, `findManyStreamBatches` | the stream method | none |
| `db.raw`, `db.sql`, `db.rawUnsafe`, `tx.raw`, `tx.rawQuery` | the entry point, such as `raw` or `sql` | none |

Four consequences:

- **A lazy `db.sql` builder executes where it is awaited, not where it was built.** A `db.sql` query created in one request and awaited in another puts its statement under the second.
- **A transaction adds no span of its own.** `BEGIN`, `COMMIT` and savepoints are not reported, and each statement inside `db.$transaction(async (tx) => ...)` nests under its operation. Wrap the transaction in your own span if you want one.
- **Batched relation loads stay under one operation.** With `relationLoadStrategy: 'batched'`, and with the `'auto'` fallback (events tagged `strategy: 'auto-batched'`), the base statement and every follow-up are children of the same operation span. A follow-up event carries the model of the query that asked for it, not the table it read, so take the table from `db.query.text`.
- **Raw statements have no table.** `RAW_QUERY_MODEL` (`'$raw'`) is left out of the span name and of `db.collection.name`.

### What the attributes mean

The `db.*` and `error.type` names follow the [OpenTelemetry database semantic conventions](https://opentelemetry.io/docs/specs/semconv/db/database-spans/). The conventions reached stable in v1.33.0, which renamed `db.system` to `db.system.name` and `db.statement` to `db.query.text`, and some values are still marked in development, such as the one for SQLite. Pin the version of the conventions your backend expects. `turbine.tag`, `turbine.batch` and `turbine.retried` are Turbine's own.

| Attribute | Value |
|---|---|
| `db.system.name` | The `DB_SYSTEM` you set for your engine. |
| `db.operation.name` | The Turbine method, such as `findMany`, `create` or `raw`. |
| `db.collection.name` | The table. Absent for raw SQL. |
| `db.query.text` | The SQL text with placeholders (`$1`, `$2`). |
| `error.type` | The error class name, such as `UniqueConstraintError`. Set on failure only. |
| `turbine.tag` | The enclosing [`db.$tag()`](#attributing-queries-to-a-feature-dbtag) label. |
| `turbine.batch` | `pipeline` or `transaction` for statements that ran as part of a batch. |
| `turbine.retried` | `true` on the failed first attempt of a read that Turbine re-sent after the server had closed its connection. |

Timing, parameters and failures:

- **`duration` is measured around the driver call.** It covers the round trip and, on a pooled client, the wait for a free connection. It does not cover SQL generation, row parsing or middleware, which is why the operation span is longer. Each span ends at the event's `timestamp` and starts `duration` earlier.
- **A pipeline's per-statement duration is the batch time divided evenly.** The pipeline sends every statement in one round trip, so the spans share the batch's wall time equally. The total is exact and the per-statement split is not. Statements in `$transaction([...])` are timed individually.
- **Parameter values stay out of the span.** Turbine binds every value, so `db.query.text` carries placeholders and never values. The one exception is [`db.rawUnsafe`](/queries), where you write the text yourself. The values are in `e.params`, which holds `'[REDACTED]'` for each entry unless [`logQueryParams`](#seeing-the-parameter-values-logqueryparams) is on. The recipe does not record them. If you add them, the conventions treat `db.query.parameter.<key>` as opt-in because values can carry personal data.
- **A retried read shows as two statement spans.** The first carries `turbine.retried` and an error status, the second times the retry alone. Alert on the operation span's status to count failed calls rather than failed attempts. Writes and statements inside a transaction are never retried.
- **`recordException` sends the error's message and stack to your backend.** See [`errorMessages`](/errors#safe-error-messages) for what a message may contain.
