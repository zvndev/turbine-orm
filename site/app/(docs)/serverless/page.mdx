# Serverless & Edge

Turbine's edge entry, `turbine-orm/serverless`, is a thin shim over the query engine: under **116 kB brotli** bundled on the edge, with no WASM. It takes any pg-compatible pool (Neon, Vercel Postgres, Cloudflare Hyperdrive, Supabase, `postgres.js`, or your own) and binds it to a `SchemaMetadata` object. The full query API runs unchanged.

When you pass an external pool, Turbine:

- **Does not** call `pg.types.setTypeParser`, so queries your own code sends on the pool keep the driver's parsing. Turbine's own queries on a PostgreSQL pool still read `bigint` as a number and zone-less `timestamp` / `date` as UTC, as they do on a pool Turbine opens. Set `utcTimestamps: false` to keep the driver's temporal readings.
- **Does not** own the pool's lifecycle: `db.disconnect()` is a no-op.
- **Does** keep every other feature: `with` inference, transactions, pipelines, middleware, typed errors, streaming.

A pool with no `connect()`, such as a stateless HTTP driver, runs each statement on its own. Work that needs several statements on one connection throws `UnsupportedFeatureError` (`TURBINE_E017`) there and names the alternative. That covers `$transaction`, `transaction()`, a pipeline sent as one batch, cursor streams, and a `createMany` large enough to be chunked. For those, use a driver pool that can check out a connection.

## The pattern

```ts
import { turbineHttp } from 'turbine-orm/serverless';
import type { TurbineClient } from './generated/turbine/index.js';
import { SCHEMA } from './generated/turbine/metadata.js';
import { Pool } from '<your-edge-driver>';

const pool = new Pool({ connectionString: process.env.DATABASE_URL! });
export const db = turbineHttp<TurbineClient>(pool, SCHEMA);
```

`SCHEMA` is the `SchemaMetadata` object that `npx turbine generate` writes to `./generated/turbine/metadata.ts`. It is a plain object with no side effects and no Node-only imports, so it works in any runtime.

The type argument gives you the generated accessors, so `db.users.findMany()` is fully typed. Without it, `turbineHttp` returns the base `TurbineClient` and you reach tables through `db.table('users')`.

The optional third argument takes every `TurbineConfig` option except `pool`, which is the first argument: `globalFilters`, `errorMessages`, `logging`, `logger`, `diagnostics`, `defaultLimit`, `warnOnUnlimited`, and the rest.

Set `diagnostics: 'production'` on a worker or function that does not set `NODE_ENV`. A runtime with no `process` already defaults to production. One that has a `process` but no `NODE_ENV` (Cloudflare Workers with Node compatibility, for example) defaults to development, which turns on per-query advice and the SQL-cache self-check. See [Diagnostics](/observability#diagnostics-diagnostics).

```ts
export const db = turbineHttp<TurbineClient>(pool, SCHEMA, { diagnostics: 'production' });
```

## Neon (HTTP driver)

Recommended for Vercel Edge, Cloudflare Workers and Deno Deploy.

```bash
npm install @neondatabase/serverless
```

```ts
// db.ts
import { Pool } from '@neondatabase/serverless';
import { turbineHttp } from 'turbine-orm/serverless';
import type { TurbineClient } from './generated/turbine/index.js';
import { SCHEMA } from './generated/turbine/metadata.js';

const pool = new Pool({ connectionString: process.env.DATABASE_URL! });
export const db = turbineHttp<TurbineClient>(pool, SCHEMA);
```

```ts
// app/api/users/route.ts  (Next.js Edge)
export const runtime = 'edge';

import { db } from '@/db';

export async function GET() {
  const users = await db.users.findMany({ limit: 20 });
  return Response.json(users);
}
```

Neon's HTTP driver reuses TCP across invocations within a region, so cold-start latency comes from the Worker cold start (~20 ms), not the database connection. `pipeline()` still batches, because Neon supports the extended-query protocol.

**Caveat: no `LISTEN/NOTIFY` or session state.** HTTP mode is one transaction per request. If you depend on session-scoped `SET` calls, use Neon's WebSocket driver instead.

## Vercel Postgres

```bash
npm install @vercel/postgres
```

```ts
import { createPool } from '@vercel/postgres';
import { turbineHttp } from 'turbine-orm/serverless';
import type { TurbineClient } from './generated/turbine/index.js';
import { SCHEMA } from './generated/turbine/metadata.js';

const pool = createPool();
export const db = turbineHttp<TurbineClient>(pool, SCHEMA);
```

Vercel Postgres wraps Neon, so the semantics are the same. If you are on Vercel and use Neon directly, skip `@vercel/postgres` and use `@neondatabase/serverless`: one less package.

## Cloudflare Hyperdrive

Hyperdrive runs a connection pool in front of any PostgreSQL database and exposes it to Workers as a binding that speaks TCP. Use `pg` in Workers through the Node compatibility flag.

```toml
# wrangler.toml
compatibility_flags = ["nodejs_compat"]

[[hyperdrive]]
binding = "HYPERDRIVE"
id = "<your-hyperdrive-id>"
```

```ts
import { Pool } from 'pg';
import { turbineHttp } from 'turbine-orm/serverless';
import type { TurbineClient } from './generated/turbine/index.js';
import { SCHEMA } from './generated/turbine/metadata.js';

export default {
  async fetch(req: Request, env: Env) {
    const pool = new Pool({ connectionString: env.HYPERDRIVE.connectionString });
    const db = turbineHttp<TurbineClient>(pool, SCHEMA);
    const users = await db.users.findMany({ limit: 20 });
    return Response.json(users);
  },
};
```

Hyperdrive pools connections at the edge, so there is no per-request TLS handshake to your origin database. Use it for Workers backed by a regular Postgres instance: AWS RDS, Supabase Postgres, or self-hosted.

## Supabase

```ts
import { Pool } from 'pg';
import { turbineHttp } from 'turbine-orm/serverless';
import type { TurbineClient } from './generated/turbine/index.js';
import { SCHEMA } from './generated/turbine/metadata.js';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL!, // supabase connection string
  ssl: { rejectUnauthorized: true },
});
export const db = turbineHttp<TurbineClient>(pool, SCHEMA);
```

For serverless, use Supabase's **connection pooler** URL (`...pooler.supabase.com:6543`), **not** the direct `...db.supabase.co:5432` URL. The pooler is PgBouncer in transaction mode, which keeps Lambda from exhausting connections.

## postgres.js (node)

For Node runtimes where you prefer `postgres.js` over `pg`:

```ts
import postgres from 'postgres';
import { turbineHttp } from 'turbine-orm/serverless';
import { SCHEMA } from './generated/turbine/metadata.js';

// postgres.js isn't exactly pg-compatible out of the box, adapt its
// interface to PgCompatPool. See the PgCompatPool type for the contract.
```

The `PgCompatPool` / `PgCompatPoolClient` / `PgCompatQueryResult` interfaces exported from `turbine-orm` define the adapter contract. It is three methods: `query`, `connect` and `end`.

## Keeping `findMany` sane on the edge

Edge memory is tight: Vercel Edge and Cloudflare Workers both cap at 128 MB. A nested `findMany` that materializes a large JSON payload can exhaust that quickly.

Two rules:

1. **Always put a `limit` on the root query.** Every edge-facing `findMany` needs an explicit limit. Paginate; never fetch everything.
2. **Always put a `limit` on a nested `hasMany` in `with`.** Write `posts: { limit: 20 }`, not `posts: true`.

Rough numbers on a 128 MB Worker hitting Neon in the same region:

| Query | Rows | Latency | Memory |
|---|---|---|---|
| `findMany({ limit: 20 })` flat | 20 | ~35 ms | < 1 MB |
| `findMany({ limit: 20, with: { posts: { limit: 5 } } })` L2 | 20 × 5 | ~40 ms | ~2 MB |
| `findMany({ limit: 20, with: { posts: { with: { comments: { limit: 50 } } } } })` L3 | 20 × 5 × 50 | ~70 ms | ~18 MB |
| `findMany({ with: { posts: { with: { comments: true } } } })` unbounded | ⚠️ | ⚠️ | ⚠️ |

The unbounded row is where you run out of memory. Don't ship it.

## Cold start

Importing the edge entry opens no connection, and on a supplied pool Turbine registers no type parsers. Under the `edge-light` and `browser` conditions (Vercel Edge, Next.js edge routes) it does not bundle `pg` at all; on Node and Cloudflare Workers, `pg` is a regular import. Cold start is your driver's cold start: typically 1–5 ms on Neon HTTP, and 0 ms on Hyperdrive, which reuses a pooled connection.

## Streaming on the edge

`findManyStream` works on any pool that can check out a connection and run `DECLARE CURSOR`, which includes Neon's `Pool`, Hyperdrive and Supabase. Edge functions rarely want to stream, since the Worker runtime needs a bounded response, but streaming into R2, S3 or other object storage works fine.

A stream left open when an invocation freezes cannot hold its connection forever. On PostgreSQL, the stream's transaction carries a server-side idle limit equal to the stream's idle timeout (`streamIdleTimeoutMs`, five minutes by default) plus 10 seconds. The server ends the transaction, and the stream's next pull after a thaw throws `ConnectionError` (`TURBINE_E004`). See [Abandoned streams close themselves](/queries#abandoned-streams-close-themselves).
