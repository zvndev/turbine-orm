# Realtime (LISTEN / NOTIFY)

Send events between processes through Postgres, with no message broker or extra service. Turbine wraps Postgres `LISTEN` / `NOTIFY` in two methods: `$listen` subscribes to a channel and `$notify` publishes to it.

Use it for cache invalidation, live dashboards and worker fan-out when you already have Postgres and do not want to run Redis or a queue.

## Subscribe with $listen

Pass a channel name and a handler. The handler receives the notification payload as a string. `$listen` resolves once the subscription is live.

```ts
const sub = await db.$listen('order_created', (payload) => {
  console.log('new order:', payload);
});
```

`$listen` checks out a dedicated pooled connection, runs `LISTEN "order_created"` on it, and holds that connection for the life of the subscription. The returned subscription exposes the resolved `channel` and an `unsubscribe()` method.

## Publish with $notify

```ts
await db.$notify('order_created', JSON.stringify({ id: 1 }));
```

`$notify` is a single round-trip: it runs `SELECT pg_notify($1, $2)` with the channel and payload bound as parameters. The payload is optional and defaults to an empty string:

```ts
await db.$notify('cache_invalidated'); // payload defaults to ''
```

The payload is a string, so serialize structured data with `JSON.stringify` and parse it in the handler.

## Unsubscribe

Call `unsubscribe()` when you are done. It runs `UNLISTEN` and returns the dedicated connection to the pool.

```ts
const sub = await db.$listen('order_created', (payload) => {
  console.log('new order:', payload);
});

// ...later
await sub.unsubscribe();
// subsequent $notify calls no longer fire the handler
```

`db.disconnect()` also releases every live subscription, so shutdown does not leak connections.

## Lost connections

A subscription holds one connection for its whole life, so a database restart, failover or compute suspend will eventually close it. `$listen` then reopens the connection with exponential backoff and runs `LISTEN` again. The first retry waits 100 ms, and the delay doubles up to 30 s.

```ts
const sub = await db.$listen('order_created', onOrder, {
  onReconnect: () => refreshOrders(), // resync: anything sent while down is gone
  onError: (err) => log.warn(err),    // each loss, as a ConnectionError (E004)
});
```

| Option | Default | Meaning |
|---|---|---|
| `reconnect` | `true` | `false` ends the subscription at the first loss. An object `{ initialDelayMs, maxDelayMs }` tunes the backoff. |
| `onError` | one line through the client's `logger` | Called with each loss and each failed reconnect attempt. |
| `onReconnect` | none | Called once the subscription is live again. |

`NOTIFY` is not durable. A notification sent while the subscription is reconnecting is never delivered, so use `onReconnect` as the signal to re-read whatever state the channel tracks. `unsubscribe()` and `db.disconnect()` cancel a pending reconnect.

## Channel names

The channel name is the one identifier interpolated into the generated SQL, so Turbine validates it strictly as a plain identifier and quotes it. A name with spaces, a leading digit, dots or other special characters throws `ValidationError` *before* any connection is used.

```ts
await db.$notify('order created');  // throws ValidationError, space
await db.$listen('1bad', () => {}); // throws ValidationError, leading digit
await db.$notify('app.events');     // throws ValidationError, no dotted namespacing
```

## Not available on serverless HTTP drivers

`$listen` needs a persistent connection to hold the subscription, which HTTP and serverless drivers (Neon HTTP, Vercel Postgres, Cloudflare Hyperdrive) do not provide. When the pool hands back a client with no event support, as a stateless HTTP driver does, `$listen` throws `ConnectionError` instead of hanging. `$notify` is a single round-trip and works everywhere.

For realtime on the edge, run `$listen` in a long-lived process (a worker or server) on a real `pg` pool, and call `$notify` from anywhere.
