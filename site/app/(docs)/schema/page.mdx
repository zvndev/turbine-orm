# Schema & Migrations

Turbine supports two schema workflows:

- **Code-first**: declare tables with `defineSchema(...)` in TypeScript, then `push` them or generate migrations from the diff.
- **Introspection**: point Turbine at an existing database and generate a typed client from its catalog.

Both produce the same generated files (`types.ts`, `metadata.ts`, `index.ts`), so you can mix them.

## Code-first with `defineSchema`

Declare your tables in a TypeScript file. Turbine uses the definitions to generate DDL, run migrations, and emit the typed client.

```ts
// turbine/schema.ts
import { defineSchema } from 'turbine-orm';

export default defineSchema({
  organizations: {
    id: { type: 'serial', primaryKey: true },
    name: { type: 'text', notNull: true },
    createdAt: { type: 'timestamp', default: 'now()' },
  },
  users: {
    id: { type: 'serial', primaryKey: true },
    email: { type: 'text', unique: true, notNull: true },
    name: { type: 'text', notNull: true },
    orgId: { type: 'bigint', notNull: true, references: 'organizations.id' },
    role: { type: 'text', notNull: true, default: "'member'" },
    createdAt: { type: 'timestamp', default: 'now()' },
  },
  posts: {
    id: { type: 'serial', primaryKey: true },
    userId: { type: 'bigint', notNull: true, references: 'users.id' },
    title: { type: 'text', notNull: true },
    content: { type: 'text' },
    published: { type: 'boolean', notNull: true, default: false },
    viewCount: { type: 'integer', notNull: true, default: 0 },
    createdAt: { type: 'timestamp', default: 'now()' },
  },
});
```

Two things the example does not show:

- `type: 'timestamp'` emits `TIMESTAMPTZ`. The alias is kept for back-compat and means the same as `'timestamptz'`, so there is no code-first spelling for a zone-less `TIMESTAMP` column. Declare one in a SQL migration and `generate` picks it up; the [type mapping](#type-mapping) below describes how it reads.
- `varchar` takes its bound as `maxLength`: `{ type: 'varchar', maxLength: 200 }`.

A `default` is SQL text (`"'member'"`, `'now()'`), a number, or a boolean. `default: 0` emits `DEFAULT 0` and `default: false` emits `DEFAULT FALSE`; the string forms `'0'` and `'false'` also work. Any other value, such as an object, throws `TURBINE_E003`.

### Unknown keys throw

`defineSchema` refuses a key it does not know. A misspelt column, table, index, `references`, check, `manyToMany` or options key throws `ValidationError` ([`TURBINE_E003`](/errors#e003)) naming the key, where it sits, and the nearest valid key:

```ts
defineSchema({
  users: {
    id: { type: 'serial', primaryKey: true },
    role: { type: 'text', defaultValue: "'member'" },
  },
});
// TURBINE_E003: defineSchema: unknown key "defaultValue" in column "users.role". Did you mean "default"?
```

In a TypeScript object literal the same key is also a compile error.

The same error covers these shapes:

- a table or column named `__proto__`, because JavaScript reads that key as the prototype setter, so the column could not be stored or queried;
- an index that declares both `columns` and `docField` (declare two indexes instead);
- an index naming a column the table does not have (the error suggests the nearest column);
- two fields that map to one database column (`userId` and `user_id`), and two tables that map to one table name.

A column may still be called `name` or `columns`.

### Typing a JSON column, `tsType`

A `json` / `jsonb` column generates as `unknown`. Give it a type with `tsType`, in the object form or on the fluent builder:

```ts
export default defineSchema({
  users: {
    id: { type: 'serial', primaryKey: true },
    settings: { type: 'jsonb', tsType: '{ theme: string; beta?: boolean }' },
  },
});

// fluent: column.jsonb().tsType('{ theme: string; beta?: boolean }')
```

`turbine generate` uses it for the column's row, create and update types. The text is emitted verbatim, so it may name any type the generated file can see (`import('../src/types.js').Settings`), and `| null` is still added for a nullable column.

The text must be one TypeScript type on one line, or `defineSchema` throws `ValidationError` (`TURBINE_E003`) naming it. That rules out comments, `;` or `,` outside brackets, unbalanced brackets, template literal types and backticks. Object types, generics, unions, function types and `import('...').T` are fine; give anything else a type alias and import it.

A declared type changes only the generated TypeScript. The runtime metadata keeps the column's mapped type, so the engines read and write the column as its database type. The same override can live in `turbine.config.ts` as [`columnTypes`](/cli#typing-columns-columntypes); when both name one column, the config entry wins.

### Composite primary keys

Pass a table-level `primaryKey` array:

```ts
memberships: {
  userId: { type: 'bigint', notNull: true, references: 'users.id' },
  orgId: { type: 'bigint', notNull: true, references: 'organizations.id' },
  role: { type: 'text', notNull: true },
  primaryKey: ['userId', 'orgId'],
}
```

`findUnique` accepts the composite key as an object: `where: { userId: 1, orgId: 2 }`.

### Foreign keys and referential actions

The short `references: 'table.column'` form emits a plain foreign key. A reference to a table in the same schema is checked:

- It must have exactly one dot. `references: 'users'` throws `TURBINE_E003`, since no foreign key would be created.
- The column must exist on that table, written as the field name (`authors.displayName`) or the column name (`authors.display_name`). Turbine emits the column name. An unknown column throws `TURBINE_E003` listing the table's columns.
- A table outside the schema is not checked, so a reference to a table another migration owns still works.

To attach `ON DELETE` / `ON UPDATE` actions, pass an object:

```ts
posts: {
  id: { type: 'serial', primaryKey: true },
  userId: {
    type: 'bigint',
    notNull: true,
    references: { target: 'users.id', onDelete: 'cascade', onUpdate: 'restrict' },
  },
}
// REFERENCES "users"("id") ON DELETE CASCADE ON UPDATE RESTRICT
```

Supported actions: `'cascade'`, `'restrict'`, `'set null'`, `'set default'`, `'no action'`. Omit a clause to get the SQL default (`NO ACTION`). The string form emits no action clauses. Introspection reads existing actions back from `pg_constraint`, so a `pull` round-trips them and `migrate create --auto` detects action changes.

### Enums

Declare enum types once in the schema options, then reference them from columns by name:

```ts
export default defineSchema(
  {
    posts: {
      id: { type: 'serial', primaryKey: true },
      status: { type: 'enum', enumName: 'post_status', notNull: true, default: "'draft'" },
    },
  },
  { enums: { post_status: ['draft', 'published', 'archived'] } },
);
```

Enum columns generate a string-literal union in `types.ts` (`'draft' | 'published' | 'archived'`).

On PostgreSQL, the DDL emits `CREATE TYPE "post_status" AS ENUM ('draft', 'published', 'archived')` before the tables that use it, and the column is typed `"post_status"`. Every write path (`create`, `createMany`, `update`, `upsert`) casts the value explicitly to `::"post_status"`, schema-qualified so it is safe across schemas. That prevents the `column is of type post_status but expression is of type text` error `createMany` would otherwise hit.

The other engines have no enum type, so `schemaToSQL` declares the column inline:

| Engine | Column |
|---|---|
| MySQL | `ENUM('draft', 'published', 'archived')` |
| SQLite | `TEXT` with a `CHECK` over the labels |
| SQL Server | `NVARCHAR` with a `CHECK` over the labels |

On those engines the enum must be declared in `enums` with at least one label (`TURBINE_E003` otherwise), an enum array throws `TURBINE_E017`, and a MySQL label holding a backslash throws `TURBINE_E003`.

### Array columns

Add `array: true` to any scalar column:

```ts
posts: {
  id: { type: 'serial', primaryKey: true },
  tags: { type: 'text', array: true, notNull: true },  // TEXT[]
}
```

Array columns map to `T[]` in generated types and support the [array WHERE operators](/queries#array-columns) (`has`, `hasEvery`, `hasSome`).

### Vector columns

For pgvector embeddings, use `{ type: 'vector', dimensions: n }`:

```ts
documents: {
  id: { type: 'serial', primaryKey: true },
  embedding: { type: 'vector', dimensions: 1536, notNull: true },  // vector(1536)
}
```

A schema containing a vector column prepends `CREATE EXTENSION IF NOT EXISTS vector;` by default. Pass `extensions: 'manual'` to `schemaToSQL` to emit a comment instead and manage the extension yourself. Vector columns map to `number[]`. See [Vector Search](/vector) for querying them.

### Check constraints

Add a column-level `check` for an inline constraint, or table-level `checks` for named ones:

```ts
products: {
  id: { type: 'serial', primaryKey: true },
  price: { type: 'integer', notNull: true, check: 'price >= 0' },
  cost: { type: 'integer', notNull: true },
  checks: [{ name: 'price_gt_cost', expression: 'price > cost' }],
}
// "price" INTEGER NOT NULL CHECK (price >= 0)
// CONSTRAINT "price_gt_cost" CHECK (price > cost)
```

A table-level check without a `name` emits a bare `CHECK (expr)`. Introspection reads check constraints back, so they survive a `pull`. A violated check throws `CheckConstraintError` (`TURBINE_E011`) at write time.

### Declared indexes

Declare plain column-list indexes at the table level with `indexes`. Each entry lists its camelCase columns, plus an optional `unique: true` and an optional `name`, which defaults to `idx_<table>_<col1>_<col2>`:

```ts
users: {
  id: { type: 'serial', primaryKey: true },
  email: { type: 'text', notNull: true },
  orgId: { type: 'integer', references: 'orgs.id' },
  indexes: [
    { columns: ['email'], unique: true },          // CREATE UNIQUE INDEX "idx_users_email"
    { columns: ['orgId', 'email'] },               // CREATE INDEX "idx_users_org_id_email"
    { columns: ['email'], name: 'users_email_ci' } // explicit name
  ],
}
```

`schemaToSQL`, and so `push`, emits these as `CREATE [UNIQUE] INDEX` after the table DDL. Foreign-key columns still get an automatic index. A declared index that resolves to the same name takes its place, so declaring `{ columns: ['orgId'], unique: true }` replaces the plain automatic FK index instead of colliding with it.

`schemaDiff` adds declared indexes that are missing from the live database, and warns when a name matches an existing index whose definition differs (uniqueness, column list, or a partial-index `WHERE`). It never drops an index automatically. PowDB doc-field expression indexes (`{ docField, path }`) are documented on the [engines page](/engines) and emit no SQL.

### PII fields

Tag a column with `pii: true` to mark it as personally identifiable information:

```ts
users: {
  id: { type: 'serial', primaryKey: true },
  name: { type: 'text', notNull: true },
  email: { type: 'text', notNull: true, pii: true },
  ssn: { type: 'text', pii: true },
}
```

A PII column is **excluded from every default projection**. It comes back only with `includePii: UNSAFE`, a [privilege option](/global-filters#privilege-options-and-the-unsafe-symbol) that accepts only the imported symbol (a literal `true` throws `TURBINE_E003`). Naming a PII column in `select` without it throws `ValidationError` (`TURBINE_E003`); with it, `select` narrows the row as usual. See [includePii on reads](/queries#pii-fields-includepii).

The rest of the policy:

- **Writes are unaffected.** You can write PII fields freely. The value is stored, but the returned row never includes it, and a write's `select` that names a PII column throws. Re-read with `includePii: UNSAFE` when you need the value back.
- **`where`, `orderBy` and `having` are always allowed.** They narrow, sort or filter rows and return no PII value.
- **Two aggregate shapes need the same `includePii: UNSAFE`**, because they return stored values: a PII column as a `groupBy` `by` key (including a JSON-path key), and `_min` / `_max` over a PII column in `groupBy` or `aggregate` (including JSON-path targets). Without the opt-in they throw `ValidationError` (`TURBINE_E003`).
- **`_count`, `_sum` and `_avg` stay allowed.** None of them returns a stored cell.

**Tag sensitive data, not keys.** A PII-tagged column that is part of the primary key is returned anyway, on every read and write path. A row returned without part of its own key cannot be addressed: feeding it into an `update` builds a partial predicate that matches more rows than intended. If a key column is sensitive, use a surrogate key instead of a tag.

Other tools honor the tag. [`turbine studio`](/studio) redacts PII cells by default (reveal them with `--show-pii`). `turbine generate` marks each PII field optional in the emitted entity type, since it is absent by default, with the doc comment `(PII: absent unless the read passes includePii: UNSAFE)`.

Studio and the [MCP server](/mcp) introspect the live database, which carries no tags, so they read the tags from the generated metadata in your `out` directory. Run `turbine generate` after tagging, or they have nothing to redact. Introspection never tags a column on its own: `pii` is a declaration you make in `defineSchema`.

#### How `generate` picks up the tags

`turbine generate` introspects the database, and the database has no column for `pii` or `updatedAt`. So `generate` also reads your schema file (`--schema-file`, or `schemaFile` in `turbine.config.ts`, default `turbine/schema.ts`) and overlays its `pii`, `updatedAt`, `maxLength` and `tsType` declarations onto what it introspected. It prints a line such as `Applied column tags from turbine/schema.ts: 2 pii, 1 updatedAt, 1 tsType`.

Clients generated before 0.90 lack the overlay: they return tagged columns by default and never stamp `updatedAt`. Regenerate after upgrading.

The overlay fails rather than generating an unprotected client:

- A schema file you named that is missing, or any schema file that cannot be loaded, fails the command. Only a missing file at the default path is skipped, which is a database-first project with no schema file.
- A `pii` or `updatedAt` tag on a table or column the database does not have fails the command, listing every such name with the closest match. Run `turbine push` first, or fix the name. A table you left out with `exclude` is not an error.
- A `.ts` schema file needs a TypeScript loader, as `turbine push` does; install `tsx` as a dev dependency.

### Auto-updated timestamps, `updatedAt`

Tag a column with `updatedAt: true` (or `.updatedAt()` on the fluent builder), and every `update` that does not name it sets it to the current time. It is the equivalent of Prisma's `@updatedAt`.

```ts
const posts = defineSchema({
  posts: {
    id: { type: 'serial', primaryKey: true },
    title: { type: 'text', notNull: true },
    updatedAt: { type: 'timestamptz', notNull: true, default: 'now()', updatedAt: true },
  },
});

// No `updatedAt` in the payload: it is filled in for you.
await db.posts.update({ where: { id: 1 }, data: { title: 'new title' } });

// An explicit value always wins, including an explicit null.
await db.posts.update({ where: { id: 1 }, data: { title: 'x', updatedAt: pinned } });
```

The timestamp is generated client-side, as Prisma does, so it goes through the same UTC coercion as any other bound `Date` on every engine. It applies to `update`, `updateMany` and the update half of `upsert`, whether that runs as one conflict statement or as a lookup followed by an update. It never applies to `create` or to an `upsert` that inserts; use a column default there. An `upsert` with an empty `update` leaves the row it finds untouched, timestamp included.

Like `pii`, `updatedAt` is a code-first declaration and is never inferred from a column's name, so an application that already manages its own `updated_at` is not changed by an upgrade. A schema with no tagged column emits byte-identical SQL.

### Runtime metadata without a database, `schemaDefToMetadata`

The runtime `SchemaMetadata` a client needs normally comes from `turbine generate`, which reads a live database. `schemaDefToMetadata(def)` derives the same object from a `defineSchema` result, with no connection and no codegen step:

```ts
import { defineSchema, schemaDefToMetadata } from 'turbine-orm';

const schema = defineSchema({ /* ... */ });
const metadata = schemaDefToMetadata(schema);
```

It is the code-first path for engines with no wire introspection, most notably PowDB, where you can pass a `defineSchema` result straight to the factory:

```ts
import { turbinePowDB } from 'turbine-orm/powdb';

const db = await turbinePowDB({ embedded: './data' }, schemaDefToMetadata(schema));
```

## DDL generation

Turbine generates quoted, deterministic DDL from any `SchemaDef`. Every identifier goes through `quoteIdent()`, so reserved words and mixed case are safe.

```bash
# Preview the SQL without running it
npx turbine push --dry-run

# Apply schema changes to the database
npx turbine push
```

`push` is the fast path for development: it diffs your `defineSchema` output against the live database and applies the difference. For production, use migrations.

### Programmatic: `schemaToSQL` and `schemaPush`

Both are exported from the package root, for test harnesses, custom bootstrap scripts, and other places where the CLI is not the right entry point.

```ts
import { schemaToSQL, schemaToSQLString, schemaPush } from 'turbine-orm';
import schema from './turbine/schema.js';

// Build the DDL. No connection involved, so this works for any engine
// whose driver can execute the statements.
const statements = schemaToSQL(schema);          // string[]
const oneScript = schemaToSQLString(schema);     // the same, joined

// Diff against a live Postgres database and apply the difference in ONE
// transaction. Data-destroying statements (drops, lossy type changes) are
// refused unless you pass allowDestructive: true.
const result = await schemaPush(schema, process.env.DATABASE_URL!);
console.log(result.statementsExecuted, result.tablesCreated, result.tablesAltered);

// Preview instead of applying
await schemaPush(schema, url, { dryRun: true });
```

`schemaPush(schema, connectionString, options?)` accepts `{ dryRun, allowDestructive, precomputedDiff }`. If the computed diff contains a data-destroying statement (a lossy `ALTER COLUMN ... TYPE` and similar), it applies nothing and **throws** a `DestructivePushRefusal`, a `ValidationError` subclass carrying the offending statements on `.destructive`. Pass `allowDestructive: true` to proceed. It is the same gate `turbine push` puts behind an interactive confirmation. `precomputedDiff` lets a caller diff once, show the plan, confirm, and then apply exactly the statements it showed, without diffing again.

`schemaPush` and `schemaDiff` connect through `pg` and are **Postgres-only**. `schemaToSQL` opens no connection, so it is not.

With `{ dialect: mysqlDialect }`, `schemaToSQL` writes defaults in the forms MySQL accepts:

- A non-`NULL` default on a `TEXT`, `BLOB` or `JSON` column becomes an expression (`DEFAULT ('member')`, `DEFAULT ('{}')`).
- A clock default on a `DATE` or `TIME` column becomes `(CURRENT_DATE)` or `(CURRENT_TIME)`.
- A clock default on a `DATETIME(n)` column follows the column's precision (`CURRENT_TIMESTAMP(3)`).

These rewrites apply to MySQL only.

## SQL-first migrations

Turbine migrations are plain `.sql` files with `-- UP` and `-- DOWN` sections. The runner tracks them in a `_turbine_migrations` table keyed on timestamp and SHA-256 checksum. For the full production workflow (deploy semantics, the destructive-statement gate, what `--auto` can and cannot do, and the two-phase recipe for changing a populated column's type), see [Migrations in Practice](/migrate).

### Create a migration

```bash
# Blank migration, write SQL manually
npx turbine migrate create add_users_table

# Auto-generate from the diff between defineSchema() and the live database
npx turbine migrate create add_email_index --auto
```

The resulting file looks like this:

```sql
-- 20260409143022_add_users_table.sql
-- UP
CREATE TABLE "users" (
  "id" SERIAL PRIMARY KEY,
  "email" TEXT UNIQUE NOT NULL,
  "name" TEXT NOT NULL,
  "created_at" TIMESTAMPTZ DEFAULT now()
);

-- DOWN
DROP TABLE "users";
```

### Apply, rollback, inspect

```bash
npx turbine migrate up       # Apply all pending migrations
npx turbine migrate down     # Roll back the last applied migration
npx turbine migrate status   # Show applied vs pending
```

Each migration runs in its own transaction, unless the file carries a `-- turbine:no-transaction` directive. If a migration fails partway, its transaction rolls back and `_turbine_migrations` stays clean.

### Concurrency safety

Turbine takes `pg_try_advisory_lock()` before running any migration. A second process that runs `migrate up` at the same time fails with `MigrationError` (`TURBINE_E006`) instead of racing, so the command is safe to run from CI/CD pipelines and deploy hooks. `migrate deploy --wait` waits for the lock instead; see [`turbine migrate deploy`](/cli#turbine-migrate-deploy).

### Checksums

Each migration file's SHA-256 hash is stored alongside its timestamp. If you edit a migration that has already been applied, `migrate status` shows it as drifted and `migrate up` refuses to run until you reconcile it (or pass `--allow-drift`).

## Schema diffing

`schemaDiff()` connects to a live Postgres database, compares it with a `SchemaDef`, and returns the DDL needed to close the gap. It powers `migrate create --auto`. The signature is `schemaDiff(schema, connectionString)`, returning a `Promise<DiffResult>`. Both `schemaDiff` and `introspect` are exported from the package root; there is no `turbine-orm/introspect` subpath:

```ts
import { schemaDiff } from 'turbine-orm';
import schema from './turbine/schema.js';

const diff = await schemaDiff(schema, process.env.DATABASE_URL!);

// diff.statements: SQL to apply (UP direction), ready to run in order
for (const sql of diff.statements) {
  console.log(sql);
}

// diff.warnings: changes the diff detected but refuses to apply automatically
for (const warning of diff.warnings ?? []) {
  console.warn(warning);
}
```

`DiffResult` has the shape `{ create, alter, drop, statements, reverseStatements, warnings }`:

- `create`, `alter` and `drop` are the structured plan: tables to create, tables to alter, and table names present in the database but absent from the schema.
- `statements` is the flat SQL to apply, and `reverseStatements` the DOWN direction.
- `warnings` lists changes the diff detected but will not apply, such as enum value removals and reorders.

Destructive changes stay out of `statements`. Table and column **drops are reported** (in `drop` and in the `alter` plan) **but never emitted** into the executable SQL, so you apply those by hand.

Auto-generated migrations are a starting point: review them before you commit. For the limits of `--auto` (blind type casts, undetected renames, `SET NOT NULL` without a backfill) and the recipe for changing a populated column's type, see [Migrations in Practice](/migrate).

## Introspection

If you already have a database, point Turbine at it:

```bash
npx turbine pull
# or: npx turbine generate
```

Turbine reads `information_schema` and `pg_catalog` to discover:

- Tables and columns (with types, nullability, defaults)
- Primary keys, unique constraints, foreign keys
- Indexes (including composite and partial)
- Enum types
- Inferred relations (hasMany / belongsTo / hasOne) from foreign keys
- `STORED` generated columns (read-only, omitted from write inputs)

Pass `--include-views` to also introspect views and materialized views as read-only entities. See [Views & Generated Columns](/views).

> **Note:** When a derived relation name would collide with a scalar column (a `currentVersionId` foreign key producing a relation named `currentVersion`, for example), the relation gets a disambiguated name instead of overwriting the column. Names without a collision are kept, so regenerating an existing schema does not rename its relations. The `turbine mcp` server and the SQLite, MySQL and SQL Server introspectors use the same naming logic.

Three files land in `./generated/turbine/`:

- **`types.ts`**: entity interfaces (singularized PascalCase), `*Create` types, `*Update` types, and relation-included `*With*` types.
- **`metadata.ts`**: the runtime `SchemaMetadata` with column maps, relations and indexes. `turbineHttp()` needs it in edge runtimes.
- **`index.ts`**: a `TurbineClient` subclass with typed `declare readonly` table accessors, plus a `turbine()` factory function.

## Type mapping

Turbine maps Postgres types to TypeScript:

| Postgres | TypeScript | Notes |
|---|---|---|
| `int2`, `int4`, `float4`, `float8` | `number` | Standard numeric types |
| `int8` / `bigint` | `number` | Values > `Number.MAX_SAFE_INTEGER` are returned as `string` to avoid precision loss. Writes also accept a `string` or `bigint` |
| `numeric`, `money` | `string` | Arbitrary precision, kept as a string to avoid JS float issues. A `numeric` write also accepts a `number` |
| `text`, `varchar`, `uuid`, `citext` | `string` | |
| `timestamptz` | `Date` | Carries a zone on the wire, so the instant is unambiguous |
| `timestamp`, `date` | `Date` | Zone-less. Read as UTC, not as the process's local zone. See [Zone-less columns](#zone-less-columns-timestamp-and-date-read-as-utc) |
| `time`, `timetz` | `string` on read, `string \| Date` on write | No date part, so never coerced to a `Date` on read. See [Time-of-day columns](#time-of-day-columns-time-and-timetz) |
| `interval` | `{ years?, months?, days?, hours?, minutes?, seconds?, milliseconds? }` | The driver's parsed object; a zero field is absent. Writes take the text form (`'1 day 02:00:00'`) |
| `point`, `circle` | `{ x, y }`, `{ x, y, radius }` | Parsed by the driver; writes take the text form. Other geometric types stay `string` |
| `macaddr8`, `bit`, `varbit`, ranges, multiranges | `string` | The text form, `'[1,5)'` for a range |
| `boolean` | `boolean` | |
| `json`, `jsonb` | `unknown` | Give it a type with [`tsType`](#typing-a-json-column-tstype) or `columnTypes` |
| `bytea` | `Buffer` | |
| Array types | `T[]` | `_text` → `string[]`. `date[]` and `timestamp[]` follow their scalar forms. `bigint[]` is `string[]` (the driver's array parser does not apply the scalar `int8` rule), and `circle[]` is `string[]` |

### Zone-less columns: `timestamp` and `date` read as UTC

A `timestamptz` carries its offset on the wire. A `timestamp` (without time zone) and a `date` do not: the database sends `2026-07-21 09:30:00` or `2026-07-21`, and something has to decide which instant that is. The pg driver defaults to the process's local zone, which makes the same stored row a different `Date` in every deployment region. Turbine reads UTC instead, the convention Prisma, Rails and Django use.

The read half is a set of pg type parsers on OIDs 1114 (`timestamp`), 1082 (`date`) and their array forms 1115 and 1182. The same rule applies to dates coerced out of nested-relation JSON, so every read path agrees, and scalar and array columns cannot disagree. The write half matches: binding a `Date` to a zone-less column renders its **UTC** components. A local read against a UTC write would make each read-modify-write cycle on a `date` move the stored day backward east of UTC, and `where: { runOn: row.runOn }` would match nothing.

SQLite, MySQL and SQL Server follow the same write rule: a `Date` written to or compared with a `date` column binds its UTC day (`YYYY-MM-DD`). On SQLite, rows written by versions before 0.90 hold the full ISO text and do not match an equality on the column until you rewrite them:

```sql
UPDATE events SET run_on = substr(run_on, 1, 10) WHERE length(run_on) > 10;
```

```ts
// Stored: date '2026-07-21'. Process running in Europe/Berlin (UTC+2).
const job = await db.jobs.findUniqueOrThrow({ where: { id: 1 } });

job.runOn.toISOString();          // '2026-07-21T00:00:00.000Z'
job.runOn.toISOString().slice(0, 10); // '2026-07-21'  <- format a date like this
```

<Callout type="warning" title="Format a `date` in UTC">
  A stored `date` reads as UTC midnight. West of UTC, local-component helpers
  show the previous evening: `toLocaleDateString()` on a stored `2026-07-21`
  returns `7/20/2026`. **Format a `date` in UTC** (`toISOString().slice(0, 10)`),
  never with local-component helpers (`toLocaleDateString()`, `getDate()`,
  `date-fns` / `dayjs` `format('yyyy-MM-dd')`).

  Upgrading from before v0.54, where a `date` read at local midnight: the
  calendar day is unchanged, but the epoch value moves by your process's UTC
  offset, and nothing warns you. `getTime()`, `toISOString()` and
  `JSON.stringify(row)` change for any process not running in UTC, and so does
  any API payload, export or golden file containing a `date` column. Nothing
  stored in the database changes, no emitted SQL changes, and a process running
  in UTC sees no difference.
</Callout>

<Callout type="note" title="utcTimestamps is process-wide, not per client">
  `utcTimestamps: false` opts out and reverts **both** halves: reads go back to
  the local zone, and writes bind local-calendar literals.

  The read half is installed with `pg.types.setTypeParser`, which sets one
  parser per OID for the whole `pg` module. So a Turbine-owned pool changes
  `date` / `timestamp` parsing for every user of that module in the process,
  including pools that already exist and are already querying. If something
  else customized the OID first, Turbine replaces it and warns once.

  The first client settles the value. A later client asking for the opposite
  throws `ValidationError` (`TURBINE_E003`) at construction, rather than
  reading and writing in different zones. Give every client in the process the
  same value, or isolate the odd one in its own process.

  A client on an **external pool** (`pool: …`, `turbineHttp()`) never registers
  parsers, but it reads through the ones an owned client installed, so it takes
  part in the same check.
</Callout>

### `infinity` and `-infinity`

Postgres accepts `infinity` and `-infinity` in `date`, `timestamp` and `timestamptz` columns, usually to model "no end date" without a nullable column. **Turbine reads both as the JS numbers `Infinity` / `-Infinity` by default.** No JavaScript `Date` represents either value, so every possible reading gives something up: an `Invalid Date` is silent and `NaN` everywhere, `null` cannot be told apart from a stored `NULL`, and a number breaks the field's declared `Date` type at runtime. The number is the only one of the three that cannot **lose** the value.

The reading is applied in one place, the ORM row parser, so every read path agrees: top-level reads, `findUnique` / `findFirst`, streaming, the join / batched / flatten strategies, the positional wire encoding, write `RETURNING` / reselect / `OUTPUT` projections, `groupBy` keys and `_min` / `_max`.

<Callout type="warning" title="Why the number, and not the nicer-looking `null`">
  Because `null` destroys data without an error. Under a `null` reading, a
  stored `infinity` and a stored `NULL` look the same. So the most common write
  shape, `const row = await db.leases.findUnique(...)` then
  `db.leases.update({ where, data: { ...row, note } })`, writes SQL `NULL` over
  the column and the `infinity` is gone. On a `NOT NULL` column that write at
  least fails with `NotNullViolationError` (`TURBINE_E010`); on the nullable
  columns where `expiresAt` / `validUntil` usually live, it succeeds.

  Turbine logs a one-time warning (code `temporal-infinity`) naming the table
  and field the first time it reads a stored infinity. Like the unlimited-read
  warning, it is always on, including under `NODE_ENV=production`, because
  production is where a `Date` method throws on live traffic. It fires once per
  process per field, and only on a row that held an infinity. Setting
  `temporalInfinity` explicitly, to `'preserve'` (the default reading) or
  `'null'`, silences it.
</Callout>

What the default costs, on exactly the rows that hold an infinity:

- **`Date` methods throw.** The generated type says `Date` and the value is a `number`, so `row.validUntil.toISOString()` and `.getTime()` raise a `TypeError`. Guard with `typeof row.validUntil === 'number'` (or `Number.isFinite`) before calling a `Date` method on a column that can hold one.
- **`JSON.stringify` renders `null`**, because JSON has no infinity literal.
- **`where: { validUntil: null }` still compiles to `IS NULL`** and does **not** match these rows. Filter them with `where: { validUntil: 'infinity' }`. Making `null` match both would change every null predicate on every temporal column.

#### `temporalInfinity: 'null'`

```ts
const db = turbine({ connectionString: process.env.DATABASE_URL, temporalInfinity: 'null' });
```

Reads a stored infinity as `null` instead. `JSON.stringify` then matches the value, a nullable column's declared `Date | null` type holds so no method call throws, and every read strategy still agrees. The cost is the data loss above, plus three consequences:

- **`groupBy` keys stop being unique.** `GROUP BY` returns one row per distinct stored value, and the ORM then labels `infinity`, `-infinity` and SQL `NULL` all as `null`. Three rows holding those three values come back as three groups keyed `null`, so a `Map` or `Object.fromEntries` built from the group value keeps only one of the three counts. `distinct: ['col']` has the same problem.
- **`+infinity` and `-infinity` collapse into each other**, not only into `NULL`. On a `validUntil` column that puts "never expires" and "expired forever" in the same bucket.
- **`_max` can be `null` on a table that clearly has rows.** With `2026-01-01`, `2026-06-01` and `infinity` stored, `aggregate` reports `_min: 2026-01-01`, `_max: null`, `_count: 3`, and `_max: null` is also what an empty table returns.

Pick `'null'` when the rows are read-only in that code path and the declared type matters more than the stored value; never write rows read under it back. Keep the default when anything reads a row and writes it again, which is most code.

Neither reading changes the write path: `'infinity'`, `'-infinity'`, `Infinity` and `-Infinity` all remain bindable, and a value read as `null` is still recoverable if you know what it held.

### Time-of-day columns: `time` and `timetz`

A `time` / `timetz` column has no date part, so Turbine never turns it into a JS `Date` on read. It comes back as the driver's string, `'09:00:00'`, and the generated row type is `string`.

On **write** the column also accepts a `Date`. Turbine narrows it to a time-of-day literal built from the Date's **UTC** components, so the generated `*Create` and `*Update` input types are widened to `string | Date`:

```ts
// Both write 09:00:00
await db.shifts.create({ data: { startsAt: '09:00:00' } });
await db.shifts.create({ data: { startsAt: new Date('1970-01-01T09:00:00Z') } });
```

Using UTC rather than the local zone matches what Prisma does with a `DateTime @db.Time(6)` field, so a ported call site stores the same value, and the value round-trips wherever the process runs. `timetz` gets an explicit `+00:00` so the session's `TimeZone` cannot be attached instead, and fractional seconds are emitted only when non-zero.

The coercion runs on every write path (`create`, `createMany`, `upsert`, and the `update` `set` clause). Widening the input type is the only type change, so existing code still compiles.

<Callout type="warning" title="One place still takes a string: aggregate `having`">
  A `Date` compared against a `time` / `timetz` column is narrowed the same way
  in a `where` clause (`WHERE "starts_at" >= $1` binds `'09:00:00'`), including
  the `findUnique` equality fast path, and in a scalar `having` predicate on a
  `groupBy` group key.

  It is **not** narrowed inside an *aggregate* `having` filter
  (`having: { startsAt: { _min: { gte: someDate } } }`). That operand is
  compared against `MIN("starts_at")`, not against the column, and it is bound
  as a full timestamp, which Postgres rejects with `22007 invalid input syntax
  for type time`. Pass a string there: `{ _min: { gte: '09:00:00' } }`.
</Callout>
