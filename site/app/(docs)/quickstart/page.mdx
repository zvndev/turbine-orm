# Quick Start

Install Turbine, point it at your database, generate a typed client, and run your first query.

## Requirements

- **Node.js ≥ 20** (the package `engines` field). The optional [SQLite engine](/engines) uses Node's built-in `node:sqlite` and needs **Node ≥ 22.5**.
- **PostgreSQL 14+** for the default path. Neon, Vercel Postgres, Supabase and a local server all work. Other engines are covered under [Database Engines](/engines).
- **`"type": "module"`** in your `package.json` is recommended. Turbine is ESM-first, but the CLI also works in CommonJS projects (the `npm init -y` default) and loads `turbine.config.ts` and schema files either way.
- **`tsx` as a dev dependency**, so the CLI can load TypeScript files: `turbine.config.ts`, `turbine/schema.ts` and TypeScript seeds.

## 1. Install

```bash
npm install turbine-orm
npm install --save-dev tsx
```

Turbine has one runtime dependency, `pg`. You can import the library from ESM or CommonJS.

To make your project ESM, add this to `package.json`:

```json
{
  "type": "module"
}
```

## 2. Set `DATABASE_URL`

Turbine reads the standard Postgres connection string from the environment. For local development, put it in a `.env` file:

```bash
# .env
DATABASE_URL=postgres://user:pass@localhost:5432/mydb
```

## 3. Initialize the project

```bash
npx turbine init
```

This creates `turbine.config.ts` at the project root and a `turbine/` directory for your schema and migrations:

```ts
// turbine.config.ts
import type { TurbineCliConfig } from 'turbine-orm/cli';

const config: TurbineCliConfig = {
  url: process.env.DATABASE_URL,
  out: './generated/turbine',
  schema: 'public',
  migrationsDir: './turbine/migrations',
  schemaFile: './turbine/schema.ts',
};

export default config;
```

> **`schema` vs `schemaFile`:**  
> - **`schema`** is the Postgres schema name, the namespace. It is almost always `'public'`.  
> - **`schemaFile`** is the path to your `defineSchema()` file, used by `turbine push` and auto-diff migrations.  
>  
> Never put a file path in `schema`. Introspection would look for tables in a schema named `'./turbine/schema.ts'` and find none.

## 4. Generate the typed client

Pick the path that matches your database.

### Path A, Existing tables

If the database already has tables, introspect them:

```bash
npx turbine generate
# or: npx turbine pull
```

### Path B, Empty database

If the database is empty, or you want to own the schema in TypeScript, define the tables first:

1. Write your tables in `turbine/schema.ts` with `defineSchema(...)`. See [Schema & Migrations](/schema).
2. Apply them to the database:

```bash
npx turbine push
```

3. Generate the typed client from the live schema:

```bash
npx turbine generate
```

`push` is the fast path for local work. In production, use SQL migrations (`turbine migrate`); see the [schema page](/schema).

### What gets written

Either path writes three files to `./generated/turbine/`, or to your config's `out`:

- `types.ts`: entity interfaces and `Create` / `Update` input types
- `metadata.ts`: runtime schema metadata
- `index.ts`: a typed `TurbineClient` subclass with table accessors

## 5. Your first query

```ts
import { turbine } from './generated/turbine/index.js';

// No arguments needed: turbine() reads DATABASE_URL from the environment.
// (Pass { connectionString } explicitly if you'd rather not rely on the env var.)
const db = turbine();

const users = await db.users.findMany({
  where: { role: 'admin' },
  orderBy: { createdAt: 'desc' },
  limit: 10,
});

console.log(users);

await db.disconnect();
```

> **Loading `.env` in your app:** the `turbine` CLI loads a local `.env` for you.
> Your application does not, because the library never reads files. Set
> `process.env.DATABASE_URL` the usual way: run with Node's
> `node --env-file=.env app.js` (Node 20.12+), call `process.loadEnvFile()` at
> startup, or use a framework that loads `.env` itself, such as Next.js.

`db.users` is fully typed. Autocomplete lists every column, operator and relation, and the result types follow: `users[0].createdAt` is a `Date` and `users[0].email` is a `string`.

## 6. Add nested relations

```ts
const usersWithPosts = await db.users.findMany({
  where: { orgId: 1 },
  with: {
    posts: {
      with: { comments: { with: { user: true } } },
      orderBy: { createdAt: 'desc' },
      limit: 5,
    },
  },
});

// One statement, one round-trip, fully typed all the way down:
usersWithPosts[0].posts[0].comments[0].user;
```

> **Where `user` comes from.** Introspection names a to-one relation after the table it points at. `comments.user_id` referencing `users.id` becomes `comments.user`, and the reverse side becomes `users.comments`. To call it `author` instead, add `relationNames: { comments: { user: 'author' } }` to `turbine.config.ts` and run `generate` again; the database does not change. Renaming a relation that does not exist is an error.

Turbine compiles the `with` clause into one SQL statement built from PostgreSQL's `json_agg` and correlated subqueries, so there is no N+1 and no client-side stitching. The default `'auto'` strategy keeps that plan, except for a relation whose correlation column has no covering index: that relation loads in one flat follow-up statement instead. The rows are identical either way. To always get the single statement, set `relationLoadStrategy: 'join'`. See [Load strategies](/relations#load-strategy-auto-join-batched-flatten).
