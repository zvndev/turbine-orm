# Typed Errors

Turbine throws typed errors you can catch with `instanceof` or by code. Every error Turbine raises extends `TurbineError` and carries a stable `readonly code` field, such as `TURBINE_E008`. PostgreSQL driver errors with a known SQLSTATE (23505, 23503, 40P01 and others) are translated into these classes by `wrapPgError()`. A driver error whose SQLSTATE Turbine does not map stays outside the hierarchy, with the SQLSTATE on `.code` (see [unmapped SQLSTATEs](#unmapped-sqlstates)).

Messages start with the code tag (`[TURBINE_E008] …`) so logs are greppable. **Do not parse the message**: branch on `err.code` or `instanceof`.

Both checks work when a process loads the package twice, once as ESM and once as CommonJS. That happens in a `"type": "commonjs"` project whose generated client is `require`d while an `.mts` entry `import`s the package, in a CJS library that wraps Turbine, or in a Jest setup. Every error carries a cross-copy brand, and each class implements `Symbol.hasInstance` over that brand and the error's code, so `err instanceof UniqueConstraintError` is true whichever copy threw it. Comparing `err.code` needs no import at all, which makes it the better check in a shared handler or a library.

Every error also carries `readonly docsUrl` (for example `https://turbineorm.dev/errors#e008`, an anchor into the table below), and its message ends with the same link. A unit test asserts every code has its row and anchor here.

Also the next pull on a cursor stream that Turbine closed after its [idle timeout](/queries#abandoned-streams-close-themselves) (`outcome: 'not-executed'`). Transactions: a query on a `tx` whose transaction has settled, a callback that returned while a query it started was still running, a statement through the outer `tx` inside an open nested `tx.$transaction` block, a transaction-control statement (`COMMIT`, `ROLLBACK`, `BEGIN`, `SAVEPOINT` and the like) sent through `raw`, `rawUnsafe`, `sql` or `$connection()` inside a transaction, `end()` or `connect()` on a transaction's connection, a `sessionContext` name without a dot that is not in `allowBuiltinSettings`. Raw SQL: an array passed to `raw` / `sql` in place of a tagged template, a `?` placeholder or a `$n` with no value in `rawUnsafe` on SQLite, MySQL or SQL Server. Client construction: a static global filter with a bad operand or an `undefined` value, a global filter that reaches its own table through relation filters, a malformed `sqlComment` option. A function global filter that returns `undefined` is refused when the query runs. Engines: a MySQL `in` / `notIn` list that takes the statement past 65,535 placeholders, a string that is not a number written to a numeric or boolean column on SQLite, an enum column `schemaToSQL` cannot declare off PostgreSQL (not in `defineSchema`'s `enums`, or no labels), a column default it cannot write; on PowDB, a number, bigint or boolean compared with or written to a `Date` column, a value that is not one of an enum column's labels, and `contains` / `startsWith` / `endsWith` / `mode: 'insensitive'` / `_sum` / `_avg` on an enum column |

| <a id="e017" /> `TURBINE_E017` | `UnsupportedFeatureError` | A Postgres-only feature (pgvector, LISTEN/NOTIFY, RLS `sessionContext`) invoked on a non-Postgres engine. | <a id="e018" /> `TURBINE_E018` | `ReadOnlyError` | A write refused because the database, the role or the transaction is read-only. Exposes `reason: 'snapshot' \| 'rbac' \| 'transaction'` (PowDB snapshot serving, a read-only role, a read-only transaction or replica) |
| <a id="e019" /> `TURBINE_E019` | `TransactionRolledBackError` | A transaction PostgreSQL rolled back instead of committing: a statement inside it failed (and the callback caught the error), or a per-query `timeout` cancelled one. The first failure is `cause`. See [a caught error still rolls the transaction back](/transactions#a-caught-error-still-rolls-the-transaction-back) |
| <a id="e020" /> `TURBINE_E020` | `InvariantError` | Turbine caught a bug in itself before sending a statement it knew was wrong: two internal paths that must agree did not, for example the SQL-template cache producing parameters that differ from a fresh build of the same query. Exposes `invariant`, a stable id of the broken rule (`'sql-cache-lockstep'`, `'sql-cache-param-count'`, `'where-scope-reference'`, `'relation-payload-json'`, and on PowDB `'powql-relation-filter-unresolved'`, `'powql-json-operator'`, `'powql-json-filter-empty'`, `'powql-filter-empty'`). Not caused by the arguments and not retryable: report it at https://github.com/zvndev/turbine-orm/issues with the message, which names the query shape and no row or parameter value |

## Catching typed errors

Import the classes from the package root and narrow with `instanceof`.

```ts
import {
  NotFoundError,
  ValidationError,
  TimeoutError,
  UniqueConstraintError,
} from 'turbine-orm';

try {
  const user = await db.users.findUniqueOrThrow({ where: { id: 999 } });
} catch (err) {
  if (err instanceof NotFoundError) {
    // err.code === 'TURBINE_E001'
    // err.table, err.where, and err.operation are all populated
    return { status: 404 };
  }
  if (err instanceof ValidationError) {
    // err.code === 'TURBINE_E003'
    return { status: 400, message: err.message };
  }
  if (err instanceof TimeoutError) {
    // err.code === 'TURBINE_E002'
    // err.timeoutMs is the configured limit
    return { status: 504 };
  }
  throw err;
}
```

### Unknown field names

Every name you supply is resolved against the schema. A name that does not
resolve throws `TURBINE_E003`, naming the table and, where it can, the column you
probably meant. This holds for `where`, `orderBy`, `distinct`, `groupBy` keys,
aggregate targets, create/update `data`, and `select` / `omit`, at every depth,
including inside a relation. A name is never dropped, and the query never runs
without it.

Naming a **relation** in `select` or `omit` gets its own message, because it is
usually a Prisma habit rather than a typo:

```
[TURBINE_E003] "comments" is a relation on table "post", not a column, so it
cannot be named in `select`. Load it with `with: { comments: true }`, which is
a sibling of `select`, not a member of it.
```

Relations live in [`with`](/relations), which sits beside `select`, not inside
it. To narrow a relation's own columns, put a `select` inside that relation's
options: `with: { comments: { select: { body: true } } }`.

## `wrapPgError` translation

Every query execution runs its pg error through `wrapPgError()`. The original driver error is kept as `.cause` on the wrapped error.

| pg SQLSTATE | Name | Turbine class |
|---|---|---|
| `23505` | unique_violation | `UniqueConstraintError` |
| `23503` | foreign_key_violation | `ForeignKeyError` |
| `23502` | not_null_violation | `NotNullViolationError` |
| `23514` | check_violation | `CheckConstraintError` |
| `23P01` | exclusion_violation | `ExclusionConstraintError` |
| `40P01` | deadlock_detected | `DeadlockError` (retryable) |
| `40001` | serialization_failure | `SerializationFailureError` (retryable) |
| `55P03` | lock_not_available | `LockNotAvailableError` (E013, retryable) |
| `57014` | query_canceled | `TimeoutError` (E002, `outcome: 'not-executed'`) |
| `25006` | read_only_sql_transaction | `ReadOnlyError` (E018, `reason: 'transaction'`) |
| `25P02` | in_failed_sql_transaction | `TransactionRolledBackError` (E019) |
| class `08`, `28000`, `28P01`, `3D000`, `42P05`, `26000`, `53300`, `57P01`, `57P02`, `57P03`, `25P03` | connection failure, refused login, unknown database, a pooler's prepared-statement mismatch, too many connections, server shutdown, idle-in-transaction timeout | `ConnectionError` (E004) |
| `08P01` with severity `ERROR` | protocol_violation on one message, usually a `Buffer` bound to a non-`bytea` column | `ValidationError` (E003) |
| `42883` | undefined_function: no operator or function for these argument types | `ValidationError` (E003) |
| class `22` (`22P02`, `22003`, `22001`, `22007`, `22008`, `22012`) | data_exception: a bad enum label, numeric overflow, a value too long, a bad date, division by zero | `ValidationError` (E003), naming the column when the driver reports one |
| `42601` from `to_tsquery` | syntax_error in a `search` query string | `ValidationError` (E003) with a hint about the search syntax |

For class `22`, `08P01` and the `42601` search case, the offending value sits in the driver's own message text. So the wrapped `ValidationError` names the column (when the driver reports one), gives a value-free account of the problem (`the value could not be parsed as the column type`, `the number is out of range for the column type`, ...) and the SQLSTATE. Under `errorMessages: 'verbose'` the account is the driver's text, and `.detail` carries it. Under the default `'safe'` mode the driver's text is kept out of the message, out of `.detail` and out of the `.cause` error's message.

Any other SQLSTATE stays outside the `TurbineError` hierarchy: there is no `TURBINE_` code, and `.code` is the SQLSTATE. See [unmapped SQLSTATEs](#unmapped-sqlstates).

```ts
import { UniqueConstraintError } from 'turbine-orm';

try {
  await db.users.create({ data: { email: 'taken@example.com', ... } });
} catch (err) {
  if (err instanceof UniqueConstraintError) {
    // err.constraint, e.g. 'users_email_key'
    // err.columns  , e.g. ['email']
    // err.table    , e.g. 'users'
    // err.cause    , the original pg error
    return { status: 409, message: 'Email already in use' };
  }
  throw err;
}
```

## Retryable errors

`DeadlockError` and `SerializationFailureError` (and its subclass `LockNotAvailableError`) expose a `readonly isRetryable = true as const` field, a type-level signal a retry loop can narrow on.

You do not have to write that loop. Turbine exports **`withRetry`**, and `TurbineClient` exposes the same function as **`db.$retry`**:

```ts
import { withRetry } from 'turbine-orm';

await withRetry(() =>
  db.$transaction(
    async (tx) => {
      const row = await tx.counters.findUniqueOrThrow({ where: { id: 1 } });
      await tx.counters.update({
        where: { id: 1 },
        data: { value: row.value + 1 },
      });
    },
    { isolationLevel: 'Serializable' },
  ),
);
```

`withRetry(fn, options?)` retries only when the thrown error carries `isRetryable === true`, and rethrows anything else at once. Options: `maxAttempts` (default `3`), `baseDelay` in ms (default `50`), `maxDelay` (default `5000`) and an `onRetry(error, attempt)` hook. Backoff is exponential with jitter, capped at `maxDelay`.

## Pipeline errors

`PipelineError` is thrown only when a pipeline runs in non-transactional mode (`{ transactional: false }`) and one or more queries fail. It carries a per-query result array showing which queries succeeded and which failed.

```ts
import { PipelineError } from 'turbine-orm';

try {
  await db.pipeline(queries, { transactional: false });
} catch (err) {
  if (err instanceof PipelineError) {
    // err.results: ({status:'ok', value} | {status:'error', error})[]
    // err.failedIndex: zero-based index of the first failed query
    // err.failedTag: DeferredQuery.tag of the first failure
    for (const [i, slot] of err.results.entries()) {
      if (slot.status === 'error') {
        console.error(`Query ${i} failed:`, slot.error);
      }
    }
  }
}
```

Transactional pipelines (the default) either fully succeed or roll back. A failure surfaces as whichever typed error the failing query raised.

## Unsupported features on other engines

`UnsupportedFeatureError` (`TURBINE_E017`) is thrown when you call a **PostgreSQL-only** feature on one of Turbine's other [database engines](/engines): SQLite, MySQL or SQL Server. It is not a `wrapPgError()` translation. Turbine raises it directly, from a capability flag on the active dialect, instead of generating broken SQL. The PostgreSQL-only features are pgvector distance operators, LISTEN/NOTIFY realtime (`$listen` / `$notify`) and RLS `sessionContext` (`$withSession`).

```ts
import { UnsupportedFeatureError } from 'turbine-orm';
import { turbineMysql } from 'turbine-orm/mysql';

const db = await turbineMysql(process.env.MYSQL_URL!, SCHEMA);

try {
  await db.$listen('orders', (payload) => console.log(payload));
} catch (err) {
  if (err instanceof UnsupportedFeatureError) {
    // err.code    === 'TURBINE_E017'
    // err.feature === '$listen (LISTEN/NOTIFY realtime)'
    // err.dialect === 'mysql'
  }
}
```

`TURBINE_E017` is not only a "wrong engine" error. It means *Turbine cannot do that here*, and PostgreSQL raises it too:

- `relationLoadStrategy: 'batched'` on a **composite-key** relation, including a composite-key many-to-many junction. The batched loader keys on one column, so it refuses rather than load the wrong rows. Use the default join plan for those relations.
- `relationLoadStrategy: 'batched'` where the **correlation key is missing from every parent row**. The batched loader stitches rows in JavaScript and needs that column in the parent rows. Without it the relation would come back silently empty, so the loader refuses, naming the relation and the key. This should not be reachable. If you hit it, report it, and use `relationLoadStrategy: 'join'` on that query in the meantime.
- On [`turbine-orm/prisma-compat`](/migrate-from-prisma), a Prisma shape with no Turbine equivalent: a **negative `take`**, `skip` on a nested `include`, the [inclusive-cursor shapes](/migrate-from-prisma#cursor-pagination) that cannot be translated exactly, `limit` on `updateMany` / `deleteMany`, and `$extends` with a `query` or `result` component. Any other component the adapter does not implement is refused at `$extends` time, with the alternative named.

Catch on `err.code === 'TURBINE_E017'` and read `err.feature`, which names what was refused. See [Database Engines](/engines) for the full capability matrix.

The same error covers PowDB's **version-gated** capabilities, where the feature exists but the connected engine is too old for it. The message names the feature, the minimum version and what the connection reported:

```
[TURBINE_E017] JSON path filters is unsupported on "PowDB". Requires PowDB >= 0.12;
this connection reports 0.11.0. Upgrade powdb-server / @zvndev/powdb-embedded
(or pass `assumeEngineVersion` if the version cannot be detected).
```

Some gates add a sentence naming a workaround. `err.feature` is the label from the first sentence, and `err.dialect` is `'PowDB'`.

## Read-only refusals

`ReadOnlyError` (`TURBINE_E018`) tells you a write hit something read-only, so you can route it elsewhere. Its `reason` field says what:

- **`'snapshot'`**: the database itself is read-only. That is a PowDB `--readonly` snapshot server, an embedded `{ readonly: true }` open, or Turbine's own client-level `readonly: true` fail-fast flag. Nothing can write here, so route the write to your primary.
- **`'rbac'`**: the database is writable, but this connection's role may not write (`permission denied: role …`). Reconnecting with a writer role may be enough.
- **`'transaction'`**: the transaction is read-only. It was opened with `BEGIN READ ONLY` or `SET TRANSACTION READ ONLY`, or it runs on a hot-standby read replica. A write inside `$transaction(fn, { readOnly: true })` lands here too. PostgreSQL SQLSTATE `25006` and MySQL error 1792 map here. Run the write in a read-write transaction on the primary.

```ts
import { ReadOnlyError } from 'turbine-orm';

try {
  await replica.orders.create({ data });
} catch (err) {
  if (err instanceof ReadOnlyError && err.reason === 'snapshot') {
    await primary.orders.create({ data }); // route to the writer
  }
}
```

See [Read Replicas](/read-replicas) for the snapshot-serving pattern this supports.

## Safe error messages

By default, `NotFoundError` messages include only the **keys** of the `where` clause. Values are redacted so PII does not leak into logs (Sentry, Datadog).

```
[TURBINE_E001] findUniqueOrThrow on "users" found no record matching where: { id, email }
```

The full `where` object is still available as `err.where`; only the message is redacted. In safe mode `where` is not enumerable, so `JSON.stringify(err)` and error serializers that walk own properties do not carry it into logs. Read `err.where` directly.

To get verbose messages (useful in local development), set `errorMessages: 'verbose'` in your `TurbineConfig`, or call `setErrorMessageMode('verbose')` at startup.

```ts
const db = turbine({
  connectionString: process.env.DATABASE_URL,
  errorMessages: process.env.NODE_ENV === 'development' ? 'verbose' : 'safe',
});
```

### What safe mode redacts

Safe mode redacts the four PostgreSQL error fields that can carry a row value: `detail`, `hint`, `where` (the CONTEXT line) and `internalQuery`. Each is replaced on both the returned error and its `.cause`, so nothing a logger walks holds the value. `hint` matters because a `RAISE ... USING HINT` interpolates whatever the function author put there. `internalQuery` carries the text an `EXECUTE format(...)` built, bound values included.

## Unmapped SQLSTATEs

A driver error whose SQLSTATE has no typed class reaches you as **an error of the driver's own class**, not a `TurbineError`, in both message modes. That way a logging setting never moves one database failure into a different `catch` branch.

- Under `'verbose'`, it is the raw driver error, unchanged.
- Under `'safe'`, it is a clone with the value-bearing fields redacted and the original on `.cause`. The clone repeats the SQLSTATE on `.sqlstate`, the name the typed errors use.

In both modes the SQLSTATE is on `.code`:

```ts
try {
  await db.orders.findMany();
} catch (err) {
  if (err instanceof TurbineError) handleTyped(err);
  else if ((err as { code?: string }).code === '42P01') runMigrations();
}
```

Under `'safe'` the **message** is kept when the SQLSTATE class's grammar cannot hold a row value, and withheld when it can:

| Class | Example | Message under `safe` |
| --- | --- | --- |
| `42` (except `42601`) | `42P01`, `42703` | kept: `relation "orders" does not exist` |
| `08`, `3D`, `3F`, `53`, `57`, `58` | connection, catalog, resource, operator, system | kept |
| `42601` | syntax error | withheld: the message quotes a token of the statement, and a token can be a string literal |
| `P0001`, class `55` | `RAISE EXCEPTION` from your own function | withheld: that text is yours, and nothing here knows what is in it |
| everything else | | withheld |

A withheld message says so and names the setting that shows it:

```
Database error P0001 (driver text withheld by errorMessages: 'safe'; set errorMessages: 'verbose' to see it)
```
