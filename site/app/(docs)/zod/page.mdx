# Zod Schemas

`turbine generate --zod` writes a `zod.ts` file next to your generated types, with a [Zod](https://zod.dev) schema per table. Use it to validate request bodies, form input or any other untrusted data against the shape your database expects. The schemas come from column metadata, so regenerating keeps them in step with the database.

```bash
npx turbine generate --zod
```

This adds a fourth file to the output directory, alongside `types.ts`, `metadata.ts` and `index.ts`:

- **`zod.ts`**: `XSchema`, `XCreateSchema` and `XUpdateSchema` for each table.

The generated file imports `zod`, but the Turbine runtime never does, so install Zod yourself:

```bash
npm install zod
```

## The three schemas

For a `posts` table, generation emits:

```ts
import { z } from 'zod';

// Full entity, every column
export const PostSchema = z.object({
  id: z.number(),
  title: z.string(),
  views: z.number(),
  published: z.boolean(),
  createdAt: z.coerce.date(),
});

// Create input: server-generated, defaulted and nullable columns optional
export const PostCreateSchema = z.object({
  id: z.number().optional(),
  title: z.string(),
  views: z.number().optional(),
  published: z.boolean(),
  createdAt: z.coerce.date().optional(),
});

// Update input, every non-PK column optional, PK omitted
export const PostUpdateSchema = z.object({
  title: z.string().optional(),
  views: z.number().optional(),
  published: z.boolean().optional(),
  createdAt: z.coerce.date().optional(),
});
```

`XCreateSchema` and `XUpdateSchema` mirror the generated `*Create` / `*Update` input types:

- The create schema makes server-generated (serial / identity), defaulted and nullable columns optional. A primary key that is none of those is **required**: a `text` natural key, a client-supplied `uuid` with no database default, or a composite key of plain integers.
- The update schema makes every non-PK column optional and drops the primary key.

## Type mapping

| Column | Zod |
|---|---|
| `text`, `varchar`, `uuid` | `z.string()` |
| `int`, `bigint`, `float` | `z.number()`. The create and update schemas also accept a string or a `bigint` for a `bigint` column. |
| `numeric` | `z.string()`, since `numeric` reads as exact decimal text. The create and update schemas also accept a number. |
| `boolean` | `z.boolean()` |
| `timestamp`, `date` | `z.coerce.date()` |
| `json`, `jsonb` | `z.unknown()` |
| enum column | `z.enum([...labels])` |
| array column | element schema `.array()` |
| `vector` | `z.array(z.number())` |
| nullable column | schema `.nullable()` |

`z.coerce.date()` accepts both `Date` objects and date strings, so it validates JSON request bodies, where dates arrive as strings.

`STORED` generated columns are left out of `XCreateSchema` and `XUpdateSchema` because you cannot write them (see [Views & Generated Columns](/views)). They stay in the full `XSchema`.

## Using the schemas

```ts
import { PostCreateSchema } from './generated/turbine/zod.js';

// Validate an untrusted request body before writing
const data = PostCreateSchema.parse(await req.json());
const post = await db.posts.create({ data });
```
