# Why Turbine

The case for choosing Turbine, with each claim pointing at something you can check.

## What is not a reason

Loading a nested `with` in one statement is common ground. Drizzle's relational queries always emit one SQL statement, Prisma does it with its `relationJoins` preview, and Kysely ships `jsonArrayFrom` / `jsonObjectFrom`. Turbine does it with correlated `json_agg` subqueries.

Raw speed is not a reason on its own either. On an indexed schema the differences are fractions of a millisecond, and over a network the round trip dominates.

## One dependency, no query engine

`dependencies` lists one package: `pg`. There is no engine binary, no WASM module and no adapter package to keep in step. Turbine builds a parameterized SQL string and caches it per query shape, so there is no query compiler running in your process and no plan cache to size.

The main entry stays under a CI-enforced size limit with `pg` external, so the [edge build](/serverless) is an import swap, not a separate package.

## Measured against hand-written SQL

The [benchmarks](/benchmarks) run Turbine, Drizzle, Prisma and a hand-written `pg` control on the same data and pool. On a local socket, Turbine runs at 1.08x the control by geometric mean, Drizzle at 1.47x and Prisma at 1.81x.

Turbine loses deep pagination unless you set `forceCustomPlan`, and its per-row stream trails the Drizzle 1.0 release candidate. Both losses sit on the page next to the wins.

## Built for agents

`npx turbine mcp` starts an MCP server with eleven tools. Prisma ships an MCP server too; the difference is what Turbine's server rules out:

- **No write surface.** No tool accepts SQL text, and every database read runs inside `BEGIN READ ONLY` with a statement timeout.
- **Answers to the schema questions agents get wrong.** `relation_graph` lists the relation names a `with` accepts, `find_join_path` returns the `with` clause that connects two tables, and `table_stats` reports a table's size before a query scans it.
- **No PII reaches the model.** `sample_rows` never fetches PII-tagged columns, and `explain_query` refuses predicates on them.

Typed query arguments turn a wrong query into a compile error, and every error carries a stable code (`TURBINE_E001` to `TURBINE_E020`) with a docs link. Setup: [Turbine for AI agents](/ai-agents).

## Tooling in the box, offline

**`turbine doctor`.** A relation load probes the child table once per parent row, so an unindexed foreign key costs a scan per parent. `doctor` lists every probed column with no covering index, each with a cost tier, and `--fix` writes the migration. One missing index took a correlated query [from 17.8 s to 62 ms](/migrate-from-prisma#before-anything-else-run-doctor). As of July 2026, no other TypeScript ORM CLI gives missing-index advice.

**PII kept out of the SQL.** Tag a column [`pii: true`](/schema#pii-fields) and every default projection leaves it out of the statement itself, writes included (`RETURNING "id", "name"`, not `RETURNING *`). Reading it takes [`includePii: UNSAFE`](/global-filters#privilege-options-and-the-unsafe-symbol), a symbol a request body cannot carry. By default, errors name the keys of a lookup, never its values.

**A read-only Studio.** `npx turbine studio` binds loopback, authenticates with a per-process token, reads inside `BEGIN READ ONLY` and has no raw-SQL surface. Without `--write`, the write endpoints do not exist. As of July 2026, no other TypeScript ORM ships a studio that is read-only by default or redacts PII.

**Destructive migrations need consent.** `migrate up`, `migrate down` and `push` list the data-destroying statements they find and refuse. Type `destroy my data` and then `yes`, or pass `--allow-destructive` in CI.

## Free and extensible

MIT, with no cloud tier, telemetry or account. Studio, doctor, the MCP server and observability ship in the npm package. Prisma's query analysis, Query Insights, is part of its hosted Prisma Postgres.

All SQL generation goes through the documented [`Dialect` contract](/dialects). The SQLite, MySQL and SQL Server engines implement it, so a new engine starts there.

## When Turbine is the wrong choice

- **You need first-class SQLite, MySQL or SQL Server tooling.** Those [engines](/engines) run the same query API, but `turbine generate` and `turbine migrate` are PostgreSQL-only, and pgvector, LISTEN/NOTIFY and RLS `sessionContext` throw [`UnsupportedFeatureError`](/errors#e017) elsewhere.
- **You stream large results off PostgreSQL.** Only PostgreSQL streams through a cursor. The other engines load the full result, then yield it in batches.
- **Your hot path is a full-table drain on an ascending key.** `findManyStream` runs 5% to 11% behind Drizzle 1.0.0-rc.4. `findManyStreamBatches` ties it and beats Drizzle 0.45.2.
- **You want a large community.** Turbine is younger, with fewer answers online.
- **You want a schema DSL.** The schema is code-first (`defineSchema`) or introspected; there is no `.prisma` file.

## Check it yourself

```bash
npx turbine doctor          # index advice on your own schema
npx turbine studio          # read-only by default
npx turbine studio --demo   # no database needed
npx turbine mcp             # the agent server
```
