# Views & Generated Columns

Turbine generates typed read accessors for database views, and it treats `STORED` generated columns as computed by Postgres and never writable. Both rules are enforced twice: in the generated types, and again in the query builder for untyped callers.

## Views

Pass `--include-views` to `generate` / `pull` and Turbine introspects views and materialized views alongside base tables:

```bash
npx turbine pull --include-views
```

Each view becomes a table in the generated metadata with `isView: true`. Codegen emits an entity type and the read accessors (`findMany`, `findFirst`, `count`, `aggregate` and the rest), as for a base table:

```ts
// active_users is a Postgres VIEW
const active = await db.activeUsers.findMany({
  where: { orgId: 1 },
  orderBy: { name: 'asc' },
});
```

### Views are read-only

Every write method refuses a view. `create`, `createMany`, `update`, `updateMany`, `delete`, `deleteMany` and `upsert` throw `ValidationError` (TURBINE_E003) naming the view, before any SQL runs:

```ts
await db.activeUsers.create({ data: { name: 'x' } });
// ❌ ValidationError (TURBINE_E003): cannot write to a view
```

The query builder enforces this, so it holds on every SQL engine, not only Postgres.

### Views without a primary key

A row in a view without a primary key cannot be addressed uniquely, so the view's generated accessor omits the `findUnique` family. Its type is `Omit<QueryInterface<T>, 'findUnique' | 'findUniqueOrThrow'>`, which makes `findUnique` on a PK-less view a compile error. A view that exposes a primary key keeps the full read surface.

## STORED generated columns

Postgres computes a `GENERATED ALWAYS AS (...) STORED` column from other columns. You can read it but never write it. Introspection detects these columns from `is_generated` and the generation expression, and marks them in the column metadata.

Consider:

```sql
CREATE TABLE invoices (
  id    bigserial PRIMARY KEY,
  qty   integer NOT NULL,
  price integer NOT NULL,
  total integer GENERATED ALWAYS AS (qty * price) STORED
);
```

### On read, present and typed

`total` appears in the generated `Invoice` entity type and comes back on every read, like any other column.

```ts
const invoice = await db.invoices.findUnique({ where: { id: 1 } });
invoice.total; // number, computed by Postgres
```

### On write, omitted and rejected

`total` is left out of the `InvoiceCreate` and `InvoiceUpdate` input types, so passing it is a compile error. If it reaches the builder at runtime anyway, say from untyped data, `create`, `update` and `upsert` throw `ValidationError` (TURBINE_E003) naming the column, before anything is sent to Postgres:

```ts
await db.invoices.create({ data: { qty: 2, price: 3 } });
// ✅ total is computed by Postgres as 6

await db.invoices.create({ data: { qty: 2, price: 3, total: 6 } });
// ❌ ValidationError (TURBINE_E003): cannot write generated column "total"
```
