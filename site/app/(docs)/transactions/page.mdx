# Transactions & Pipelines

Turbine has two ways to run several statements together:

- **`$transaction`** makes them atomic: one `BEGIN` and `COMMIT`, rolled back if your callback throws.
- **`pipeline`** cuts latency: independent queries in one round trip, in one transaction by default.

## $transaction, callback form

Return to commit, throw to roll back:

```ts
const user = await db.$transaction(async (tx) => {
  const created = await tx.users.create({ data: { email: 'alice@example.com' } });
  await tx.posts.create({ data: { userId: created.id, title: 'Hello' } });
  return created;
});
```

Run every query through `tx`. A query through `db` runs on another connection, outside the transaction.

### Every query finishes inside the callback

Await everything before the callback returns. If a query on `tx` is still running when it returns, Turbine rolls back and rejects with `ValidationError` ([E003](/errors#e003)). A query on `tx` after the transaction settles throws the same error.

```ts
await db.$transaction(async (tx) => {
  // ❌ forEach does not wait, so the transaction rolls back
  ids.forEach(async (id) => {
    await tx.posts.update({ where: { id }, data: { published: true } });
  });

  // ✅
  for (const id of ids) {
    await tx.posts.update({ where: { id }, data: { published: true } });
  }
});
```

## Transaction options

Pass options as the second argument:

```ts
await db.$transaction(async (tx) => tx.invoices.findMany(), {
  isolationLevel: 'Serializable',
  timeout: 5_000,
});
```

| Option | Type | Default | What it does |
|---|---|---|---|
| `isolationLevel` | `'ReadUncommitted' \| 'ReadCommitted' \| 'RepeatableRead' \| 'Serializable'` | the database default | Isolation level, set on `BEGIN` |
| `timeout` | `number` (ms) | none | Rolls back and rejects once exceeded. See [Timeouts](#timeouts) |
| `readOnly` | `boolean` | `false` | `BEGIN READ ONLY`; a write throws `ReadOnlyError` ([E018](/errors#e018)). PostgreSQL and MySQL only |
| `sessionContext` | `Record<string, string \| number \| boolean>` | none | Transaction-local settings for Row-Level Security, applied right after `BEGIN` |
| `allowBuiltinSettings` | `string[]` | none | PostgreSQL's own settings that `sessionContext` may set |

Pair `readOnly` with `isolationLevel: 'RepeatableRead'` when several reads must see one snapshot.

### Row-Level Security with `sessionContext`

```ts
// Policy: USING (tenant_id = current_setting('app.current_tenant')::int)
const docs = await db.$transaction(async (tx) => tx.documents.findMany(), {
  sessionContext: { 'app.current_tenant': tenantId },
});

// The same thing, shorter
const docs2 = await db.$withSession({ 'app.current_tenant': tenantId }, (tx) =>
  tx.documents.findMany(),
);
```

- Each entry runs as `set_config(name, value, true)`, so it resets at commit or rollback.
- Values must be strings, numbers or booleans. `undefined` throws [E003](/errors#e003) before a connection is taken.
- Names need a dot. A built-in setting such as `role` throws [E003](/errors#e003) unless you list it:

```ts
await db.$transaction(async (tx) => tx.documents.findMany(), {
  sessionContext: { 'app.current_tenant': tenantId, statement_timeout: '5s' },
  allowBuiltinSettings: ['statement_timeout'],
});
```

List only names your code sets, never one from a request. `sessionContext` is PostgreSQL only; the [RLS recipe](/recipes) covers the policy side.

## Nested transactions (savepoints)

Calling `$transaction` on `tx` opens a `SAVEPOINT`. If the inner block throws, only it rolls back:

```ts
await db.$transaction(async (tx) => {
  const user = await tx.users.create({ data: { email: 'a@b.c' } });

  try {
    await tx.$transaction(async (inner) => {
      await inner.auditLog.create({ data: { userId: user.id, action: 'signup' } });
      throw new Error('skip audit log');
    });
  } catch {
    // only the savepoint rolled back
  }

  await tx.posts.create({ data: { userId: user.id, title: 'Hello' } }); // still commits
});
```

- Use the inner handle (`inner`) for the block's work. A query through the outer `tx` while the block is open throws [E003](/errors#e003).
- `tx.$transaction` takes no options. Isolation, timeout and session context belong to the outer transaction.
- Blocks that share a parent run one at a time, even under `Promise.all`.
- A nested create, nested update or lookup-first `upsert` on `tx` gets its own savepoint, so a failure part way leaves the transaction as it was.
- If a block fails and the server does not acknowledge its `ROLLBACK TO SAVEPOINT` (the connection dropped, or the answer came too late), the block throws its own error and the outer transaction can no longer commit, since it may still hold the block's writes. An outer callback that catches the error and returns gets ROLLBACK instead of COMMIT, and rejects with [E019](/errors#e019) once the server acknowledges it, or with the block's error when it does not.

## A caught error still rolls the transaction back

PostgreSQL aborts a transaction at its first failed statement, and catching the error does not undo that. Nothing is saved. `$transaction` rejects with `TransactionRolledBackError` ([E019](/errors#e019)), with the first failure as `cause`, and later statements are refused without being sent. A deadlock, serialization failure or unavailable lock keeps its own retryable class.

To survive an expected failure, run that statement in a nested block:

```ts
import { UniqueConstraintError } from 'turbine-orm';

await db.$transaction(async (tx) => {
  const user = await tx.users.create({ data: { email } });
  try {
    await tx.$transaction((inner) =>
      inner.subscriptions.create({ data: { userId: user.id, plan: 'trial' } }),
    );
  } catch (err) {
    if (!(err instanceof UniqueConstraintError)) throw err;
  }
  // the user row still commits
});
```

## Timeouts

When `timeout` fires, Turbine tries to stop the transaction on the server: on PostgreSQL it sends a cancel request for a statement that is still running and waits for that statement to answer, then it sends ROLLBACK, giving each step at most 2 seconds. The call then rejects with `TimeoutError` ([E002](/errors#e002)). `outcome` says what the server confirmed:

- `'not-executed'`: the server acknowledged the ROLLBACK, so nothing was saved and the locks are free.
- `'unknown'`: the cancel request could not be sent, or the statement or the ROLLBACK did not answer within 2 seconds, so the connection was discarded. The call rejects without waiting longer, and the server may still be running the statement. COMMIT was never sent, so none of the writes were saved and a retry cannot apply them twice. The server may still hold the transaction's locks until it notices the closed connection, so a retry can wait on them.

The error does not say whether the running statement itself was cancelled: the server ignores a cancel request that arrives after the statement finished.

```ts
import { TimeoutError } from 'turbine-orm';

try {
  await db.$transaction(async (tx) => tx.reports.create({ data: report }), { timeout: 5_000 });
} catch (err) {
  if (!(err instanceof TimeoutError)) throw err;
  err.outcome; // 'not-executed' or 'unknown': either way COMMIT was never sent
}
```

`timeout` takes milliseconds below 2^31, or `0` for none. Anything else throws [E003](/errors#e003). It bounds the callback only: once COMMIT is sent, it is never interrupted.

On PostgreSQL, a [per-query `timeout`](/client#per-query-timeout) inside a transaction sends a cancel for that statement and stops the transaction from committing, so returning afterwards rejects with [E019](/errors#e019) once the rollback is acknowledged (or with the statement's own `TimeoutError` when it is not). Run the statement in a nested block to keep going.

A write that takes several statements (a nested write, a lookup-first upsert, a `createMany` split across statements, and on MySQL a write and its re-read) already runs in a savepoint of its own (on every engine except PowDB, which has none), and its timeout rolls back to that savepoint. When the server acknowledges that rollback, the `TimeoutError` says `outcome: 'not-executed'`, and the transaction can continue and commit. When it does not, the error says `'unknown'` and the transaction cannot commit.

## When the outcome is unknown

Turbine reports a transaction as rolled back only when rollback was confirmed. On PostgreSQL, an ERROR answer to COMMIT or its `ROLLBACK` command tag also confirms rollback. FATAL, PANIC and unreadable answers do not. When it cannot confirm that, it says so instead:

| What happened | What you get |
|---|---|
| COMMIT got no answer Turbine could read | `TransactionOutcomeUnknownError` ([E021](/errors#e021)), with the hiding failure as `cause` |
| Your callback failed and the ROLLBACK was not acknowledged | Your callback's own error |
| `timeout` fired and the rollback was not confirmed | `TimeoutError` with `outcome: 'unknown'` |
| A nested block failed and its `ROLLBACK TO SAVEPOINT` was not acknowledged | The block's own error, and the outer transaction cannot commit |
| A write's `timeout` fired and the rollback to its savepoint was not acknowledged | `TimeoutError` with `outcome: 'unknown'`, and the outer transaction cannot commit |

On PostgreSQL, MySQL and Neon WebSocket, the first three cases discard the connection rather than reuse it. Other engines have the limits described below. A `tx` used afterwards does not say the transaction was rolled back. With `logging: true`, `$transaction` (both forms) logs `transaction-outcome-unknown` to your [logger](/observability) rather than `transaction-rolled-back`. `transaction()` and the transactions Turbine opens on its own (below) log neither.

Only the first case can have committed. The answer to a COMMIT is lost when the connection drops while it runs, or when node-postgres's `query_timeout` is shorter than the COMMIT, which can be slow when deferred constraint triggers or synchronous replication run at commit time. Turbine sends no ROLLBACK after it: one sent then cannot tell a commit from a rollback, since it only reports that no transaction is open.

Reading the database does not settle it either. The COMMIT may still be running, and can commit after a read finds nothing, so a retry chosen that way can save the write twice. Make the write safe to repeat instead: store a unique idempotency key in the same transaction, enforced by a `UNIQUE` constraint, and replay the transaction. A replay that starts while the first COMMIT is still running waits for it on the key, then either saves the write or fails with [E008](/errors#e008) on the key's constraint. That error says a row with this key is committed, not that it is this write: read it back and compare before you treat the first attempt as done. E008 on any other unique constraint says nothing about the first attempt, so let it propagate:

```ts
import { TransactionOutcomeUnknownError, UniqueConstraintError } from 'turbine-orm';

// payments.idempotency_key has a UNIQUE constraint named payments_idempotency_key_key.
const pay = () => db.$transaction(async (tx) => tx.payments.create({ data: { idempotencyKey, amount } }));

try {
  await pay();
} catch (err) {
  if (!(err instanceof TransactionOutcomeUnknownError)) throw err;
  try {
    await pay(); // saves the payment, unless a payment with this key is already committed
  } catch (replay) {
    // Only a conflict on the idempotency key itself can mean the first attempt committed.
    if (!(replay instanceof UniqueConstraintError) || replay.constraint !== 'payments_idempotency_key_key') {
      throw replay;
    }
    const stored = await db.payments.findUniqueOrThrow({ where: { idempotencyKey } });
    if (stored.amount !== amount) throw new Error(`idempotency key ${idempotencyKey} holds a different payment`);
    // the first attempt committed
  }
}
```

A replay can itself end in E021; handle it the same way. Without such a key, a read settles nothing until the original transaction has finished, and Turbine cannot tell you when that is.

### Transactions Turbine opens on its own

The same rules cover the transactions Turbine opens for a single call: a `create` or `update` with nested relation writes, a lookup-first `upsert`, a write that takes several statements (a MySQL write and its re-read, a `createMany` split into chunks), and a `pipeline()` that runs its queries one after another. An unanswered COMMIT there is E021 too, with the connection discarded. A per-query `timeout` that ends one of them rejects with `TimeoutError`: `outcome: 'not-executed'` once the server acknowledged the ROLLBACK, `'unknown'` when it did not, and COMMIT was never sent either way. A `pipeline()` over node-postgres's pipeline protocol keeps its own rule: its `timeout` destroys the connection and rejects with `TimeoutError`, `outcome: 'unknown'`. When its connection closes instead, it rejects with the error a statement failed with, with `ConnectionError` (E004) when no COMMIT was sent, or with E021 once a COMMIT was sent and not answered. A batch of plain SELECTs sends its COMMIT with the batch, so a closed connection there is E021 from the start: a SELECT can write through a function it calls.

### Which engines raise E021

E021 is raised where Turbine can tell the server's answer to COMMIT from no answer. On the PostgreSQL dialect, over node-postgres or a compatible pool, `capabilities.classifiesCommitAnswer` is `true`, and a server ERROR at COMMIT is read from its SQLSTATE as well as its severity, so a server reporting in another language still gets the typed error. The MySQL engine and the Neon WebSocket driver settle their own transactions and raise it too: a COMMIT that got no answer (a lost or timed-out connection, and on MySQL also a server shutting down or a statement or connection killed while the COMMIT runs) is E021 with the driver's error as `cause`, the connection discarded and no rollback claimed. An error the server answered the COMMIT with keeps its typed class. SQLite and libsql run in process, where a failed COMMIT is the engine's own answer.

On SQL Server and PowDB, Turbine does not detect an unanswered COMMIT: the driver's error is rethrown. On SQL Server the `mssql` driver also returns the connection to its own pool inside its commit callback, before Turbine sees the result, so Turbine cannot discard it. That pool does not lend a connection again once it is closed or has had a socket error, but a connection whose COMMIT failed while it stayed open goes back into the pool.

## Retryable errors

| Code | Class | Raised for |
|---|---|---|
| [E012](/errors#e012) | `DeadlockError` | PostgreSQL 40P01 |
| [E013](/errors#e013) | `SerializationFailureError` | PostgreSQL 40001 |
| [E013](/errors#e013) | `LockNotAvailableError` | A [row lock](/queries#row-locks) that could not be taken |

Each has `isRetryable: true`. Retry the whole transaction with `withRetry` (or `db.$retry`):

```ts
import { withRetry } from 'turbine-orm';

await withRetry(
  () => db.$transaction(async (tx) => { /* ... */ }, { isolationLevel: 'Serializable' }),
  { maxAttempts: 5 },
);
```

| Option | Default | What it does |
|---|---|---|
| `maxAttempts` | `3` | Total attempts |
| `baseDelay` | `50` | ms; doubles each attempt, with jitter |
| `maxDelay` | `5000` | ms cap |
| `onRetry` | none | `(error, attempt) => void` |

Any other error is rethrown at once.

## Lost connections

A restart, failover or suspended serverless compute closes connections from the server side. The pending call rejects with `ConnectionError` ([E004](/errors#e004)), and the process keeps running. Turbine resends only what cannot double-apply:

| Statement | On a connection the server closed |
|---|---|
| A read outside a transaction | Sent once more on a fresh connection |
| The `BEGIN` of a transaction | Sent once more on a fresh connection |
| A write outside a transaction | Fails with E004, never resent |
| Anything inside a transaction | Fails with E004 |

A lost write may have committed before the reply was lost, so retry it yourself only if it is idempotent. Pools Turbine opens also evict connections that died while a serverless function was frozen, before lending them out.

## $transaction, batch form

Pass `build*` queries instead of a callback. They run in order in one transaction and return a typed tuple:

```ts
const [user, postCount] = await db.$transaction([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildCount({ where: { userId: 1 } }),
]);
```

Items must be `build*` queries. A promise such as `db.users.create(...)` already started outside the transaction, so it throws [E003](/errors#e003) before anything runs. The batch form takes the same options as the callback form.

## Pipeline, N queries, 1 round trip

```ts
const [user, posts, commentCount] = await db.pipeline([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildFindMany({ where: { userId: 1 }, limit: 10 }),
  db.comments.buildCount({ where: { userId: 1 } }),
]);
```

A pipeline sends every query before reading any reply, so use it for independent queries. By default the batch runs in one transaction, and if any query fails, nothing in it is committed. With `{ transactional: false }` each query stands alone, and a partial failure throws `PipelineError` ([E014](/errors#e014)):

```ts
import { PipelineError } from 'turbine-orm';

try {
  await db.pipeline(queries, { transactional: false });
} catch (err) {
  if (err instanceof PipelineError) {
    err.results; // [{ status: 'ok', value }, { status: 'error', error }, ...]
  }
}
```

Without the pipeline protocol (some serverless drivers, and the non-PostgreSQL engines), the queries run one after another on one connection. `await db.pipelineSupported()` tells you which path you get. With a raw `pg.Pool`, `executePipeline(pool, queries, options)` and `pipelineSupported(pool)` do the same.

There is no `tx.pipeline()`. For an atomic batch, use the batch form of `db.$transaction`.

## What `tx` has

| Member | What it is |
|---|---|
| `tx.users`, `tx.posts`, ... | The same table accessors as `db` |
| `tx.table<T>(name)` | Accessor for a table missing from the generated types |
| `tx.$transaction(fn)` | A nested block on a savepoint |
| ``tx.raw`...` `` | Tagged-template SQL; every `${value}` is bound |
| ``tx.sql<T>`...` `` | [Typed SQL](/raw-sql#typed-raw-sql-dbsqlt) on the transaction's connection |
| `tx.rawUnsafe(text, ...values)` | SQL text built at runtime, with `$1`, `$2` placeholders; never put untrusted input in `text` |
| `tx.$connection()` | The driver connection, for another library's query function |
| `tx.schema` | The schema metadata |

```ts
await db.$transaction(async (tx) => {
  const rows = await tx.raw<{ n: number }>`
    SELECT count(*)::int AS n FROM posts WHERE user_id = ${userId}`;
  await tx.users.update({ where: { id: userId }, data: { postCount: rows[0].n } });
});
```

Raw SQL inside a transaction runs no `$use` middleware. It also refuses `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` and other transaction-control statements with [E003](/errors#e003): return to commit, throw to roll back.

`tx` has no `pipeline`, `$use`, `$listen`, `$on`, `$retry`, `$withSession` or pool methods. Use those on `db`, and wrap the whole `db.$transaction(...)` call to retry it.

## The raw transaction API

`db.transaction(fn)` (no `$`) hands your callback the raw driver client instead of `tx`, with the same commit and rollback handling. Use it only for hand-written SQL:

```ts
await db.transaction(async (client) => {
  await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [100, from]);
  await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [100, to]);
});
```

`SAVEPOINT`, `RELEASE` and `ROLLBACK TO` work on it. `BEGIN`, `COMMIT`, `ROLLBACK` and `release()` throw [E003](/errors#e003).
