# Transactions & Pipelines

Two distinct tools that are often confused:

- **`$transaction`**, ACID atomicity across multiple statements. One `BEGIN` / `COMMIT` pair, rollback on throw.
- **`pipeline`**, throughput. N independent queries sent in one TCP round-trip via the Postgres extended-query protocol. Not atomic.

Use transactions when you need all-or-nothing semantics. Use pipelines when you need latency.

## $transaction, callback form

Pass a callback that receives a transactional client. Throw to roll back, return to commit.

```ts
const result = await db.$transaction(async (tx) => {
  const user = await tx.users.create({
    data: { email: 'alice@example.com', name: 'Alice' },
  });

  await tx.posts.create({
    data: { userId: user.id, title: 'Hello' },
  });

  return user;
});
// result is the User returned by the callback
```

The `tx` client has the same table accessors as `db` (the [reference](#transactionclient-reference) below lists what else it has). Queries *must* use `tx`, not `db`, or they'll run on a different connection outside the transaction.

### Every query finishes inside the callback

Once the callback settles, `tx` is closed. Its connection goes back to the pool and may already be running another request's transaction, so a query issued through `tx` afterwards throws `ValidationError` ([`TURBINE_E003`](/errors#e003)) instead of being sent. The usual causes are a missing `await`, an `async` callback passed to `forEach`, or a `tx` kept in a variable or a timer:

```ts
await db.$transaction(async (tx) => {
  // ❌ forEach does not wait: these run after the callback returns, and throw.
  ids.forEach(async (id) => {
    await tx.posts.update({ where: { id }, data: { published: true } });
  });

  // ✅ Awaited, so every update runs inside the transaction.
  for (const id of ids) {
    await tx.posts.update({ where: { id }, data: { published: true } });
  }
});
```

### A caught error still rolls the transaction back

PostgreSQL aborts a transaction at its first failed statement. Catching that error inside the callback does not undo the abort: the `COMMIT` that follows is answered with a `ROLLBACK`, and nothing the transaction wrote is saved. `$transaction` rejects in that case rather than reporting a commit. The error is a `ValidationError` (`TURBINE_E003`) carrying the statement that failed first as `cause`, except when that failure was a deadlock or a serialization conflict, which keep their class (`DeadlockError`, `SerializationFailureError`) so a retry of the whole block still works.

To recover from an expected failure and keep the rest of the work, run the statement that can fail in a [nested `$transaction`](#nested-transactions-real-savepoints), which rolls back only its own savepoint:

```ts
import { UniqueConstraintError } from 'turbine-orm';

await db.$transaction(async (tx) => {
  const user = await tx.users.create({ data: { email } });

  try {
    await tx.$transaction((inner) =>
      inner.subscriptions.create({ data: { userId: user.id, plan: 'trial' } }),
    );
  } catch (err) {
    if (!(err instanceof UniqueConstraintError)) throw err;
    // Only the savepoint rolled back; the user row still commits.
  }
});
```

### Multi-statement writes stay whole

A single call that issues several statements (a nested create or update, a lookup-first `upsert`) runs inside its own savepoint when you call it on `tx`. If it fails part way through, the statements it already ran are rolled back and your transaction carries on as if the call had never started, rather than committing half of it later.

> **Note:** If the opening `BEGIN` itself fails, Turbine does not fire a best-effort `ROLLBACK` afterward: on single-handle engines like embedded PowDB, a stray rollback could tear down an unrelated open transaction. A `BEGIN` that failed because its connection was already closed is sent once more on a fresh connection first, see [Lost connections](#lost-connections).

## $transaction, batch form

Pass an array of `DeferredQuery` objects (the `build*` methods, same as [`pipeline`](#pipeline-n-queries-1-round-trip)) and `$transaction` runs them atomically on one connection, `BEGIN`, each query in order, `COMMIT`, returning a positionally-typed tuple of each query's result. Any error rolls the whole batch back and rethrows.

```ts
const [user, postCount] = await db.$transaction([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildCount({ where: { userId: 1 } }),
]);
// user: User | null, postCount: number, all-or-nothing
```

Use the batch form when a fixed set of independent statements must succeed or fail together and you don't need a callback's control flow. It takes the same options object as the callback form (`isolationLevel`, `timeout`, `sessionContext`) as its second argument. An empty array resolves to `[]` without opening a transaction, after validating those options. `$transaction` accepts either form.

Each item must be a deferred query. Passing a promise (`db.users.create(...)` instead of `db.users.buildCreate(...)`, the shape Prisma's array form takes) throws `ValidationError` (`TURBINE_E003`) before anything in the batch runs, because that query already started on its own connection, outside the transaction, the moment it was created.

> **Batch form vs pipeline:** both take `DeferredQuery[]`. The [pipeline](#pipeline-n-queries-1-round-trip) optimizes for latency (one round-trip, **not** atomic); the batch `$transaction` optimizes for atomicity.

## Isolation levels

Pass `isolationLevel` to set the transaction's isolation on `BEGIN`:

```ts
await db.$transaction(
  async (tx) => {
    const row = await tx.inventory.findUnique({ where: { sku: 'ABC' } });
    await tx.inventory.update({
      where: { sku: 'ABC' },
      data: { stock: { decrement: 1 } },
    });
  },
  { isolationLevel: 'Serializable' },
);
```

Supported: `'ReadUncommitted'`, `'ReadCommitted'` (Postgres default), `'RepeatableRead'`, `'Serializable'`.

When `Serializable` detects a conflict, it throws `SerializationFailureError` (TURBINE_E013) with `isRetryable: true as const`. See the retry section below.

## Timeouts

Per-transaction timeout in milliseconds, enforced client-side. If the callback exceeds `timeout`, Turbine destroys the connection (aborting any in-flight statement server-side), rolls back, and throws `TimeoutError` (TURBINE_E002):

```ts
await db.$transaction(
  async (tx) => {
    await tx.reports.create({ data: { /* ... */ } });
  },
  { timeout: 5_000 },
);
```

## Nested transactions, real SAVEPOINTs

Calling `$transaction` inside another `$transaction` opens a Postgres `SAVEPOINT`, not a no-op and not a new connection. The inner block can fail and recover independently:

```ts
await db.$transaction(async (tx) => {
  const user = await tx.users.create({ data: { email: 'a@b.c' } });

  try {
    await tx.$transaction(async (inner) => {
      await inner.auditLog.create({ data: { userId: user.id, action: 'signup' } });
      throw new Error('skip audit log');
    });
  } catch {
    // Inner block rolled back to SAVEPOINT; outer is still healthy
  }

  await tx.posts.create({ data: { userId: user.id, title: 'Hello' } });
  // user + post still commit
});
```

SAVEPOINT names are auto-generated with a counter, so nesting is safe.

Savepoints are a stack on the one connection, so nested blocks that share a parent run one at a time, even when you start them together with `Promise.all`. Without that, rolling back the first block would also discard a second block that opened inside it and had already reported success. A block started from inside another block's callback nests under it and does not wait.

A nested block whose callback swallowed a statement failure rejects with the same rolled-back error described [above](#a-caught-error-still-rolls-the-transaction-back), carrying the failure as `cause`, and the outer transaction stays usable.

## Multi-tenant queries with RLS session context

Set transaction-local Postgres settings (GUCs) so PostgreSQL Row-Level Security policies that call `current_setting()` filter rows for you: the database enforces the tenant boundary, not your application code.

Pass `sessionContext` to `$transaction`:

```ts
// Postgres policy: USING (tenant_id = current_setting('app.current_tenant')::int)
const rows = await db.$transaction(
  async (tx) => tx.documents.findMany(),
  { sessionContext: { 'app.current_tenant': tenantId } },
);
// Only this tenant's documents come back, the policy did the filtering
```

Each entry is applied as `SELECT set_config(name, value, true)` right after `BEGIN`, so the setting is scoped to the transaction and resets automatically on commit or rollback. Values may be strings, numbers, or booleans; numbers and booleans are converted to text, since a setting is text. Any other value, including `undefined` and `null`, throws `ValidationError` (`TURBINE_E003`): a missing tenant id used to reach the policy as the string `"undefined"`. An invalid setting name throws the same error. Both are checked before a connection is taken, so nothing runs.

### $withSession shorthand

For a single-purpose session, `$withSession` skips the options object, pass the context first, then the callback:

```ts
const rows = await db.$withSession(
  { 'app.current_tenant': tenantId },
  async (tx) => tx.documents.findMany(),
);
```

`$withSession(ctx, fn)` is exactly `$transaction(fn, { sessionContext: ctx })`. Use it when the only reason you're opening a transaction is to scope the RLS context.

## Retryable errors

Two error classes carry `readonly isRetryable = true as const`, so TypeScript narrows them and you don't need a runtime field check.

| Code | Class | SQLSTATE |
|---|---|---|
| E012 | `DeadlockError` | 40P01 |
| E013 | `SerializationFailureError` | 40001 |

Canonical retry loop, using the `withRetry` helper the package exports (or the identical `db.$retry`):

```ts
import { withRetry } from 'turbine-orm';

await withRetry(() =>
  db.$transaction(
    async (tx) => {
      /* ... */
    },
    { isolationLevel: 'Serializable' },
  ),
);
```

`withRetry` retries only errors carrying `isRetryable === true` and rethrows everything else at once. Tune it with `maxAttempts` (default `3`), `baseDelay` (default `50` ms), `maxDelay` (default `5000` ms), and `onRetry(error, attempt)`; backoff is exponential with jitter.

The `as const` on `isRetryable` means `err.isRetryable` is the literal type `true` on those classes and never narrows to `false`, so your control flow type-checks without casts.

## Lost connections

A database restart, a failover, a pooler recycle, a serverless compute suspend or `pg_terminate_backend` closes connections from the server side. Since 0.80 this never exits your process, whatever held the connection at the time. The pending call rejects with `ConnectionError` (E004) and the pool discards the connection.

Turbine recovers on its own where resending cannot change the outcome.

| Statement | On a connection the server already closed |
|---|---|
| A read outside a transaction (`findMany`, `findFirst`, `findUnique`, `count`, `aggregate`, `groupBy`, a stream's first query) | Sent once more on a fresh connection |
| The `BEGIN` of `$transaction`, `transaction()` or a nested write, and `connect()`'s check | Sent once more on a fresh connection |
| A write (`create`, `update`, `delete`, `upsert`, `*Many`) | Fails with E004, never resent |
| Anything inside a transaction | Fails with E004: the connection was the transaction |

Writes are not resent because a lost connection does not say whether the statement committed first. A connection can drop after the server commits and before the reply arrives, so a second `INSERT` could insert the row twice. If your write is idempotent, retry it yourself on `ConnectionError`.

The retried attempt shows up in `$on('query')` as its own event, carrying the error and `retried: true`. A listener that alerts on failed calls can skip those.

### After a freeze

The dead connections that matter most come from a process that was not running. pg-pool drops an idle connection when it reads the server's close, which needs the event loop. A serverless function frozen between invocations reads nothing, so a restart during the freeze leaves every idle connection dead and still in the pool.

So a pool Turbine creates waits one event-loop turn before lending out a connection that has been idle for a second or more. That turn reads the closes, the dead connections are evicted, and the caller gets a live one. It costs no round trip, and a pool in steady use never waits. Measured with five idle connections terminated while the loop was blocked: five concurrent queries all failed before, none after, reads and writes alike.

A pool you pass in yourself (`TurbineConfig.pool`, `turbineHttp`) does not get the wait, since it is not Turbine's to change. The read and `BEGIN` retries above still apply to it.

## pipeline, N queries, 1 round-trip

A pipeline bundles independent queries and sends them together using the Postgres extended-query pipeline protocol. Each query gets its own parsed SQL, own params, own typed result. **The batch is transactional by default** (`transactional: true`): all of it is wrapped in one `BEGIN`/`COMMIT`, so if query 3 fails the whole batch rolls back and nothing is durable.

Pass `{ transactional: false }` when you want each query independent, a failure in one leaving the others untouched:

```ts
const results = await db.pipeline(queries, { transactional: false });
```

A transactional batch also rolls back when a `transform` rejects its result: a `buildFindUniqueOrThrow` that finds nothing, or an update that loses its `optimisticLock` check. A batch that may write therefore holds its `COMMIT` until every transform has accepted, which costs one extra round trip; a read-only batch still takes one. This matches `$transaction([...])` on the same input.

With `transactional: false`, a partial failure rejects with a `PipelineError` (TURBINE_E014) carrying a per-slot `.results` array, so you can see which queries succeeded. The transactional default never produces a `PipelineError`; it rethrows the underlying typed error after the rollback.

```ts
const [user, posts, commentCount, orgs, latestLogin] = await db.pipeline([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildFindMany({ where: { userId: 1 }, limit: 10 }),
  db.comments.buildCount({ where: { userId: 1 } }),
  db.organizations.buildFindMany({ where: { ownerId: 1 } }),
  db.sessions.buildFindFirst({ where: { userId: 1 }, orderBy: { createdAt: 'desc' } }),
]);
```

Each `build*` method returns a `DeferredQuery<T>`, `{ sql, params, transform, tag }`. The pipeline driver writes them all to the wire, reads all responses, applies each `transform`. The result type is a tuple that matches the input order and carries the per-query return type.

### Driving a pipeline yourself

`db.pipeline()` is the wrapper. The underlying function is exported too, for cases where you hold a `pg.Pool` directly rather than a `TurbineClient`:

```ts
import { executePipeline, pipelineSupported } from 'turbine-orm';

const results = await executePipeline(pool, queries, options);
```

`executePipeline(pool, queries, options?)` takes a `pg.Pool`, a readonly array of `DeferredQuery` objects, and the same `PipelineOptions` as `db.pipeline()`; it returns the same order-matched tuple. An empty array short-circuits to `[]` without touching the pool. `await pipelineSupported(pool)` resolves to a boolean telling you whether that pool's driver exposes the wire-protocol path (some pg-compatible serverless drivers do not), so you can fall back to sequential execution rather than fail.

## When pipeline wins

- **Edge runtimes.** One round-trip to Neon (~35 ms) instead of five (~175 ms).
- **Dashboard loads.** Five independent widget queries → one round-trip.
- **Fan-out reads.** Load the user + their N related collections for a profile page.

## When pipeline loses

- **One query depends on another's result.** Pipeline queries must be independent; they're all submitted before any response is read.
- **You need interactive control.** A pipeline is one shot: no reading a row, branching, then writing. Use the callback form of `$transaction`.
- **You opted out of the transaction and a query might fail.** With `{ transactional: false }`, `PipelineError` (TURBINE_E014) wraps the partial-success case; decide how you want to handle each slot.

## Batching inside a transaction

There is **no `tx.pipeline()`**. The extended-query pipeline protocol needs to own the connection, and inside a transaction the connection is already owned by the `BEGIN` block. If you want a set of statements to run atomically as one unit, use the array form of `$transaction` at the top level:

```ts
const [user, posts] = await db.$transaction([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildFindMany({ where: { userId: 1 } }),
]);
```

That runs every statement on one connection inside one `BEGIN` / `COMMIT`, and rolls the whole batch back on the first failure. It is sequential on the connection by default, which is safe on every driver including HTTP and serverless pools. The one-write-burst path needs **both** conditions to hold: the checked-out connection advertises `supportsPipelining`, **and** the active dialect's `resultStrategy` is not `'reselect'`. When both are true the statements are dispatched in one write burst with replies collected in order, saving a round trip each. MySQL is `'reselect'`, so the batch always runs sequentially there. Either way this is a transaction, not the pipeline protocol: for that, use `db.pipeline(...)` outside a transaction.

## TransactionClient reference

The `tx` handed to your `$transaction` callback is a `TransactionClient`, and it is deliberately a **smaller** object than `db`. Everything it exposes runs on the single dedicated connection the transaction holds.

### What `tx` has

| Member | Signature | Notes |
|---|---|---|
| Table accessors | `tx.users`, `tx.orderItems`, ... | Same `QueryInterface` API as `db.users`. Accessor names are the camelCase form of each table name in the schema, defined at construction. |
| `tx.table<T>(name)` | `(name: string) => QueryInterface<T>` | Escape hatch for a table not present in the generated types. Same instance is reused for repeated calls. |
| `tx.$transaction(fn)` | `(fn: (tx: TransactionClient) => Promise<R>) => Promise<R>` | Nested block via `SAVEPOINT sp_1`, `sp_2`, ... Releases the savepoint on success, rolls back **to the savepoint only** on throw, then rethrows. **Takes no options object**: isolation level, timeout and `sessionContext` are properties of the outer transaction and cannot be changed part way through. `fn` receives the *same* `tx`, not a child object. |
| `tx.raw` | ``tx.raw<T>`SELECT ... ${value}` `` | Tagged template, the one to reach for in application code. Every `${value}` becomes a placeholder bound by the driver, so a value cannot end up concatenated into the SQL text. Returns the rows. Driver errors are translated by `wrapPgError`, so you get the same typed errors as ORM queries. |
| `tx.schema` | `SchemaMetadata` | The metadata the transaction was built from. |

<Callout type="note">
**Transaction-scoped raw SQL is not instrumented.** `tx.raw` (and the internal `tx.rawQuery` below) go straight to the transaction's connection: no `$on('query')` event, no middleware, no timing, so they never appear in query listeners or `$observe` metrics. Table-scoped calls inside the same transaction (`tx.users.findMany(...)`) are instrumented exactly as they are outside one. If you need a raw statement in your query log, log it at the call site.
</Callout>

### The one internal member

`tx.rawQuery(text, params)` is marked `@internal` and is **not** application API. It is the seam `turbine-orm/prisma-compat` detects by shape (`typeof tx.rawQuery === 'function'`) so it can run compat raw SQL on the transaction's own connection instead of falling back to a pool connection outside the transaction. It takes the SQL as a plain string, which moves the escaping discipline to the caller, the property `tx.raw` exists to remove. It still exists at runtime and still typechecks, so existing callers keep working; use `tx.raw`.

### What `tx` does not have

Reaching for any of these is a **compile error** (`TS2339: Property '<x>' does not exist on type 'TransactionClient'`). `TransactionClient` declares exactly the members above, the table accessors are installed at construction and typed by the generated `TypedTransactionClient` subclass (one property per table), and neither class has an index signature, so nothing below type-checks.

| Missing | Use instead | Why |
|---|---|---|
| `tx.sql` | `tx.raw` inside, or `db.sql` outside | `db.sql` builds a `TypedSqlQuery` bound to the **pool**, so it would check out a second connection and run outside your transaction. `tx.raw` is the transaction-scoped equivalent; you lose `.one()` / `.scalar()` and type the rows yourself. |
| `tx.pipeline` | `db.$transaction([...])` at the top level | See above: the pipeline protocol needs to own the connection. |
| `tx.$use` | Register middleware on `db` before opening the transaction | The transaction inherits the client's middleware list at construction. There is no way to add one mid-transaction. |
| `tx.$listen` / `tx.$notify` | `db.$listen` / `db.$notify` | `$listen` holds its own dedicated connection for the subscription's lifetime, which is not the transaction's connection. |
| `tx.$observe`, `tx.$on`, `tx.$off` | Configure them on `db` | Observability is client-scoped. Queries run inside the transaction still emit events and metrics through the parent client. |
| `tx.pipelineSupported()` | `db.pipelineSupported()` | It reports whether a **pool's** driver exposes the wire-protocol path, which is a property of the pool, not of a borrowed connection. |
| `tx.transaction(fn)` | You are already in one | `db.transaction(fn)` (no `$`) opens a fresh `BEGIN` on a pooled connection. Inside a transaction the nesting primitive is `tx.$transaction(fn)`, which uses a SAVEPOINT. |
| `tx.connect()` | Nothing needed | `db.connect()` warms and health-checks the pool. The transaction already holds a live connection. |
| `tx.$retry`, `withRetry` | Wrap the whole `db.$transaction(...)` call | Retrying part of an aborted transaction cannot work: after a serialization failure the transaction is already dead. Retry the whole block. |
| `tx.$primary` | Nothing needed | Transactions always run on the primary. Read-replica routing never applies inside one. |
| `tx.$withSession` | `db.$transaction(fn, { sessionContext })` | Session GUCs are applied right after `BEGIN`, before your callback runs. |
| `tx.pool`, `tx.stats`, `tx.disconnect()`, `tx.end()` | The equivalents on `db` | The transaction does not own a pool and must not close one. |

### Transaction options

Options are passed as the second argument to `db.$transaction(fn, options)` and apply to the whole block.

```ts
await db.$transaction(
  async (tx) => {
    return tx.invoices.findMany();
  },
  {
    isolationLevel: 'Serializable',
    timeout: 5_000,
    sessionContext: { 'app.current_tenant': tenantId },
  },
);
```

- **`isolationLevel`**: one of `'ReadUncommitted'`, `'ReadCommitted'`, `'RepeatableRead'`, `'Serializable'`. Composed into the `BEGIN` statement by the active dialect. Under `Serializable` or `RepeatableRead`, expect `SerializationFailureError` (`TURBINE_E013`) and retry the whole block.
- **`timeout`**: milliseconds. When it fires, the transaction is rolled back and the connection is destroyed rather than returned to the pool, so the in-flight backend query is actually aborted rather than left running. You get a `TimeoutError` (`TURBINE_E002`).
- **`sessionContext`**: a record of transaction-local Postgres GUCs, applied as `SELECT set_config($1, $2, true)` immediately after `BEGIN` and before your callback. Both the name and the value are bound parameters. The name is additionally checked against a strict identifier pattern and the value must be a string, number or boolean, so a malformed entry throws `ValidationError` before a connection is taken. `is_local = true` means the setting resets on `COMMIT` or `ROLLBACK` and never leaks onto the pooled connection. Postgres-only: on an engine whose dialect reports no RLS support it throws `UnsupportedFeatureError` (`TURBINE_E017`). `db.$withSession(context, fn)` is the shorthand.

### The raw transaction API

`db.transaction(fn)` (no `$`) is the older, lower-level form: your callback receives a raw `pg.PoolClient` rather than a `TransactionClient`, with the same `BEGIN` / `COMMIT` / rollback-on-throw handling and no typed table accessors. A `COMMIT` that PostgreSQL answers with `ROLLBACK` rejects here too.

Prefer `$transaction`; reach for this only when you want to issue hand-written SQL on the transaction's own connection.
