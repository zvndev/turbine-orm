# Optimistic Locking

Optimistic locking lets concurrent writers detect a *lost update* without holding a row lock. You read a row along with its version, then write back on the condition that the version is unchanged. If someone else committed in between, your update matches zero rows and Turbine throws `OptimisticLockError`.

Nothing is locked: you bet that conflicts are rare and pay only when one happens. Pessimistic `SELECT ... FOR UPDATE` is the opposite and serializes writers up front.

## The version column

Add an integer column that increments on every update. The convention is `version`, defaulting to `0`.

```ts
// schema.ts
export default defineSchema({
  posts: {
    id: { type: 'serial', primaryKey: true },
    title: { type: 'text', notNull: true },
    version: { type: 'integer', notNull: true, default: 0 },
  },
});
```

Or as a migration against an existing table:

```sql
ALTER TABLE posts ADD COLUMN version integer NOT NULL DEFAULT 0;
```

## The `optimisticLock` option

Pass `optimisticLock: { field, expected }` to `update`. `field` is the version column and `expected` is the version you read.

```ts
const post = await db.posts.findUniqueOrThrow({ where: { id: 1 } });

await db.posts.update({
  where: { id: post.id },
  data: { title: 'Updated title' },
  optimisticLock: { field: 'version', expected: post.version },
});
```

Turbine adds the version check to the `WHERE` clause and increments the column in the same statement:

```sql
UPDATE posts SET title = $1, version = version + 1
WHERE id = $2 AND version = $3
RETURNING *
```

If another writer bumped `version` after you read it, the `version = $3` predicate fails and no row is updated. Turbine then throws `OptimisticLockError` rather than returning as if nothing happened.

### `update` only

`optimisticLock` is an `update` option. Passing it to `updateMany`, `upsert`, `delete` or `deleteMany` throws `ValidationError` ([`TURBINE_E003`](/errors#e003)) rather than letting a stale write through. The message names the equivalent:

```ts
// updateMany: put the expected version in `where` and bump it in `data`.
const { count } = await db.posts.updateMany({
  where: { authorId: 7, version: expected },
  data: { published: true, version: { increment: 1 } },
});
// `count` is the number of rows that were still at that version.

// upsert: read the row first, then update or create, inside one transaction.
await db.$transaction(async (tx) => {
  const row = await tx.posts.findUnique({ where: { id } });
  if (row) {
    await tx.posts.update({ where: { id }, data, optimisticLock: { field: 'version', expected } });
  } else {
    await tx.posts.create({ data: { id, ...data } });
  }
});
```

The `upsert` refusal applies to every call, including one whose `create` or `update` carries nested relation data, and it throws before anything is read or written.

For `delete`, put the expected version in `where` beside the key (`where: { id, version: expected }`). A row at another version is not deleted, and the call throws `NotFoundError`. For `deleteMany`, put the version in `where`; the returned count is the number of rows still at that version.

## Handling a conflict

`OptimisticLockError` is `TURBINE_E015`. It carries the `table`, the `versionField` and the `expectedVersion` you supplied. Under the default `errorMessages: 'safe'`, the message names the version field but not the value you sent, because a version can be a timestamp or any other stored value. The value is always available on `.expectedVersion` and `.detail`.

```ts
import { OptimisticLockError } from 'turbine-orm';

try {
  await db.posts.update({
    where: { id: post.id },
    data: { title: input.title },
    optimisticLock: { field: 'version', expected: post.version },
  });
} catch (err) {
  if (err instanceof OptimisticLockError) {
    // err.table          -> 'posts'
    // err.versionField   -> 'version'
    // err.expectedVersion-> the stale version you sent
    // The row changed under you. Re-read and reapply, or surface a 409 conflict.
  }
  throw err;
}
```

### Not auto-retryable

Unlike `DeadlockError` and `SerializationFailureError`, `OptimisticLockError` has **no** `isRetryable` flag. A version conflict means the data changed, so replaying the same statement would be wrong. Re-read the current row and decide whether your change still makes sense.

A re-read-then-retry helper makes that step explicit:

```ts
import { OptimisticLockError } from 'turbine-orm';

async function patchPost(id: number, patch: { title?: string }, maxAttempts = 3) {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const current = await db.posts.findUniqueOrThrow({ where: { id } });
    try {
      return await db.posts.update({
        where: { id },
        data: patch,
        optimisticLock: { field: 'version', expected: current.version },
      });
    } catch (err) {
      if (err instanceof OptimisticLockError && attempt < maxAttempts) continue;
      throw err;
    }
  }
}
```

For a user-facing edit form, return the conflict (HTTP `409`) so the person can review the latest data, instead of overwriting it.

## Optimistic locking vs atomic operators

These solve different problems:

- **Atomic update operators** (`{ increment: 1 }`, `{ decrement: 1 }`, …) compute the new value from the current column inside the `UPDATE`, so concurrent `+1`s never cancel each other. Use them for counters and balances where the previous value does not matter.
- **Optimistic locking** guards a *read-modify-write*, where the new value depends on what the user saw. Use it for edit forms and any update your application computes from a value it read earlier.

```ts
// Atomic, no lock needed, both increments land:
await db.posts.update({ where: { id: 1 }, data: { viewCount: { increment: 1 } } });

// Read-modify-write, guard with optimisticLock:
const p = await db.posts.findUniqueOrThrow({ where: { id: 1 } });
await db.posts.update({
  where: { id: 1 },
  data: { title: rewrite(p.title) },
  optimisticLock: { field: 'version', expected: p.version },
});
```
