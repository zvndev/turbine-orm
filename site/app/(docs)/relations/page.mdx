# Relations

Turbine infers relations from foreign keys. Declare them in `defineSchema()` or let `npx turbine generate` read them, then load related rows with `with`, in one SQL statement by default.

## One-to-many (hasMany)

A user has many posts because `posts.user_id` references `users.id`.

```ts
// schema.ts
import { defineSchema } from 'turbine-orm';

export default defineSchema({
  users: {
    id: { type: 'serial', primaryKey: true },
    email: { type: 'text', unique: true, notNull: true },
  },
  posts: {
    id: { type: 'serial', primaryKey: true },
    userId: { type: 'bigint', notNull: true, references: 'users.id' },
    title: { type: 'text', notNull: true },
  },
});
```

```ts
const users = await db.users.findMany({
  with: { posts: true },
});
// users[0].posts is Post[], [] when the user has none
```

A to-many relation is always an array, never `null`.

## One-to-one (belongsTo + hasOne)

The table holding the foreign key gets `belongsTo`. `turbine generate` gives the other side `hasOne` when the key column is `UNIQUE`, else `hasMany`.

```ts
users: {
  id: { type: 'serial', primaryKey: true },
  profileId: { type: 'bigint', unique: true, references: 'profiles.id' },
},
profiles: {
  id: { type: 'serial', primaryKey: true },
  bio: { type: 'text' },
},
```

```ts
const user = await db.users.findUnique({
  where: { id: 1 },
  with: { profile: true },
});
// user.profile is Profile | null
```

## Many-to-many

`turbine generate` turns a pure junction table into a many-to-many relation on both ends. A pure junction has only two columns: foreign keys to two different tables that together form its primary key.

```ts
posts: {
  id: { type: 'serial', primaryKey: true },
  title: { type: 'text', notNull: true },
},
tags: {
  id: { type: 'serial', primaryKey: true },
  name: { type: 'text', notNull: true },
},
postsTags: {
  postId: { type: 'bigint', notNull: true, references: 'posts.id' },
  tagId: { type: 'bigint', notNull: true, references: 'tags.id' },
  primaryKey: ['postId', 'tagId'],
},
```

```ts
const posts = await db.posts.findMany({
  with: { tags: { where: { name: 'sql' }, orderBy: { name: 'asc' }, limit: 5 } },
});
// posts[0].tags is Tag[]
```

### Junctions with extra columns

A junction with its own columns (a role, a timestamp) stays a `hasMany`, so those columns come back:

```ts
const user = await db.users.findUnique({
  where: { id: 1 },
  with: { memberships: { with: { organization: true } } },
});
user.memberships[0].role;              // the junction's own column
user.memberships.map((m) => m.organization); // the flat list
```

### Declaring one by hand

Use `manyToMany` for a flat relation over a junction that is not pure:

```ts
import { defineSchema } from 'turbine-orm';

export default defineSchema({
  posts: {
    id: { type: 'serial', primaryKey: true },
    title: { type: 'text', notNull: true },
    manyToMany: [
      { name: 'tags', target: 'tags', through: 'postsTags',
        sourceKey: 'postId', targetKey: 'tagId' },
    ],
  },
  // ...tags and postsTags table definitions
});
```

`sourceKey` and `targetKey` are the junction columns pointing at each side. Add `references` when the source's key is not `id`.

### Linking rows

A many-to-many relation takes `connect`, `disconnect` and `set`. They write junction rows in the parent write's transaction:

```ts
await db.posts.create({
  data: { title: 'Indexing', tags: { connect: [{ id: 7 }, { id: 9 }] } },
});

await db.posts.update({
  where: { id: 1 },
  data: { tags: { connect: { id: 7 }, disconnect: { id: 3 } } },
});

await db.posts.update({
  where: { id: 1 },
  data: { tags: { set: [{ id: 7 }] } }, // now the post's only tag
});
```

The other nested writes throw `ValidationError` ([E003](/errors#e003)) here. See [Nested writes](/nested-writes#many-to-many-relations).

## Self relations

A foreign key to its own table gives that table a `belongsTo` and a `hasMany`:

```ts
categories: {
  id: { type: 'serial', primaryKey: true },
  parentId: { type: 'bigint', references: 'categories.id' },
  name: { type: 'text', notNull: true },
},
```

```ts
const tree = await db.categories.findFirst({
  where: { id: 1 },
  with: { parent: true, children: { with: { children: true } } },
});
// tree.parent is Category | null, tree.children is Category[]
```

Introspection names these `category` and `categories`; the example renames them with [`relationNames`](/cli#renaming-derived-relations-relationnames). Back-references such as `posts -> user -> posts` work.

## Options at every level of `with`

Each relation takes the same read options as `findMany`:

```ts
await db.users.findMany({
  with: {
    posts: {
      where: { published: true },
      orderBy: { createdAt: 'desc' },
      limit: 5,
      select: { id: true, title: true, createdAt: true },
      with: {
        comments: { where: { flagged: false }, orderBy: { createdAt: 'asc' }, limit: 20 },
      },
    },
  },
});
```

- `where` filters the related rows, not the parents.
- `orderBy`, `limit`, `take`, `offset` and `skip` apply per parent. `offset` on a to-one relation throws [E003](/errors#e003).
- `select` or `omit` picks columns; use one, not both.
- `with` nests to a depth of 10, then throws `CircularRelationError` ([E007](/errors#e007)).

<Callout type="note" title="Relation arrays have no guaranteed order">
  Without `orderBy`, a to-many relation's order depends on the database and
  the load strategy. Add `orderBy`, or set `stableRelationOrder: true` on the
  client or query to order unordered to-many relations by primary key.
</Callout>

## Relation filters

Filter parents by their relations without loading them:

```ts
// Users with at least one published post
await db.users.findMany({ where: { posts: { some: { published: true } } } });

// Users whose posts are all published
await db.users.findMany({ where: { posts: { every: { published: true } } } });

// Users with no posts
await db.users.findMany({ where: { posts: { none: {} } } });

// Posts whose author is active (to-one)
await db.posts.findMany({ where: { user: { is: { active: true } } } });
```

To-one relations take `is` and `isNot`. See [Relation filters](/filtering#relation-filters).

## Counting and ordering by relations

```ts
const users = await db.users.findMany({
  with: { _count: { posts: true } },
  orderBy: { posts: { _count: 'desc' } },
});
users[0]._count.posts; // 12
```

`_count` works in the top-level `with` only; nested, it throws `RelationError` ([E005](/errors#e005)). Posts can sort by their user's email: `orderBy: { user: { email: 'asc' } }`. See [Counting related rows](/queries#counting-related-rows-_count) and [Ordering by a relation](/filtering#ordering-by-a-relation).

## Load strategy: `auto`, `join`, `batched`, `flatten`

`relationLoadStrategy` decides how a `with` tree loads. Every strategy returns the same rows.

| Strategy | What it does | Pick it when |
|---|---|---|
| `'auto'` (default) | `'join'`, moving individual relations to `'batched'` by the rules below | Almost always |
| `'join'` | One statement; each relation is a correlated JSON subquery | One round trip matters most |
| `'batched'` | The base query, then one `WHERE fk = ANY($1)` query per relation | Unindexed foreign keys, huge child sets |
| `'flatten'` | One statement; eligible to-one relations become a `LEFT JOIN` | Many parents loading a to-one relation |

The default plan for `db.posts.findMany({ limit: 1000, with: { user: true } })` is one statement:

```sql
SELECT "posts"."id", "posts"."title", "posts"."user_id",
  (SELECT json_build_array(t0."id", t0."email")
     FROM "users" t0
    WHERE t0."id" = "posts"."user_id"
    LIMIT 1) AS "user"
FROM "posts"
LIMIT $1
```

Each relation subquery runs per parent row, so index your foreign keys ([`turbine doctor`](/cli#turbine-doctor) lists missing ones). Set the strategy per query or per client:

```ts
await db.users.findMany({ with: { posts: true }, relationLoadStrategy: 'batched' });

const db = turbine({
  connectionString: process.env.DATABASE_URL,
  relationLoadStrategy: 'join',
});
```

An explicit strategy always wins over `'auto'`. On PowDB the default is its own loader.

### How `'auto'` chooses

`'auto'` moves a relation to the batched loader when:

- index metadata proves a lookup in its subtree is unindexed (generated clients only), or
- it is to-one and the query's `limit` is missing or above the threshold below.

An unindexed `_count` moves to one grouped query unless the parent set is one row. Query events for moved relations carry `strategy: 'auto-batched'`.

| Option | Default | What it does |
|---|---|---|
| `autoRoundTripMs` | `0.7` | Your round trip in ms, as `ping` reports it; sets the to-one threshold |
| `autoToOneJoinMaxRows` | `1000` | The to-one threshold in rows; overrides `autoRoundTripMs` |

```ts
const db = turbine({ connectionString: process.env.DATABASE_URL, autoRoundTripMs: 1.2 });
```

### `'batched'`

- Each level of relations adds a round trip. At 1 ms of round trip `'join'` already wins on small reads, so benchmark on a link like production ([numbers](/benchmarks)).
- A per-relation `limit` still applies per parent. Inside `$transaction`, the follow-ups see the transaction's writes.
- Composite-key relations throw `UnsupportedFeatureError` ([E017](/errors#e017)). Use `'join'` for those.

### `'flatten'`: to-one relations as a LEFT JOIN

```ts
const posts = await db.posts.findMany({
  with: { user: { with: { profile: true } } },
  relationLoadStrategy: 'flatten',
  jsonEncoding: 'object', // required on PostgreSQL
});
```

Each eligible to-one relation becomes a `LEFT JOIN`. An ineligible one stays a subquery, logging `flatten-fallback` while [`diagnostics`](/observability#diagnostics-diagnostics) advice is on. Eligible means:

- `belongsTo` or `hasOne`, with no `limit` or `orderBy`;
- a provably unique target key (the primary key, a unique constraint, or a full unique index on exactly those columns);
- prefixed column aliases that collide with nothing and fit the identifier length limit.

`distinct`, positional JSON (the PostgreSQL default) and SQL Server turn it off for the whole query (`flatten-blocked`). `findUnique` never flattens; `'auto'` never picks it.

### JSON encoding

On PostgreSQL the join plan sends each nested row as a key-less array (`'positional'`, as above), which cuts the payload; other engines use `'object'`. Rows parse the same either way. Use `'object'` for a readable query log, or with `'flatten'`:

```ts
const db = turbine({ connectionString: process.env.DATABASE_URL, jsonEncoding: 'object' });

await db.users.findMany({ with: { posts: true }, jsonEncoding: 'object' }); // per query
```

`'positional'` elsewhere throws [E017](/errors#e017).

## Large result sets

The join plan builds the whole object graph on the server before sending it. Stream when the root query has no `limit` or returns over about 10,000 rows, or a nested `hasMany` has no `limit`:

```ts
for await (const user of db.users.findManyStream({
  with: { posts: { limit: 5 } },
  batchSize: 500,
})) {
  console.log(user.posts[0]?.title);
}
```

Relation subqueries run per fetched batch. See [findManyStream](/queries#findmanystream).

## Performance

### The generic-plan cliff: `planCacheMode`

From its sixth execution, PostgreSQL may switch a named prepared statement to a generic plan, built without the bound values, for the rest of the connection. If a predicate's selectivity swings by value (`tenant_id` on a shared table), sparse values inherit a plan built for dense ones, and the query turns orders of magnitude slower.

Turbine names prepared statements on pools it opens, unless the connection names a pooler. On the slow session:

```sql
SELECT name, generic_plans, custom_plans FROM pg_prepared_statements;
```

A growing `generic_plans` means it switched; [`turbine doctor`](/cli#turbine-doctor) flags reads at risk. The fix plans every run with the real values:

```ts
const db = turbine({
  connectionString: process.env.DATABASE_URL,
  planCacheMode: 'force_custom_plan',
});
```

`'auto'` states the server default, and `'force_generic_plan'` reproduces the cliff for testing. Turbine sends the value as a connection parameter, appended to any `PGOPTIONS` or `?options=`. Limits:

- An external `pool` ignores it and logs `plan-cache-mode-ignored` once.
- A pooler may drop it. Set it on the role: `ALTER ROLE app_user SET plan_cache_mode = 'force_custom_plan';`.
- CockroachDB, YugabyteDB and PostgreSQL before 12 reject it. Other engines throw [E017](/errors#e017); an unknown value throws [E003](/errors#e003).

`preparedStatements: false` also avoids the cliff, but parses and plans every statement on every run.

### A per-query lever: `forceCustomPlan`

Force a custom plan for one read only:

```ts
const rows = await db.orders.findMany({
  where: { tenantId },
  orderBy: { id: 'asc' },
  limit: 20,
  forceCustomPlan: true,
});
```

The statement goes unnamed, so it is planned with its real values each time. Any read takes it (`find*`, `count`, `aggregate`, `groupBy`, streams); writes do not.

- It throws `ValidationError` ([E003](/errors#e003)) under `planCacheMode: 'force_generic_plan'`, which governs unnamed statements too.
- SQLite, MySQL, SQL Server and PowDB throw `UnsupportedFeatureError` ([E017](/errors#e017)).
- `false` does not opt out of a client-level `planCacheMode`.

A custom plan is not always faster, and re-planning a deep `with` costs more, so set it only where you measured a switch. In `turbine-orm/prisma-compat` it is a [Turbine-native query option](/migrate-from-prisma#turbine-native-query-options).
