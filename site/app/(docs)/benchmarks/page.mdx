# Benchmarks

Turbine, Drizzle 0.45, Prisma 7.9 and a hand-written `pg` control run the same queries against the same data and pool. Every figure is a median in milliseconds, and lower is better.

## Results

Local PostgreSQL 17.9 over a Unix socket. With no network round trip, the differences are each library's own per-query cost. Bold marks the fastest ORM. A row marked *tie* is too close to call between Turbine and Drizzle.

| Scenario | Turbine | Drizzle | Prisma | hand-written `pg` |
|---|---|---|---|---|
| findMany, 100 users | **0.181** | 0.242 | 0.241 | 0.164 |
| findMany, 50 users + posts *(tie)* | **1.670** | 1.711 | 4.302 | 1.847¹ |
| findMany, 10 users + posts + comments *(tie)* | **1.082** | 1.166 | 4.204 | n/a |
| findUnique by primary key | **0.035** | 0.080 | 0.078 | 0.036 |
| findUnique, user + posts + comments | **0.146** | 0.285 | 0.374 | n/a |
| count, all users | **0.038** | 0.053 | 0.070 | 0.041 |
| atomic increment *(tie)* | **0.067** | 0.073 | 0.106 | 0.055 |
| pipeline, 5-query batch | **0.165** | 0.341 | 0.338 | 0.177 |
| hot findUnique, rotating ids | **0.026** | 0.069 | 0.059 | 0.030 |

¹ The control spells its nested rows with `json_build_object`. Turbine emits `json_build_array`, which is 1.83x cheaper on the same rows, so the overhead figure below uses an encoding-matched control.

| Geometric mean | Turbine | Drizzle | Prisma |
|---|---|---|---|
| Overhead above hand-written `pg` (8 scenarios with a control) | **1.08x** | 1.47x | 1.81x |
| Ratio to the fastest ORM (10 scenarios) | **1.025x** | 1.498x | 2.072x |

Both means come from the same run as the table and include its streaming scenario, which Drizzle won in that run. [Streaming](#streaming) has its own harness and later figures.

### Streaming

Draining 50,000 comments in batches of 1,000, against two Drizzle releases.

| Arm | Median |
|---|---|
| Turbine `findManyStreamBatches` | **36.70** |
| Drizzle 1.0.0-rc.4 | 37.10 |
| Turbine `findManyStream` (per row) | 40.69 |
| Drizzle 0.45.2 | 44.20 |

Both Turbine APIs beat Drizzle 0.45.2. Against the Drizzle 1.0 release candidate, `findManyStreamBatches` ties and `findManyStream` loses. Turbine reads through a server-side cursor inside a transaction, while the Drizzle arms page by key (`WHERE id > $1 ORDER BY id LIMIT 1000`), so the database work differs.

## Where Turbine loses

- **Deep pagination.** A sorted 20-row page at offset 9,000 takes 0.549 ms on Turbine, 0.341 on Drizzle and 0.318 on Prisma. Turbine names its prepared statements, and PostgreSQL gives a named statement a generic plan that cannot see the bound offset. Set [`forceCustomPlan: true`](/relations#a-per-query-lever-forcecustomplan) on that query: it runs in 0.292 ms.
- **Per-row streaming against Drizzle 1.0.** `findManyStream` runs 5% to 11% behind the release candidate. Use `findManyStreamBatches` when the per-row API is not needed.
- **`relationLoadStrategy: 'batched'` over a network.** It is the fastest strategy on a socket and slower than the join from 1 ms of round-trip time, because it spends an extra round trip per relation. The default, `'auto'`, stays on the join.
- **Point-read leads vanish at distance.** Once the round trip dominates, every library lands near the floor. Through a 25 ms proxy all `findUnique` arms finish within 0.3 ms of each other.
- **Ties.** Against Drizzle, the two nested `findMany` reads, atomic increment, single-row writes, `groupBy` and the first query on a new client are too close to call. Prisma is slower than Turbine on every scenario here except deep pagination.

## Over a network

A real link to Neon PostgreSQL 17.11 (median round trip 22.17 ms). This run compares Turbine with itself and with hand-written `pg`, not with other ORMs.

| Scenario | Faster arm | Slower arm | Ratio |
|---|---|---|---|
| 5-query dashboard | `pipeline()` 24.07 | sequential 172.30 | 7.16x |
| 200 users + posts | `join` 34.73 | `batched` 57.92 | 1.67x |
| 200 users + posts | positional encoding 33.45 | object encoding 36.49 | 1.09x |
| 50 users + posts + comments | positional encoding 35.29 | object encoding 38.80 | 1.10x |
| findUnique by primary key | hand-written `pg` 22.33 | Turbine 23.67 | 1.06x |

The pipeline gap against other ORMs, measured through a local proxy that adds a fixed round-trip time:

| 5-query dashboard | 0 ms | 1 ms | 5 ms | 25 ms |
|---|---|---|---|---|
| Turbine `pipeline` | **0.395** | **3.059** | **5.583** | **26.830** |
| Drizzle transaction | 1.053 | 18.349 | 34.823 | 184.030 |
| Prisma `$transaction` | 1.133 | 18.346 | 35.169 | 183.841 |

`pipeline()` sends the five queries in one round trip. A transaction sends roughly seven (`BEGIN`, five queries, `COMMIT`), so the gap grows with distance.

## Run conditions

- **Machine:** an Apple Silicon MacBook Pro with client and database on one host (Node 24.18.0 for the results table).
- **Database:** PostgreSQL 17.9 over a Unix socket, a dedicated database seeded with 5 orgs, 1,000 users, 10,000 posts and 50,000 comments, then `ANALYZE`d.
- **Libraries:** Prisma 7.9.1 with `@prisma/adapter-pg` and the `relationJoins` preview, so its nested reads use its join strategy. Drizzle 0.45.2 with its relational API. `pg` 8.22.0 under every arm.
- **Pools:** a `pg.Pool` of 10 for Prisma, Drizzle and the control. Turbine uses its own pool at the default size and its default settings.
- **Turbine version per table:** the results table 0.71.0 (2026-08-15), more scenarios and the proxy table 0.67.0, streaming 0.76.0 (2026-08-22), the network table 0.78.0. The current release is {TURBINE_VERSION}; rerun the suite to measure it.

## Method

- Every arm runs once per round and the arm order rotates every round, so machine drift lands on all arms alike.
- The results table reports the median of 200 rounds after 20 warmup, taken as the median of three full runs. Streaming uses three runs of 15 rounds.
- The hand-written control runs in the same rounds, which is why the overhead ratio is the figure to quote.
- Figures under 0.15 ms carry about a third uncertainty in their absolute value. Their order held across runs; their margins are not quotable.
- Each ORM arm is written the way that ORM's docs prescribe. Drizzle has no relation `_count` or relation-filter primitive, so those two arms are subqueries through its query builder.
- In the many-to-many scenario Turbine returns `post.tags[]`, while Prisma and Drizzle return `post.postTags[].tag`.
- Compare figures within a table, not across tables: each comes from its own run.

## Reproduce

From the repository root, against any PostgreSQL database:

```bash
createdb turbine_bench
export DATABASE_URL="postgresql:///turbine_bench?host=/tmp"

npm install && npm run build      # the harnesses import the built package
cd benchmarks && npm install && npx prisma generate
npx tsx seed-neon.ts
cd .. && node dist/cli/index.js generate && cd benchmarks

npx tsx bench-interleaved.ts      # results table
npx tsx bench-extended.ts         # more scenarios
npx tsx bench-stream-parity.ts    # streaming
npx tsx bench-latency.ts          # simulated round-trip times
npx tsx bench-network.ts          # point DATABASE_URL at a direct, non-pooler endpoint
```

Expect the shape above on a local socket, and a flatter table on a remote database, where the round trip dominates.
