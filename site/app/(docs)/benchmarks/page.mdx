## Over a network, the gap grows

On a local socket every query is cheap and the differences are the libraries' own CPU time. In production the database is milliseconds away, and round trips decide the result. A five-query dashboard shows it: Turbine's `pipeline()` sends all five queries in one round trip, and a transaction sends about seven.

## Streaming

<StreamBars />

`findManyStreamBatches` finishes in {ms(batches.median)} ms against {ms(rc.median)} for the Drizzle 1.0 release candidate, a tie, and both Turbine APIs beat Drizzle {BENCH.env.drizzle}. Turbine reads through a server-side cursor inside a transaction, while the Drizzle arms and the control page by key (`WHERE id > $1 ORDER BY id LIMIT 1000`), so the database work differs.

## Where Turbine loses

- **Deep pagination.** A sorted 20-row page at offset 9,000 takes {ms(BENCH.deepPagination.turbine)} ms on Turbine, {ms(BENCH.deepPagination.drizzle)} on Drizzle and {ms(BENCH.deepPagination.prisma)} on Prisma. Turbine names its prepared statements, and PostgreSQL gives a named statement a generic plan that cannot see the bound offset. Set [`forceCustomPlan: true`](/relations#a-per-query-lever-forcecustomplan) on that query and it runs in {ms(BENCH.deepPagination.turbineForceCustomPlan)} ms.
- **The first query on a new client.** Drizzle answers it in {ms(cold.drizzle)} ms against Turbine's {ms(cold.turbine)}, in every run. It is a one-time cost per client.
- **Per-row streaming against Drizzle 1.0.** `findManyStream` takes {ms(perRow.median)} ms against the release candidate's {ms(rc.median)}. Use `findManyStreamBatches` when you don't need rows one at a time.
- **`relationLoadStrategy: 'batched'` over a network.** It is fast on a local socket and slower once the database is a network hop away, because it spends a round trip per relation. The default, `'auto'`, uses the join.
- **Ties.** Scenarios marked *tie*, mostly single-row writes, are too close to call between Turbine and Drizzle across runs.

## How it is measured

- **Same rounds.** Every arm, the hand-written control included, runs once per round, and the arm order rotates every round, so machine drift lands on all arms alike.
- **Medians.** {BENCH.env.rounds} rounds after {BENCH.env.warmup} warmup for the core scenarios, fewer for the slowest ones, each taken as the median of {BENCH.env.runs} full runs.
- **Each ORM as its docs prescribe.** Prisma {BENCH.env.prisma} with `@prisma/adapter-pg` and the `relationJoins` preview, Drizzle {BENCH.env.drizzle} with its relational API, `pg` {BENCH.env.pgDriver} under every arm. Drizzle has no relation `_count` or relation-filter primitive, so those two arms are subqueries through its query builder.
- **Machine.** {BENCH.env.machine}, Node {BENCH.env.node}, PostgreSQL {BENCH.env.postgres} over a Unix socket, seeded with 5 orgs, 1,000 users, 10,000 posts and 50,000 comments, then `ANALYZE`d.
- **Large reads beat the control.** On 50,000 rows Turbine takes {ms(big.turbine)} ms and hand-written `pg` {ms(big.control)}. Turbine parses timestamps with its own faster parser, while the control uses node-postgres's default. Given the same parser, the control is about 5% faster than Turbine.
- **Small numbers.** Figures under 0.15 ms carry about a third uncertainty in their absolute value. Their order held across runs; their margins are not quotable.

## Run it yourself

From the repository root, against any PostgreSQL database:

```bash
createdb turbine_bench
export DATABASE_URL="postgresql:///turbine_bench?host=/tmp"

npm install && npm run build      # the harnesses import the built package
cd benchmarks && npm install && npx prisma generate
npx tsx seed-neon.ts
cd .. && node dist/cli/index.js generate && cd benchmarks

npx tsx bench-interleaved.ts      # core scenarios
npx tsx bench-extended.ts         # more scenarios
npx tsx bench-stream-parity.ts    # streaming
npx tsx bench-latency.ts          # simulated round-trip times
npx tsx bench-network.ts          # a real link: use a direct, non-pooler endpoint
```

Expect this shape on a local socket, and a flatter one on a remote database, where the round trip dominates. The full write-up, with per-run figures: <a href={`https://github.com/zvndev/turbine-orm/blob/main/benchmarks/RESULTS-${BENCH.version}.md`}><code>{`RESULTS-${BENCH.version}.md`}</code></a>.
