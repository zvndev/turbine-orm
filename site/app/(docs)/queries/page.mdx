# API Reference

Every query method, operator and client option Turbine exposes. A generated client has one accessor per table, `db.<table>`, with the full API below. The examples use `db.users` and `db.posts`; every table works the same way.

## findMany

Returns the rows matching the query. Takes `where`, `with`, `orderBy`, `limit` / `take`, `offset` / `skip`, `cursor`, `distinct`, `select` and `omit`.

```ts
const users = await db.users.findMany({
  where: { role: 'admin', orgId: 1 },
  orderBy: { createdAt: 'desc' },
  limit: 20,
  offset: 0,
});
```

With nested relations:

```ts
const users = await db.users.findMany({
  where: { orgId: 1 },
  with: {
    posts: {
      where: { published: true },
      orderBy: { createdAt: 'desc' },
      limit: 5,
      with: { comments: true },
    },
  },
});
```

With `relationLoadStrategy: 'join'` the whole graph loads in one SQL statement. Under the default, `'auto'`, Turbine moves a relation to a follow-up statement when the join plan would be slower, usually because its correlation column is unindexed or it is a to-one relation over an unbounded parent set. The rows are identical either way, and `users[0].posts[0].comments[0]` is fully typed. [Load strategies](/relations#load-strategy-auto-join-batched-flatten) has the rules and how to pin one.

### Silencing the unlimited-query warning

`warnOnUnlimited` is on by default: a `findMany` with no `limit`, `take` or `cursor` logs a warning once per table, through the client's `logger` with code `unlimited-find-many`. It fires in production too, whatever `NODE_ENV` or [`diagnostics`](/observability#diagnostics-diagnostics) say, because an unbounded read costs the most there. A `where` that pins the primary key or a unique column set never warns, and neither does a client with a `defaultLimit`.

Silence it for a query you know is small:

```ts
// This one is fine, a tiny lookup table
const roles = await db.roles.findMany({ warnOnUnlimited: false });
```

Or turn it off on the client: globally with `warnOnUnlimited: false`, or per table with a map keyed by accessor or `snake_case` name, `warnOnUnlimited: { userProfiles: false }`. A per-call value wins over a per-table one, which wins over the global boolean.

### Deterministic pages: the unordered-pagination warning

An unordered `LIMIT` is not stable. Once the table changes, the database can return different rows for the same `LIMIT`, so paging with no `orderBy` can repeat a row or skip one. A `findMany` that paginates (`limit`, `take` or `offset`) with no `orderBy` logs a one-time warning, code `unordered-page`, naming the table, the pagination shape and the `orderBy` to add:

```ts
// warns: the page is not deterministic
const page = await db.users.findMany({ limit: 20, offset: 40 });

// no warning: the page is stable
const page = await db.users.findMany({ orderBy: { id: 'asc' }, limit: 20, offset: 40 });
```

A `distinct` query never warns (`DISTINCT ON` imposes its own order), and neither does a `cursor` page, which is [always ordered](#pagination-limit--take-offset--skip-cursor). The warning follows the same `warnOnUnlimited` setting (per call, per table, global) and fires once per table and shape. Unlike the unlimited-query warning it is advice: it stays silent while the client's [`diagnostics`](/observability#diagnostics-diagnostics) advice is off, the default under `NODE_ENV=production`.

To fix every query at once, set **`implicitPkOrdering: true`** on the client. A paginating `findMany` with no `orderBy` then gets `ORDER BY <primary key> ASC` (every column of a composite key, in declaration order), and the warning stops. An explicit `orderBy` always wins, a table with no primary key is left alone, and a `cursor` page keeps its own ordering rule.

```ts
const db = turbine({ connectionString: process.env.DATABASE_URL, implicitPkOrdering: true });
```

It is off by default because it changes SQL your application already sends, and with it the rows a page returns and the plan the engine picks. The [`prisma-compat`](/migrate-from-prisma) adapter always applies this ordering, as Prisma does.

### select / omit

`select` returns only the named columns. `omit` returns every column except the named ones.

```ts
// Only return id and email
const users = await db.users.findMany({
  select: { id: true, email: true },
});

// Return everything except the password_hash column
const users = await db.users.findMany({
  omit: { passwordHash: true },
});
```

The same rules apply at the top level and inside a relation's `with` block:

- Use one or the other. `select` and `omit` in the same block, each naming at least one field, throws `ValidationError` (`TURBINE_E003`).
- A `select` that names no field (empty, or every value `false`) throws `TURBINE_E003`.
- Both take **column** names. A name that does not resolve throws `TURBINE_E003`, naming the table and the closest match. A relation name gets [its own message](/errors#unknown-field-names) pointing at `with`.

### PII fields: `includePii`

Columns tagged `pii: true` in [`defineSchema`](/schema#pii-fields) are left out of every default projection: top-level rows, relation subqueries, batched loads and the row a write returns. A read returns them only with `includePii: UNSAFE`, which returns every PII column at the top level and at every nested `with` level of that query. With it set, `select` can also narrow the result to a PII column.

Naming a PII column in `select` is not an opt-in. Without `includePii: UNSAFE` it throws `ValidationError` (`TURBINE_E003`) at any depth, because `select` often comes from request data and a request must not be able to read PII by naming a column. Before 0.90, `select` alone was the opt-in; see [Upgrading to 0.90](/upgrading-to-0-90#a-pii-column-in-select-needs-includepii-unsafe).

One exception: a PII-tagged column that is part of the primary key is always returned, on reads and writes alike. A row missing part of its key, fed back into an `update`, would build a partial predicate that matches more rows than you meant. Tag sensitive data, not keys.

```ts
import { UNSAFE } from 'turbine-orm';

// Default: email (pii) is absent
const u = await db.users.findFirst({ where: { id: 1 } });
u.email; // undefined

// select alone is refused: ValidationError [TURBINE_E003] ... "email", which is tagged PII
await db.users.findFirst({ where: { id: 1 }, select: { email: true } });

// With the opt-in, select narrows to exactly it
const withEmail = await db.users.findFirst({ where: { id: 1 }, select: { email: true }, includePii: UNSAFE });

// includePii returns every PII column, including inside `with`
const full = await db.users.findMany({
  where: { active: true },
  with: { posts: true },
  includePii: UNSAFE,
});
```

`includePii` is a [privilege option](/global-filters#privilege-options-and-the-unsafe-symbol): only the imported `UNSAFE` symbol enables it, and `includePii: true` throws `TURBINE_E003`. `JSON.parse` cannot produce a symbol, so `db.users.findMany({ ...req.body })` cannot switch it on.

It is a read option, accepted by `findMany`, `findUnique`, `findFirst`, their `*OrThrow` forms, `findManyStream`, and the `groupBy` / `aggregate` shapes below. Writes do not take it. The flag guards one thing, **whether a stored PII value can reach your application**, so `where`, `orderBy` and `having` on a PII column are always allowed: they return no PII value.

Aggregates follow the same line. A shape that returns a stored cell needs the opt-in, and the error names the column:

| Over a PII column | Without `includePii: UNSAFE` |
|---|---|
| A `groupBy` `by` key, including a JSON-path key | Throws `TURBINE_E003`: the group keys *are* the values |
| `_min` / `_max`, in `groupBy` or `aggregate`, including JSON-path targets | Throws `TURBINE_E003`: each returns one row's stored value |
| `_count` | Allowed: it returns a count |
| `_sum` / `_avg` | Allowed: each returns a value computed across rows, not a stored cell |

```ts
// Refused: the group keys would be the email values
await db.users.groupBy({ by: ['email'], _count: true });
// ValidationError [TURBINE_E003]: ... "email" is a PII column ...

// Refused: _max returns one row's stored email
await db.users.aggregate({ _max: { email: true } });

// Allowed: explicit opt-in on either args type
await db.users.groupBy({ by: ['email'], _count: true, includePii: UNSAFE });
await db.users.aggregate({ _max: { email: true }, includePii: UNSAFE });

// Allowed with no flag: no stored PII value is returned
await db.users.groupBy({ by: ['role'], _count: true });
await db.users.aggregate({ _count: true, where: { email: { endsWith: '@acme.com' } } });
```

With `includePii: UNSAFE` set, the SQL is the same as for an untagged schema. The policy applies on PowDB as well as the SQL engines, and a schema with no `pii` tags is unaffected everywhere.

Writes hold the same line in the SQL itself. On a table with PII columns, `create`, `createMany`, `update`, `delete`, `upsert` and nested writes return an explicit non-PII column list instead of `RETURNING *`:

| Engine | How PII is left out |
|---|---|
| PostgreSQL, SQLite | `RETURNING "id", "name", ...` |
| MySQL | a re-select of the listed columns |
| SQL Server | per-column `OUTPUT` |
| PowDB | stripped after the row arrives, because its `returning` takes no column list |

PII values are written and stored normally; they are not returned. A PII-tagged primary key stays in the list, and a table with no PII columns keeps `RETURNING *`. A write `select` that names a PII column throws `TURBINE_E003`, since writes take no `includePii`. Read the row back with `includePii: UNSAFE` instead.

### Pagination, `limit` / `take`, `offset` / `skip`, `cursor`

Offset pagination uses `limit` and `offset`. `take` and `skip` are Prisma's names for the same two options: both spellings compile to the same SQL and share one cache entry. Both spellings of one bound with different values (`{ limit: 10, take: 5 }`) throw `ValidationError` (`TURBINE_E003`); equal values are accepted. `offset` works without `limit` on every engine.

```ts
const page2 = await db.posts.findMany({
  orderBy: { id: 'asc' },
  limit: 20,   // or take: 20, same thing
  offset: 20,
});
```

For deep pagination, use `cursor`. It names where the last page ended, and Turbine seeks past that point (`>` for ascending order, `<` for descending). The cursor row itself is excluded. Unlike `OFFSET 100000`, a keyset page never scans the rows it skips:

```ts
const firstPage = await db.posts.findMany({
  orderBy: { id: 'asc' },
  take: 20,
});

const nextPage = await db.posts.findMany({
  orderBy: { id: 'asc' },
  cursor: { id: firstPage.at(-1)!.id }, // rows with id > this value
  take: 20,
});
```

**The page order.** A cursor page is always ordered: by your `orderBy`, plus the primary key as a tiebreaker in the direction of the last `orderBy` term, unless the `orderBy` already contains a unique key. With no `orderBy` at all, the page is ordered by the primary key. A table with neither a primary key nor a unique key on NOT NULL columns cannot take a cursor (`TURBINE_E003`). This ordering is new in 0.90; see [Upgrading to 0.90](/upgrading-to-0-90#a-cursor-page-is-always-ordered).

**Placing the page.** The cursor places the page in one of two ways:

- **By value.** It carries a value for every column of the page order. Pass the last row's values for each ordered field plus the key: `cursor: { createdAt: last.createdAt, id: last.id }`. Extra fields are ignored, so passing the whole last row works.
- **By row.** It names one row by a unique key, the same rule as [`findUnique`](#findunique--finduniqueorthrow): `cursor: { id: last.id }` under `orderBy: { createdAt: 'desc' }`. Turbine reads that row's ordered values in the same statement. If the row has been deleted, the page is empty.

A cursor that does neither throws `ValidationError` (`TURBINE_E003`) naming the missing fields and the unique keys that would work. So does a cursor beside a relation, JSON-path or vector `orderBy`; page those with `offset`.

```ts
// TURBINE_E003: the page order is (createdAt desc, id desc) and the cursor has no "id"
await db.posts.findMany({ orderBy: { createdAt: 'desc' }, cursor: { createdAt: last.createdAt }, take: 20 });
```

A multi-column order is a keyset seek, not a conjunction. For `orderBy: [{ viewCount: 'asc' }, { id: 'asc' }]` the predicate is `(view_count > $1 OR (view_count = $1 AND id > $2))`, with `<` for a `desc` field, so rows that tie on the leading key are not skipped. Each value is bound once, however many branches reference it.

**NULL sort keys.** Rows whose sort key is `NULL` are visited exactly once, in each engine's NULL placement. PostgreSQL puts NULLs last ascending and first descending, unless you pass `nulls`. SQLite, MySQL and SQL Server treat NULL as the smallest value. On PostgreSQL, Turbine writes the placement out for a nullable ordered column, so a Postgres-compatible engine with a different default still reads the order the seek assumes.

**Cursor values.** Each value is a plain value or `{ equals: value }`, the one-row rule of `findUnique`. These throw `TURBINE_E003`:

- an operator object, an array or a column reference as a value;
- a cursor whose every field is `undefined`, which would quietly restart at the first row;
- `cursor: null`, `cursor: {}`, or a cursor that is not an object;
- `null` for a NOT NULL or primary-key column, since no row holds it. On a nullable column, `null` is a real position.

For the first page, leave `cursor` out or pass `undefined`:

```ts
// First page: no cursor. Later pages: the last row's key.
await db.posts.findMany({ orderBy: { createdAt: 'desc' }, take: 20, cursor: last ? { id: last.id } : undefined });
```

**The first page uses the same order.** A paginated `findMany` (`limit` / `take` / `offset` / `skip`) whose `orderBy` can tie gets the same tiebreaker appended, so the first page and the cursor pages after it are cut from one total order:

```ts
await db.users.findMany({ orderBy: { name: 'desc' }, take: 20 });
// ORDER BY "name" DESC, "id" DESC LIMIT $1
```

An `orderBy` that already contains a unique NOT NULL key is left as written. A `findFirst` with `offset` is a page and gets the tiebreaker too, so the row it returns does not depend on how the engine breaks ties. These are left unchanged:

- `findFirst` without `offset`;
- a query with no `limit` or `offset`;
- a `distinct` query;
- an order by vector distance, where a tiebreaker would turn a nearest-neighbour index scan into a full sort;
- a paginated query with no `orderBy` at all, which only gets the [warning](#deterministic-pages-the-unordered-pagination-warning).

### distinct

`distinct` de-duplicates rows by the listed fields using PostgreSQL's `DISTINCT ON`:

```ts
// One post per author
const sample = await db.posts.findMany({
  distinct: ['userId'],
  orderBy: { userId: 'asc' },
});
```

`orderBy` decides which row survives in each group: sort by the `distinct` fields first, then by whatever should pick the winner.

<Callout type="warning" title="PostgreSQL only">
  `DISTINCT ON` is a PostgreSQL extension. On SQLite, MySQL and SQL Server,
  `distinct` throws `UnsupportedFeatureError` (`TURBINE_E017`), as
  `groupBy({ distinctOn })` does. CockroachDB and YugabyteDB run on the
  PostgreSQL dialect and get the clause as written.
</Callout>

### Ordering, direction and NULLS placement

`orderBy` maps fields to a direction. A plain `'asc'` or `'desc'` works everywhere. To control where `NULL` values land, pass a spec object instead:

```ts
const users = await db.users.findMany({
  orderBy: { lastLoginAt: { sort: 'desc', nulls: 'last' } },
});
// ORDER BY "last_login_at" DESC NULLS LAST
```

Plain and spec entries mix freely, and their order is preserved:

```ts
orderBy: { name: 'asc', lastLoginAt: { sort: 'desc', nulls: 'last' } }
// ORDER BY "name" ASC, "last_login_at" DESC NULLS LAST
```

For multi-key ordering you can also pass a Prisma-style array of objects. The array's order is the sort precedence, independent of object key order:

```ts
orderBy: [{ createdAt: 'desc' }, { id: 'asc' }]
// ORDER BY "created_at" DESC, "id" ASC
```

Both forms take `{ sort, nulls }` specs, produce the same SQL for the same key order, and work wherever an `orderBy` does: `findMany`, a `with` relation and `groupBy`.

> **Pitfall:** `NULLS FIRST` / `NULLS LAST` is a PostgreSQL and SQLite feature. On MySQL and SQL Server, explicit `nulls` placement throws `UnsupportedFeatureError` (`TURBINE_E017`). Plain `'asc'` / `'desc'` works on every engine.

### Ordering by a relation

Order rows by their related rows. For a **to-many** relation the only key is `_count`, compiled to a correlated `COUNT(*)` subquery:

```ts
// Users, most posts first
const users = await db.users.findMany({
  orderBy: { posts: { _count: 'desc' } },
});
```

For a **to-one** relation, order by a column of the target. It compiles to a correlated scalar subquery and takes `{ sort, nulls }`:

```ts
// Posts, ordered by their author's name
const posts = await db.posts.findMany({
  orderBy: { author: { name: 'asc' } },
});
```

The chain can be more than one hop long, as long as every hop is to-one:

```ts
// Versions, ordered by the name of their model's category
const versions = await db.versions.findMany({
  orderBy: { model: { category: { name: 'asc' } } },
});
```

Each extra hop is an `INNER JOIN` inside the *same* correlated subquery, so a chain of any length is one subquery with one `LIMIT 1`. Every hop applies its target's global filter to the join, so ordering never keys off a soft-deleted or other-tenant row. On a generated client the chain is typed: each value is a direction, a `{ sort, nulls }` spec or the next hop, up to the head relation plus ten hops. That is where the builder stops; one more hop throws `TURBINE_E007`.

A to-many hop in the middle of a chain has no single value to order by, so it throws `TURBINE_E003` at runtime. The type cannot catch it, because it keys hops by name. Use a pick-row ordering (`{ pick, by }`) or `_count` instead.

Relation ordering adds no bound parameters. An unknown relation throws `RelationError` (`TURBINE_E005`). A non-`_count` key on a to-many relation, or an unknown column on a to-one relation, throws `ValidationError` (`TURBINE_E003`).

<Callout type="note" title="orderBy keys are checked at compile time">
On a generated client, `orderBy: { nmae: 'asc' }` is a type error rather than a runtime `TURBINE_E003`. The check reaches a `with` block's `select`, `omit` and `orderBy`, each scoped to that relation's target. A clause built dynamically (`Record<string, 'asc' | 'desc'>`) still assigns, and an untyped `db.table(name)` stays open. See [Misspelled keys](#misspelled-keys-are-a-compile-error).
</Callout>

## findUnique / findUniqueOrThrow

Look up a row by a unique column (primary key or any `unique` constraint).

```ts
const user = await db.users.findUnique({
  where: { id: 42 },
  with: { posts: true },
});
// user is User | null

const user2 = await db.users.findUniqueOrThrow({
  where: { email: 'alice@example.com' },
});
// Throws NotFoundError (TURBINE_E001) if not found
```

Composite primary keys are passed as an object matching the keys:

```ts
const row = await db.memberships.findUnique({
  where: { userId: 1, orgId: 2 },
});
```

The `where` must identify a single row: the primary key, a single-column unique, every column of a compound unique, or a compound-unique selector. Extra predicates beside the key are fine, since they can only narrow it. Anything else throws `ValidationError` (`TURBINE_E003`) naming the keys that would work.

Each key column must be a plain value (`{ id: 42 }`) or `{ equals: value }`. A column reference, `mode: 'insensitive'`, an `in` list, a range, or any other operator beside `equals` can match many rows, so it does not identify one. Neither does `null`, even on a unique column: PostgreSQL allows any number of NULLs in a unique index. The same rule applies to the `where` of `update`, `delete` and `upsert`, on every engine.

```ts
// TURBINE_E003: an insensitive match can hit "Ada@x.com" and "ada@x.com"
await db.users.findUnique({ where: { email: { equals: input, mode: 'insensitive' } } });

// "Any row matching a filter" is findFirst
await db.users.findFirst({ where: { email: { equals: input, mode: 'insensitive' } } });
```

## findFirst / findFirstOrThrow

Returns the first row matching `where`, in `orderBy` order, or `null`. Use it for lookups that are not by a unique key. `findFirstOrThrow` throws `NotFoundError` (`TURBINE_E001`) instead of returning `null`.

```ts
const post = await db.posts.findFirst({
  where: { authorId: 42, published: true },
  orderBy: { createdAt: 'desc' },
});
```

A `where` whose every key is `undefined` throws `TURBINE_E003`. Otherwise `findFirst({ where: { resetToken: token } })` with `token` undefined would return an arbitrary row. To ask for any row on purpose, omit `where` or pass `where: {}`. `findMany` and `count` treat an all-`undefined` `where` as no filter; see [`undefined` means absent](#undefined-means-absent).

## Row locks

`findMany`, `findFirst`, `findFirstOrThrow`, `findUnique` and `findUniqueOrThrow` take `lock`, which locks the rows they return until the transaction ends. Use it to read a row you are about to change, so no other transaction can change it in between:

```ts
await db.$transaction(async (tx) => {
  const job = await tx.jobs.findFirst({
    where: { status: 'queued' },
    orderBy: { id: 'asc' },
    lock: { mode: 'update', skipLocked: true },
  });
  // SELECT ... WHERE "status" = $1 ORDER BY "id" ASC LIMIT $2 FOR UPDATE OF "jobs" SKIP LOCKED
  if (job) await tx.jobs.update({ where: { id: job.id }, data: { status: 'running' } });
});
```

| `lock` | SQL |
|---|---|
| `'update'` | `FOR UPDATE` |
| `'noKeyUpdate'` | `FOR NO KEY UPDATE` |
| `'share'` | `FOR SHARE` |
| `'keyShare'` | `FOR KEY SHARE` |
| `{ mode, noWait: true }` | `... NOWAIT`: fail at once if a row is locked by another transaction |
| `{ mode, skipLocked: true }` | `... SKIP LOCKED`: leave locked rows out of the result |

`noWait` and `skipLocked` cannot be combined. A misspelled mode or key throws `TURBINE_E003` with a suggestion.

- **Only the queried table is locked.** Turbine emits `FOR <mode> OF "<table>"` after `LIMIT` / `OFFSET`, so rows loaded by `with` are never locked, whatever the [relation strategy](/relations).
- **It needs a transaction.** Outside `$transaction` the lock would be released before the call returns, so a locking read on `db` throws `TURBINE_E003`. A `$transaction([...])` batch and a transactional [pipeline](#pipeline) hold the lock for the batch; a pipeline with `transactional: false` refuses a locking read.
- **Refused shapes:** `lock` on `findManyStream` / `findManyStreamBatches`, or with `distinct`, throws `TURBINE_E003`.
- **Engines:** PostgreSQL takes all four modes. MySQL 8 takes `'update'` and `'share'`. SQLite, SQL Server and PowDB throw `UnsupportedFeatureError` (`TURBINE_E017`).

A lock that cannot be taken (`noWait` on a locked row, or a wait past the server's lock timeout) throws [`LockNotAvailableError`](/errors#e013). It is `TURBINE_E013`, carries `isRetryable`, and extends `SerializationFailureError`, so an existing retry loop catches it. On PostgreSQL the failure aborts the transaction. To try a lock and carry on when it fails, take it in a nested block:

```ts
import { LockNotAvailableError } from 'turbine-orm';

await db.$transaction(async (tx) => {
  try {
    await tx.$transaction((inner) =>
      inner.accounts.findUnique({ where: { id }, lock: { mode: 'update', noWait: true } }),
    );
  } catch (err) {
    if (!(err instanceof LockNotAvailableError)) throw err;
    // Only the savepoint rolled back; the transaction is still usable.
  }
});
```

Studio's Query tab and the MCP server's `explain_query` and `compile_query` tools refuse `lock` by name: they run reads in a read-only transaction, where a lock cannot be taken.

## create

Inserts one row and returns it, generated columns included.

```ts
const newUser = await db.users.create({
  data: {
    email: 'alice@example.com',
    name: 'Alice',
    orgId: 1,
  },
});
```

### Returning fewer columns

`create`, `update`, `delete` and `upsert` take the same `select` / `omit` as a read. Use it when the row carries a large column you just wrote and do not need back:

```ts
const { id } = await db.events.create({
  data: { kind: 'click', payload },
  select: { id: true },
});
```

The narrowing happens in the statement: `RETURNING "id"` on PostgreSQL and SQLite, the follow-up `SELECT` on MySQL, `OUTPUT INSERTED.[id]` on SQL Server. The rest of the row never crosses the wire.

The read rules apply, checked before anything is written: an unknown field, a relation name, an empty `select`, or `select` and `omit` together throw `ValidationError` (`TURBINE_E003`). A write never returns a [PII field](#pii-fields-includepii), and a `select` that names one throws `TURBINE_E003`. The result type narrows to match. A nested create or update applies the projection to the row it returns. PowDB, whose `returning` takes no column list, narrows the row after it arrives, with the same result.

### Inserting a row of pure defaults

`data: {}`, or a `data` whose every field is `undefined`, inserts a row in which every column takes its database default:

```ts
// INSERT INTO "events" DEFAULT VALUES RETURNING *
const event = await db.events.create({ data: {} });
```

A table whose columns lack defaults fails with the database's NOT NULL violation (`NotNullViolationError`, `TURBINE_E010`).

<Callout type="warning" title="The bulk form is not portable">
`create({ data: {} })` works on every engine. The multi-row form does not, because `INSERT ... DEFAULT VALUES` is single-row only in most dialects:

- **PostgreSQL** emits `INSERT INTO t SELECT FROM generate_series(1, N)`, any row count.
- **MySQL** repeats its empty `VALUES ()` tuple, any row count, *except* with `skipDuplicates: true`: `ON DUPLICATE KEY UPDATE` needs a column to assign and there is none, so that combination throws `UnsupportedFeatureError` (`TURBINE_E017`).
- **SQLite** and **SQL Server** throw `UnsupportedFeatureError` (`TURBINE_E017`) for more than one all-defaults row. Call `create({ data: {} })` once per row.

Every row must also name the same fields; see [uniform rows](#createmany) below.
</Callout>

### Writing JSON columns

What a `json` / `jsonb` column stores depends on the JS value you write. The rule is the same on every write path (`create`, `createMany`, `update`, `updateMany`, `upsert`, nested writes) and every engine:

| Value | Stored |
|---|---|
| an object | that JSON object |
| an array | that JSON array |
| a string | **raw JSON text**: `'{"a":1}'` stores the object `{ a: 1 }`, so `JSON.stringify(value)` works |
| `null` | SQL `NULL` |
| `jsonValue(v)` | `JSON.stringify(v)`: a way to store a JSON string or a JSON `null` |

```ts
import { jsonValue } from 'turbine-orm';

await db.docs.create({ data: { data: ['a', 'b'] } });          // the JSON array ["a", "b"]
await db.docs.create({ data: { data: jsonValue('hello') } });  // the JSON string "hello"
await db.docs.create({ data: { data: jsonValue(null) } });     // JSON null; the column is not SQL NULL
```

A value with no JSON form (a `bigint` inside an array, say) throws `ValidationError` (`TURBINE_E003`) naming the column.

### Objects on non-JSON columns

On PostgreSQL, a plain object or an array written to a built-in scalar column throws `ValidationError` (`TURBINE_E003`) naming the column, its type and the fix. The scalar types are the text types, integers, `numeric`, floats, `boolean`, the temporal types, `uuid`, `bytea`, network types, `money`, `xml` and `interval`. To store JSON text on purpose, write `JSON.stringify(value)` or `jsonValue(value)`. Dates, Buffers, `bigint`, class instances, array columns, enums, domains and extension types are not affected.

SQLite, MySQL and SQL Server accept an object on a text column, where a text column is a normal home for JSON.

### Field names and column names resolve identically

A key in `data`, `where`, `orderBy`, `select`, `omit`, `distinct`, `cursor`, `groupBy`'s `by`, or an aggregate target may be spelled as the field name (`lastRun`) or as the underlying column name (`last_run`). Both spellings compile to the same SQL and go through the same value processing, including the UTC rewrite on zone-less temporal columns:

```ts
// Identical statement, and identical bound value.
await db.jobs.update({ where: { id: 1 }, data: { lastRun: new Date() } });
await db.jobs.update({ where: { id: 1 }, data: { last_run: new Date() } });
```

A name that resolves to no column throws `ValidationError` (`TURBINE_E003`), so a typo stays a typo.

### Relation names resolve the same way

A relation may be named by its declared name (`blogPosts`) or by the table spelling of that name (`blog_posts`), in `with`, `_count`, relation filters (`some` / `every` / `none` / `is` / `isNot`) and `orderBy`, at any nesting depth:

```ts
// Identical statement, identical rows.
await db.authors.findMany({ with: { blogPosts: true } });
await db.authors.findMany({ with: { blog_posts: true } });
```

The declared name always wins, so a schema that declares `blog_posts` keeps it. Relation keys in the returned rows use the declared name whichever spelling you queried with, just as a column selected as `last_run` comes back as `lastRun`. A name that matches no relation throws `RelationError` (`TURBINE_E005`).

## createMany

Inserts many rows in one statement. On PostgreSQL that is a single `INSERT ... UNNEST(...)`, not one insert per row. A batch of [pure defaults](#inserting-a-row-of-pure-defaults) has no columns to unnest, so it emits `INSERT INTO t SELECT FROM generate_series(1, N)` instead.

```ts
const users = await db.users.createMany({
  data: [
    { email: 'a@b.com', name: 'A', orgId: 1 },
    { email: 'b@b.com', name: 'B', orgId: 1 },
    { email: 'c@b.com', name: 'C', orgId: 1 },
  ],
});
```

It returns the inserted rows, except on MySQL, where a plain `createMany` returns `[]`; see [Engines](/engines).

<Callout type="warning" title="Every row must name the same fields">
`createMany` compiles **one** statement, and its column list comes from the first row. A row that disagrees would lose data silently in both directions: a field the first row names and a later row omits would bind as `NULL`, overriding that column's default, and a field only a later row names would not be in the column list at all.

So a ragged call throws `ValidationError` (`TURBINE_E003`) naming the offending row index and the differing columns, on every engine including PowDB. A field set to `undefined` counts as omitted, as in `create`. Supply the field on every row, or split the call into one `createMany` per field set.
</Callout>

A `json` / `jsonb` cell takes the same values as a single [JSON write](#writing-json-columns), and each element of `data` inserts exactly one row.

**Large batches.** A statement takes a limited number of bind parameters: 65,535 on PostgreSQL and MySQL, 32,766 on SQLite. A `createMany` that needs more is split into chunks inside one transaction, so the rows land together or not at all. PostgreSQL's `UNNEST` form binds one array per column and never gets near the limit. A table with an array column inserts with a `VALUES` tuple per row instead, which can reach it, and is chunked the same way.

- **SQL Server** takes at most 1,000 rows and 2,098 parameters in one `INSERT`, so a plain `createMany` is chunked at whichever it reaches first, inside one transaction. A [`createMany` with `onConflict`](#multi-row-upsert-onconflict) is chunked at 2,098 parameters.
- **SQLite** is chunked at 250 parameters, far below its limit: SQLite finds each named parameter by a linear search, so a statement's cost grows with the square of its size. Two kinds of call keep one statement as large as SQLite allows: an `onConflict` call whose written rows cannot be told apart across statements (its `update` assigns the key, or the only key is a PII column), and a call on a pool without `connect()`.
- **`buildCreateMany`** (one statement, for [`pipeline`](#pipeline) or `$transaction([...])`) refuses an oversized batch with `TURBINE_E003`, naming the limit and a chunk size.
- **Inside a `$transaction` callback** the chunks run on that transaction, in a savepoint of their own. A failed chunk rolls back every chunk before it, even when your callback catches the error and commits.
- **A pool without `connect()`** (a stateless HTTP driver) cannot hold the transaction the chunks need, so an oversized call there throws `UnsupportedFeatureError` (`TURBINE_E017`) naming the alternative.

`createMany` takes [`select` / `omit`](#returning-fewer-columns) like `create`, to narrow the rows it returns.

### Counting instead of returning rows: `returning: false`

`returning: false` resolves to `{ count }` instead of the rows. A plain insert then sends no `RETURNING` (no `OUTPUT` on SQL Server), so neither the server nor your process handles rows you would not read:

```ts
const { count } = await db.events.createMany({ data: batch, returning: false });
```

- With [`onConflict`](#multi-row-upsert-onconflict), the statement returns only the conflict-key columns, which keeps the case-insensitive duplicate check below, and `count` is the rows inserted or updated. An ignored conflict and an existing row that `where` excludes are not counted.
- With `skipDuplicates`, `count` is the rows inserted. MySQL refuses this combination with `TURBINE_E017`, because it counts a skipped row as written.
- A chunked call adds up its chunks' counts.
- The result type follows the flag: `{ count: number }` for `false`, rows for `true` or no flag. `select` or `omit` beside `returning: false`, or a `returning` that is not a boolean, throws `TURBINE_E003`.

### Writing to several tables at once

Turbine has no data-modifying CTE (`WITH a AS (INSERT ...) INSERT ...`). To write batches to several tables together, put one `buildCreateMany` per table in a [pipeline](#pipeline). The statements are sent together and run in one transaction, so every batch lands or none does.

```ts
const [orders, lines] = await db.pipeline(
  db.orders.buildCreateMany({ data: orderRows, returning: false }),
  db.orderLines.buildCreateMany({ data: lineRows, returning: false }),
);
// [{ count: 3 }, { count: 12 }]
```

Every statement is built before any of them runs, so the second cannot see ids the first generates. Rows that reference each other need keys you supply (a UUID, or ids you read first). Each `buildCreateMany` is one statement, so an oversized batch throws `TURBINE_E003` instead of being chunked.

### Multi-row upsert: `onConflict`

`onConflict` turns `createMany` into an upsert of many rows in one statement. Rows with a new key are inserted; rows whose key already exists update the existing row instead:

```ts
const rows = await db.users.createMany({
  data: [
    { email: 'a@b.com', name: 'A' },
    { email: 'b@b.com', name: 'B' },
  ],
  onConflict: { target: ['email'], update: ['name'] },
});
// INSERT ... ON CONFLICT ("email") DO UPDATE SET "name" = EXCLUDED."name" RETURNING *
```

- **`target`** names the conflict key: the primary key or one full unique key, in any order. A partial unique index cannot be a target. Anything else throws `TURBINE_E003` listing the valid targets.
- **`update`** is either a list of fields, each set to the incoming row's value, or a per-column object. The object takes plain values, the [atomic operators](#atomic-update-operators), [update expressions](#update-expressions-expr), and `expr.excluded('field')` for the incoming row's value:

```ts
import { col, expr } from 'turbine-orm';

await db.pageViews.createMany({
  data: batch, // [{ path, views }, ...]
  onConflict: {
    target: ['path'],
    update: { views: expr.add(col('views'), expr.excluded('views')) },
    where: { archived: false }, // only existing rows that match are updated
  },
});
```

- **`where`** limits which existing rows are updated. A conflicting row that does not match is left alone and is not returned. Inserted rows are not filtered, as with `create`.
- **`ignore: true`** (instead of `update`) leaves every existing row untouched.

Further rules:

- Two rows with the same key in one call throw `TURBINE_E003` before any SQL runs, because one statement cannot write a key twice. Merge them first.
- Two keys that differ in JavaScript but compare equal in the column (`'bob'` and `'BOB'` under a case-insensitive collation, `citext`, or SQLite's `COLLATE NOCASE`) also throw `TURBINE_E003`, on every engine and across the statements of a chunked call. The call is rolled back, so none of its rows stay.
- An active [global filter](/global-filters) applies to the conflict update, as `where` does.
- [`updatedAt`](#updatedat-columns) columns are stamped on the update unless `update` names them.
- The result holds the rows inserted or updated, in no guaranteed order.

| Engine | Support |
|---|---|
| PostgreSQL, SQLite | `INSERT ... ON CONFLICT` |
| SQL Server | `MERGE ... WITH (HOLDLOCK)` |
| MySQL 8.0.19+ | `INSERT ... AS ... ON DUPLICATE KEY UPDATE`. Throws `UnsupportedFeatureError` (`TURBINE_E017`) for `where` (no predicate slot), `ignore` (inserted and skipped rows cannot be told apart), an active global filter (unless `skipGlobalFilters: UNSAFE`), a NULL target value, and a second unique key whose columns are in `data` (MySQL cannot limit the update to one key). The rows come back through a re-read by key in the same transaction |
| PowDB | `TURBINE_E017` |

## update / updateMany

`update` changes **one row, addressed by a unique key**. `updateMany` changes every row matching a filter.

```ts
await db.users.update({
  where: { id: 42 },
  data: { name: 'Alice Updated' },
});

await db.users.updateMany({
  where: { role: 'guest' },
  data: { role: 'member' },
});
```

`update` returns the updated row and takes [`select` / `omit`](#returning-fewer-columns) to narrow it. `updateMany` returns `{ count }`.

An `update` whose `where` does not identify a single row throws `TURBINE_E003`, naming the unique keys the table has. It is the same rule [`findUnique`](#findunique--finduniqueorthrow) applies. `delete` and `deleteMany` split the same way, and [`upsert`](#upsert) carries the rule for its own reason. `update({ where: {}, optimisticLock })` is refused too: a version column is not unique.

If your predicate does identify one row, through a constraint Turbine's metadata cannot see, pass `allowFullTableScan: UNSAFE`. That also disarms the empty-`where` guard, so an all-`undefined` `where` then matches every row instead of throwing.

`limit`, `take`, `offset` and `skip` on `updateMany` or `deleteMany` throw `TURBINE_E003` on every engine. To write a bounded batch, select the ids first:

```ts
const batch = await db.jobs.findMany({ where: { status: 'queued' }, select: { id: true }, orderBy: { id: 'asc' }, limit: 100 });
await db.jobs.updateMany({ where: { id: { in: batch.map((j) => j.id) } }, data: { status: 'running' } });
```

### Atomic update operators

Pass an operator object instead of a value to change a number in place. Turbine emits `col = col + $n`, so concurrent updates cannot lose writes.

```ts
await db.posts.update({
  where: { id: 1 },
  data: {
    viewCount: { increment: 1 },
    likesCount: { decrement: 1 },
    score: { multiply: 2 },
    rank: { divide: 2 },
    title: { set: 'New title' }, // explicit set, same as a literal
  },
});
```

The operators on numeric columns are `set`, `increment`, `decrement`, `multiply` and `divide`. `divide` on an integer column truncates, on every engine.

On a `json` / `jsonb` column only `set` is an operator. `{ increment: 1 }` there is the JSON document `{"increment":1}`, and `{ set: doc }` is how to write a document that itself has a `set` key. Operators apply in `update` data only. In `create` data an operator object is a value, so on a scalar PostgreSQL column it is refused like any [object](#objects-on-non-json-columns).

### Update expressions: `expr`

When the new value depends on the row itself, build it with `expr` and refer to columns with `col()`. The expression runs in the database, inside the `UPDATE`, so concurrent writers cannot lose each other's changes:

```ts
import { col, expr } from 'turbine-orm';

await db.posts.update({
  where: { id: 1 },
  data: {
    viewCount: expr.add(col('viewCount'), 1),
    peakViews: expr.greatest(col('peakViews'), col('viewCount')),
    tier: expr.case([{ when: { viewCount: { gt: 1000 } }, then: 'hot' }], 'cold'),
    seenAt: expr.now(),
  },
});
```

| Builder | SQL | Notes |
|---|---|---|
| `expr.add(a, b)`, `sub`, `mul`, `div` | `a + b`, `a - b`, `a * b`, `a / b` | Numeric operands only. Between integers (integer numbers and integer columns) it is integer arithmetic on every engine, and `div` truncates toward zero: `75 / 2` is `37`, even when the result goes into a float column. With a non-integer operand it is decimal arithmetic, and writing that result to an integer column throws `TURBINE_E003`. For a decimal half, write `expr.mul(col('n'), 0.5)` into a float column |
| `expr.coalesce(a, b, ...)` | `COALESCE(...)` | 2 to 8 operands |
| `expr.greatest(a, b, ...)`, `expr.least(...)` | `GREATEST(...)`, `LEAST(...)` | 2 to 8 operands. NULLs are ignored on every engine, as on PostgreSQL: the result is NULL only when every operand is |
| `expr.case(arms, otherwise?)` | `CASE WHEN ... THEN ... ELSE ... END` | 1 to 16 arms of `{ when, then }`. `when` is a filter on the row's own columns, written like `where` (no relation filters). The first matching arm wins; without `otherwise` an unmatched row gets NULL |
| `expr.now()` | The server's current time | Temporal columns only. Stored in the zone convention Turbine reads with, so a zone-less `timestamp` gets the UTC wall clock and a `date` column gets the UTC day, SQLite included. On PostgreSQL it is the transaction's start time |
| `expr.excluded('field')` | The incoming row's value | Only in `upsert`'s `update` and `createMany`'s [`onConflict.update`](#multi-row-upsert-onconflict) |
| `expr.secondsBetween(col('a'), col('b'))` | `EXTRACT(EPOCH FROM (b - a))` | The seconds from one timestamp column to another, fractional. Both `timestamptz`, or both zone-less `timestamp`. Valid only in a [percentile's `of`](#percentiles-of-an-expression-of); `TURBINE_E003` in update data |

An operand is a JavaScript value, `col('field')` for the current row's column, or another expression, so expressions nest: `expr.add(col('a'), expr.mul(col('b'), 2))`. A client generated before 0.90 does not type expressions in its update inputs; regenerate it.

Expressions are accepted as the direct value of a field in `update`, `updateMany`, `upsert`'s `update`, nested `update` and `upsert` data, and `onConflict.update`. They throw `ValidationError` (`TURBINE_E003`) in `create` and `createMany` data, inside an operator such as `{ set }`, and on a `json`, `jsonb` or array column.

Only `expr` builds an expression. Each node carries a symbol brand that `JSON.parse` cannot produce, so request data can never become SQL. A plain object shaped like a node (`{ kind: 'add', args: [...] }`) is a value, and on a non-JSON column it throws `TURBINE_E003`.

PostgreSQL, MySQL, SQLite and SQL Server support expressions. PowDB and `turbine-orm/prisma-compat` throw `UnsupportedFeatureError` (`TURBINE_E017`).

<Callout type="note">
Lint rules that ban an object property named `then` (Biome's `noThenProperty`, `unicorn/no-thenable`) flag the `{ when, then }` arms of `expr.case`. Disable the rule for that line.
</Callout>

### `updatedAt` columns

A column tagged [`updatedAt`](/schema#auto-updated-timestamps-updatedat) is stamped by `update`, `updateMany` and both branches of `upsert` that update a row, unless the call names it. An explicit value always wins.

### `optimisticLock`

[`optimisticLock`](/optimistic-locking) is an `update` option. `updateMany` and `upsert` refuse it with `TURBINE_E003` rather than ignore it. On `updateMany`, put `version: expected` in `where` and `version: { increment: 1 }` in `data`. On `upsert`, read the row, then `update` with `optimisticLock` or `create`, inside one `$transaction`.

## delete / deleteMany

```ts
await db.users.delete({ where: { id: 42 } });

await db.users.deleteMany({
  where: { createdAt: { lt: thirtyDaysAgo } },
});
```

`delete` returns the deleted row and takes [`select` / `omit`](#returning-fewer-columns) to narrow it. `deleteMany` returns `{ count }`, and refuses `limit` / `take` / `offset` / `skip` as [`updateMany`](#update--updatemany) does.

Turbine blocks accidental mass deletes. These throw `ValidationError` (`TURBINE_E003`):

- An empty `where`: `{}`, or one whose every value is `undefined`.
- A `where` that is always true and would compile to SQL matching every row: `NOT: { OR: [] }`, `{ id: { notIn: [] } }`, `{ posts: { none: { OR: [] } } }`, or an `OR` with a branch that applies no condition (`OR: [{ id: 1 }, {}]`).
- On a NOT NULL column, a filter every row passes: `contains: ''` (and `startsWith: ''` / `endsWith: ''`), `not: null`, a column compared with itself (`{ equals: col('email') }` on `email`), and `hasEvery: []` on an array column.
- A bare to-one relation filter (`{ author: {} }` or `{ author: { is: {} } }`) over a NOT NULL foreign key. This one is allowed on SQLite, where a row can point at a row that does not exist while the connection's `foreign_keys` pragma is off, and when the target table has a global filter.

Reads with these shapes are unchanged. An always-false `where` (`{ id: { in: [] } }`, `OR: []`) is not refused; it matches nothing.

To write every row on purpose, import the sentinel and pass `allowFullTableScan: UNSAFE`:

```ts
import { UNSAFE } from 'turbine-orm';

await db.sessions.deleteMany({ where: {}, allowFullTableScan: UNSAFE }); // every row
```

`where` itself is still required: `allowFullTableScan` disarms the guard on an empty or always-true `where`, it does not let you drop the key. A list that may be empty (`notIn: excludedIds`) needs a decision: pass `allowFullTableScan: UNSAFE` when every row is meant, or skip the call.

`allowFullTableScan` is a [privilege option](/global-filters#privilege-options-and-the-unsafe-symbol): the `UNSAFE` symbol is the only value that enables it, and `true` throws (`TURBINE_E003`). The option is typed `Unsafe`, so a boolean does not compile; write a conditional call site as `{ where, ...(flag ? { allowFullTableScan: UNSAFE } : {}) }`. All of this applies to `updateMany` too.

## upsert

Updates the row `where` names, or inserts `create` when no row matches. `where` must identify one row, through a unique or primary key column.

```ts
const user = await db.users.upsert({
  where: { email: 'alice@example.com' },
  create: { email: 'alice@example.com', name: 'Alice', orgId: 1 },
  update: { name: 'Alice Updated' },
});
```

Returns the full row (via `RETURNING *`) whether it was inserted or updated, or the columns a [`select` / `omit`](#returning-fewer-columns) asks for.

```ts
// Upsert with a composite key
const membership = await db.memberships.upsert({
  where: { userId: 1, orgId: 2 },
  create: { userId: 1, orgId: 2, role: 'member' },
  update: { role: 'admin' },
});
```

The one-row requirement is checked before any SQL is built and throws the same `TURBINE_E003` as `update` and `delete`. A table with no primary key and no unique constraint gets its own message: no `where` can identify one row there, so use `create` or `updateMany` instead.

### One statement, or a lookup first

When every `where` key has the same value in `create`, as in the examples above, the upsert runs as one atomic `INSERT ... ON CONFLICT ... DO UPDATE`.

Otherwise Turbine looks the row up by `where`, then updates it or inserts `create`, in one transaction (yours, when the call is already inside `$transaction`). A conflict statement cannot answer these calls, because it matches on the values it inserts, which are `create`'s. These shapes take the lookup:

- `where: { id: 5 }` with a `create` that leaves `id` to its sequence.
- `where: { email: a }` with `create: { email: b }`.
- An empty `update: {}`, which reads as "create it if it is missing".
- [Nested writes](/nested-writes) inside `create` or `update`.
- A table with a [global filter](/global-filters) on MySQL or SQL Server, whose conflict statements cannot carry the filter.
- On MySQL, a `create` that also sets another unique key. `ON DUPLICATE KEY UPDATE` updates whichever row a unique key collides on first, which may not be the row `where` names.

Like Prisma's lookup, it is not atomic against a concurrent insert of the same key: two callers can both miss, and the second insert then fails with `UniqueConstraintError` (`TURBINE_E008`).

Both halves are validated before the lookup runs, so a typo in `update` is refused whether or not the row exists. A [batched](#pipeline) `buildUpsert` has no round trip for a lookup, so it refuses these shapes and names the fix: `TURBINE_E017` for the global-filter and MySQL unique-key cases, `TURBINE_E003` for the rest.

## count

Returns the number of rows matching `where`.

```ts
const total = await db.users.count();
const admins = await db.users.count({ where: { role: 'admin' } });
```

## aggregate

```ts
const stats = await db.posts.aggregate({
  where: { orgId: 1 },
  _sum: { viewCount: true },
  _avg: { score: true },
  _max: { createdAt: true },
  _count: true,
});
```

On a PII-tagged column, `_min` / `_max` require `includePii: UNSAFE`;
`_count` and `where` need no opt-in. See [PII fields](#pii-fields-includepii).

Result types depend on the column, here and in [`groupBy`](#groupby):

| Aggregate | Column | Returns |
|---|---|---|
| `_sum` / `_avg` | `int2` / `int4` / `float` | a `number` |
| `_sum` / `_avg` | `int8` / `bigint`, `numeric` / `decimal` | an exact string |
| `_min` / `_max` | any | the stored value, read like a row: an `int8` is a `number` while it is a safe integer and a string above that |

`_sum` and `_avg` follow the column's type because they compute a value no row holds. PostgreSQL returns it as `numeric` text, and `Number()` would round anything past 15 significant digits (a `SUM(bigint)` passes 2^53 easily). That loss could not be undone by a later read, so the text is passed through as is. `_min` / `_max` return one stored cell, so they follow the row rule, decided by the value's size. Over zero matching rows, `_sum` and `_avg` are `null`.

### Percentiles: `_percentile`

`aggregate` and `groupBy` take `_percentile: { field: { p, method? } }`. `p` is a fraction from 0 to 1, or an array of them, and the result mirrors that shape:

```ts
const stats = await db.requests.aggregate({
  _percentile: {
    latencyMs: { p: [0.5, 0.95, 0.99] },
    sizeBytes: { p: 0.5, method: 'disc' },
  },
});
// stats._percentile.latencyMs: [median, p95, p99]
// stats._percentile.sizeBytes: one stored value
```

- **`method: 'cont'`** (the default) interpolates between rows, `percentile_cont`. It needs a numeric or interval column; on a date or time column it throws `TURBINE_E003`, which names `method: 'disc'`.
- **`method: 'disc'`** returns a value that is stored in the column, `percentile_disc`.

Values read the way the column reads: a date column gives `Date`, an interval gives the driver's interval object, and `numeric` stays an exact string. Over zero rows the result is `null`, in both the scalar and the array form. On a PII-tagged column both methods need `includePii: UNSAFE`, as `_min` / `_max` do.

PostgreSQL only; other engines throw `UnsupportedFeatureError` (`TURBINE_E017`). A JSON-path target throws `TURBINE_E003`, and so does ordering groups by `_percentile` or filtering them on it in `having`.

#### Percentiles of an expression: `of`

A key that names no field takes `of`, an [expression](#update-expressions-expr) over the row's columns, and the result comes back under that key:

```ts
import { col, expr } from 'turbine-orm';

const stats = await db.jobs.aggregate({
  where: { kind: 'render' },
  _percentile: {
    wait: { of: expr.secondsBetween(col('requestedAt'), col('readyAt')), p: [0.5, 0.95] },
    costPerTry: { of: expr.div(col('cost'), expr.greatest(col('tries'), 1)), p: 0.9 },
  },
});
// stats._percentile.wait: [median, p95], in seconds
```

- `of` takes `expr.add` / `sub` / `mul` / `div`, `coalesce`, `greatest`, `least`, `case`, and `expr.secondsBetween` for the seconds between two timestamp columns. Bound values are numbers or bigints.
- The expression is ordered as double precision, so both methods return a `number`, or `null` over zero rows.
- Arithmetic is typed by its operands, as in updates: `expr.div` between two integers truncates before the cast. For a fractional result, multiply by a fraction instead: `expr.mul(col('ms'), 0.001)`.
- The key only names the result and never reaches the SQL. A key without `of` must be a field, which the types check, so a misspelled field is a compile error.
- `TURBINE_E003` for a field key with `of`, `col('x')` alone (use the key `x`), a string, `Date` or boolean bound value, a result that is not numeric, `expr.now()` and `expr.excluded()`.
- A PII-tagged column the expression reads as a value needs `includePii: UNSAFE`; a column that only an `expr.case` arm's `when` tests does not.

## groupBy

Groups rows by one or more columns and computes aggregates per group, like SQL `GROUP BY`.

```ts
const postsByUser = await db.posts.groupBy({
  by: ['userId'],
  _count: true,
  _sum: { viewCount: true },
  _avg: { score: true },
});
// [{ userId: 1, _count: 12, _sum: { viewCount: 4800 }, _avg: { score: 4.2 } }, ...]
// If `score` were numeric (or bigint), _avg would be the exact string PostgreSQL
// renders, e.g. _avg: { score: '4.2000000000000000' }; see the type note below.
```

`by` must be a non-empty array of field names. A missing `by`, a string (write `by: ['name']`), an empty array or a `null` entry throws `TURBINE_E003` naming `by`. For one group over every row, use [`aggregate()`](#aggregate).

Grouping by a PII-tagged column, or `_min` / `_max` over one, requires
`includePii: UNSAFE`; `where` / `orderBy` / `having` stay unrestricted. See
[PII fields](#pii-fields-includepii).

The result row is fully typed from the args, no `as const` needed. Each `by` field carries its entity field type, `_count` is a `number`, `_sum` / `_avg` fields are `number | string | null`, and `_min` / `_max` fields carry the field's own type. The call above infers:

```ts
// { userId: number; _count: number;
//   _sum: { viewCount: number | string | null };
//   _avg: { score: number | string | null } }[]
```

The `string` in `_sum` / `_avg` is the exact-value rule described under [`aggregate`](#aggregate): over `int8` / `bigint` and `numeric` / `decimal` columns the value is PostgreSQL's `numeric` text, unrounded. Over `int2` / `int4` / `float` columns it is a `number`.

Grouping by a JSON path yields a runtime alias that cannot be typed, so those columns are left off the row type; cast the result.

### Filtering groups

Pass a `where` clause to filter rows before grouping:

```ts
const activePostsByOrg = await db.posts.groupBy({
  by: ['orgId'],
  where: { published: true },
  _count: true,
  _max: { createdAt: true },
  orderBy: { _count: 'desc' },
});
```

### Multiple group-by columns

```ts
const breakdown = await db.posts.groupBy({
  by: ['orgId', 'published'],
  _count: true,
  _min: { createdAt: true },
  _max: { createdAt: true },
});
```

The aggregates are `_count`, `_sum`, `_avg`, `_min`, `_max` and [`_percentile`](#percentiles-_percentile). When `_count` is `true` or omitted, each group carries `_count`, its row count. The Prisma record form, `_count: { _all: true }`, returns `_count: { _all: n }` instead, and a field key in it (`_count: { _all: true, title: true }`) adds that field's count of non-NULL values.

### Grouping and aggregating over JSON paths

Group keys and aggregate targets can drill into `json` / `jsonb` columns. A group key is `{ field, path, alias? }`; an aggregate target is keyed by its result alias and points at `{ field, path, type? }`:

```ts
const revenueByCategory = await db.orderItems.groupBy({
  by: [{ field: 'data', path: ['category'] }],           // result key: 'category'
  _sum: { price: { field: 'data', path: ['price'] } },    // numeric cast, result key: 'price'
});
```

`_sum` / `_avg` always cast to numeric; `_min` / `_max` compare as text unless you pass `type: 'numeric'`. `having` works on the alias. Two targets that would produce the same result key throw before the query runs.

### Ordering groups

`orderBy` sorts the groups by any column the result contains: a plain `by` column, a JSON group-key alias, or a requested aggregate. Order by `_count` directly, or by `_sum` / `_avg` / `_min` / `_max` keyed by the aggregate field or its JSON alias:

```ts
const topCategories = await db.orderItems.groupBy({
  by: [{ field: 'data', path: ['category'] }],           // result key: 'category'
  _count: true,
  _sum: { price: { field: 'data', path: ['price'] } },    // result key: 'price'
  orderBy: {
    _sum: { price: 'desc' },   // biggest revenue first (by the JSON aggregate)
    category: 'asc',           // tie-break by the group-key alias
  },
});
```

Each key re-emits the SQL expression it selected (the same one `having` uses), so aggregate and JSON-alias ordering works on every engine. Ordering by an aggregate you did not request, or by an unknown key, throws with the list of valid keys. `{ sort, nulls }` specs work here too, on PostgreSQL and SQLite.

### Top N groups: `limit` and `offset`

`groupBy` takes `limit` and `offset`, applied after `ORDER BY`. Pair them with a deterministic `orderBy` for "top N groups" and paginated grouped results:

```ts
// The 10 users with the most posts
const topAuthors = await db.posts.groupBy({
  by: ['userId'],
  _count: true,
  orderBy: { _count: 'desc' },
  limit: 10,
});
```

`limit` / `offset` are parameterized on PostgreSQL, SQLite and SQL Server, inlined on MySQL, and native on PowDB.

### Latest row per parent: `distinctOn`

Aggregate over only the newest row per group of some key (a version store's "latest version per instance") with `distinctOn`. PostgreSQL only:

```ts
const latestByCategory = await db.versions.groupBy({
  distinctOn: { columns: ['instanceId'], orderBy: { createdAt: 'desc' } },
  by: [{ field: 'data', path: ['category'] }],
  _sum: { price: { field: 'data', path: ['price'] } },
});
```

The row source becomes `SELECT DISTINCT ON ("instance_id") ... ORDER BY "instance_id", "created_at" DESC` before grouping, and `where` filters rows before the pick. `distinctOn.orderBy` is required, so the pick is deterministic.

### Filtering groups with HAVING

A `where` clause filters rows *before* grouping. A `having` clause filters the resulting groups *after*. Every comparison value is parameterized.

```ts
// Users with more than one post
const prolific = await db.posts.groupBy({
  by: ['userId'],
  _count: true,
  having: { _count: { gt: 1 } },
});

// Groups whose summed view count clears a threshold
const popular = await db.posts.groupBy({
  by: ['published'],
  _sum: { viewCount: true },
  having: { viewCount: { _sum: { gte: 100 } } },
});
```

Filter on the group's row count with the top-level `_count`, or on a column aggregate with `{ column: { _sum | _avg | _min | _max: { ... } } }`. The aggregate operators are `equals`, `not`, `gt`, `gte`, `lt`, `lte`, `in` and `notIn`; a bare value is shorthand for equality. Several `having` predicates combine with `AND`:

```ts
// Groups with > 1 row AND a summed view count <= 500
const niche = await db.posts.groupBy({
  by: ['userId'],
  _count: true,
  _sum: { viewCount: true },
  having: { _count: { gt: 1 }, viewCount: { _sum: { lte: 500 } } },
});
```

`_min` / `_max` operands are not numeric-only. They return a stored cell, so the operand is the column's own type:

```ts
const lateAlphabetically = await db.posts.groupBy({
  by: ['userId'],
  _min: { title: true },
  having: { title: { _min: { gt: 'm' } } },
});
// ... HAVING MIN("title") > $1
```

Each `_min` / `_max` operand, and each `in` / `notIn` element, binds the way a `where` operand on that column does. So on MySQL a number compared with a text column binds as text.

#### Filtering on the grouped value

A field entry can also filter the grouped value itself, not only an aggregate of it. This is Prisma's `having` shape, and it covers the common "drop the NULL group" case:

```ts
const byType = await db.posts.groupBy({
  by: ['typeId'],
  _count: true,
  having: { typeId: { not: null }, _count: { gt: 1 } },
});
// ... GROUP BY "type_id" HAVING "type_id" IS NOT NULL AND COUNT(*) > $1
```

A bare value is equality shorthand, and both forms may appear in the same object, joined with `AND`:

```ts
await db.posts.groupBy({ by: ['published'], _count: true, having: { published: true } });
// ... HAVING "published" = $1

await db.posts.groupBy({
  by: ['status'],
  _sum: { viewCount: true },
  having: { status: { startsWith: 'pub' }, viewCount: { _sum: { gte: 100 } } },
});
// ... HAVING "status" LIKE $1 ESCAPE '\' AND SUM("view_count") >= $2
```

Scalar predicates compile like `where`, so the whole [WHERE operator](#where-operators) surface is available: `in` / `notIn`, `contains` / `startsWith` / `endsWith` with `mode: 'insensitive'`, JSON and array filters, LIKE escaping, and each engine's own `IN` form. A JSON-path group key works too, keyed by its alias.

<Callout type="warning" title="A scalar filter is only legal on a `by` column">
  `HAVING` can only reference a grouped column, so a scalar filter on anything
  else throws a `ValidationError` (`TURBINE_E003`) naming the column and listing
  the `by` keys. A predicate meant to select **rows** belongs in `where`; one
  meant to select **groups** needs the column in `by`, or an aggregate filter.
</Callout>

#### `AND` / `OR` / `NOT`

Scalar and aggregate predicates combine at any depth:

```ts
const interesting = await db.posts.groupBy({
  by: ['status'],
  _count: true,
  _sum: { viewCount: true },
  having: {
    OR: [
      { _count: { gt: 100 } },
      { AND: [{ status: 'draft' }, { viewCount: { _sum: { gt: 1000 } } }] },
    ],
  },
});
// ... HAVING (COUNT(*) > $1 OR ("status" = $2 AND SUM("view_count") > $3))
```

`AND` and `NOT` take one `having` object or an array of them; `OR` takes an array. The shapes and rules match the [`where` combinators](#combinators).

`HAVING` is emitted after `GROUP BY` and before `ORDER BY`, and its parameters continue the numbering of any `where` parameters.

## findManyStream

Streams rows through an async iterator, nested `with` included. On PostgreSQL it reads through a server-side cursor, in constant memory whatever the result size. SQLite, MySQL and SQL Server load the full result first, then yield it in batches.

```ts
for await (const user of db.users.findManyStream({
  where: { orgId: 1 },
  orderBy: { id: 'asc' },
  batchSize: 1000,       // internal FETCH batch size (default: 1000)
  with: { posts: true }, // nested relations work inside the stream
})) {
  process.stdout.write(`${user.email}\n`);
}
```

With a `batchSize` at or below the default of 1000, the stream first runs a plain query with `LIMIT batchSize + 1`. If the whole result fits in one batch, the rows are yielded directly and the cursor's four round trips (`BEGIN`, `DECLARE`, `CLOSE`, `COMMIT`) are skipped. A larger result switches to a cursor. You can `break` early; the cursor and connection are cleaned up.

A stream honours `limit` / `take` and `offset` / `skip` exactly as `findMany` does, and the first fetch is capped by your `limit` (or the client's `defaultLimit`).

`findManyStreamBatches` takes the same arguments and yields an array of rows per fetch instead of one row at a time. Prefer it when the consumer can work on an array, since it skips a promise resolution per row. A batch is never empty and holds at most `batchSize` rows; do not read meaning into where one batch ends.

```ts
for await (const batch of db.users.findManyStreamBatches({ where: { orgId: 1 }, batchSize: 500 })) {
  await sink.writeAll(batch);
}
```

<Callout type="note" title="Why the speculative fetch stops above batchSize 1000">
  Rows from a failed speculation cannot be reused (they were read outside the
  cursor's transaction), so the cursor re-reads from row one, and the waste
  grows with `batchSize`. Above the default, the stream opens the cursor
  directly. Being wrong then costs four round trips on a result that would
  have fit, never any transferred rows. The [benchmarks](/benchmarks) carry
  the streaming measurements.
</Callout>

### Abandoned streams close themselves

A stream that has opened a cursor holds a connection between pulls. If its consumer asks for nothing for five minutes, Turbine closes it. Otherwise an iterator that is never finished, or a response stream torn down without calling `return()`, would hold a pooled connection forever, and on PostgreSQL an open transaction whose snapshot holds back vacuum. A stream that fit in one batch holds nothing.

On expiry Turbine closes the cursor, releases the connection and logs `stream-idle-timeout`. The next pull, if one comes, throws `TimeoutError` (`TURBINE_E002`, `outcome: 'not-executed'`). Only the time the consumer spends between pulls counts, never the time Turbine spends fetching.

```ts
// Per call: a slow consumer that pauses longer than five minutes between rows
for await (const row of db.events.findManyStream({ idleTimeoutMs: 30 * 60_000 })) {
  await slowSink.write(row);
}

// Per client: streamIdleTimeoutMs, in milliseconds. 0 disables the timeout.
const db = turbine({ connectionString: process.env.DATABASE_URL, streamIdleTimeoutMs: 0 });
```

Both take a whole number of milliseconds; anything else throws `TURBINE_E003`. The per-call option is `idleTimeoutMs`, but on the client that name is the pool's idle-connection timeout, so the client-level stream setting is `streamIdleTimeoutMs`. A stream inside `$transaction` is not watched: it rides the transaction's connection, and the transaction's own timeout bounds it.

On PostgreSQL the stream's transaction also sets `idle_in_transaction_session_timeout` to the idle timeout plus 10 seconds. It is transaction-local, never a session `SET`, and a stricter limit already in force is kept. So a process that stops running timers, such as a serverless instance frozen between invocations, cannot hold the transaction open either; its next pull throws `ConnectionError` (`TURBINE_E004`). While the stream is live, Turbine sends `SELECT 1` whenever half the timeout passes with no statement, so a consumer slowly reading a fetched batch never looks idle to the server. The server limit fires only when timers cannot run.

## WHERE operators

Every operator composes freely with `AND`, `OR`, `NOT` and relation filters.

### Misspelled keys are a compile error

On a generated, typed client, an unknown key in `where` does not compile:

```ts
// Compile error: "emial" does not exist on the where clause.
await db.users.findMany({ where: { emial: 'a@b.com' } });
```

The check follows the clause everywhere it nests:

```ts
await db.users.findMany({
  where: {
    OR: [
      { emial: 'a@b.com' },              // error, inside OR
      { posts: { some: { titel: 'x' } } }, // error, inside a relation filter
    ],
  },
  with: {
    posts: { where: { titel: 'x' } },     // error, inside a with block
  },
});
```

It needs no regeneration and changes no SQL: it is type-level only, built on the relation types your generated client already carries. The same check covers `orderBy`, a `with` block's `select` / `omit`, and the `build*` methods.

**Where keys stay open.** These still compile with any key:

| Still open-keyed | Why |
|---|---|
| Clients with no relations map | `defineSchema`-only clients and `client.table(name)` have no relation type to check against, so `where` and `orderBy` accept any key. Top-level `select` / `omit` are still checked |
| Legacy generated clients whose `*Relations` members are bare types rather than brands | The relation **key** is checked; its **value** is not |

Because this is a type-level check, `tsx` and other transpile-only runners will not catch it. Run `tsc --noEmit` in CI.

### Operands must fit the column

Every operand is checked against its column at runtime, on the first build and on every cache hit. On a non-JSON column a value position (a bare value, `equals`, `not`, `gt`, `gte`, `lt`, `lte`) takes a string, number, `bigint`, boolean, `Date`, `Buffer` or typed array, `null` where it means something, or a [column reference](#column-to-column-comparison). Everything else throws `ValidationError` (`TURBINE_E003`):

| Shape | Use instead |
|---|---|
| an object or array as a value: `{ id: [1, 2] }` | `{ id: { in: [1, 2] } }` |
| `gt` / `gte` / `lt` / `lte: null` | `equals: null` or `not: null` |
| a non-string `contains` / `startsWith` / `endsWith` | a string |
| a non-array `in` / `notIn`, or an element that is not a scalar | an array of values |
| an empty operator object as written: `{ id: {} }` | a value or an operator |
| an operator object naming no operator: `{ name: { mode: 'insensitive' } }` | add one, `{ contains: 'x', mode: 'insensitive' }` |
| a `distinct` element that is not a field-name string | `distinct: ['email']` |
| a `Map`, `Set`, `Promise`, `RegExp` or `Error` | a scalar |
| `mode` other than `'insensitive'` or `'default'` | one of those |

A class instance that renders itself (`toPostgres`, `toJSON`, or its own `toString`, as decimal libraries do) is accepted as a scalar.

### `undefined` means absent

A key whose value is `undefined` is removed before the query is built. That holds at every depth of `where` (inside `AND` / `OR` / `NOT`, relation filters and `with` wheres), and in `having`, `cursor` and `orderBy`. An object that becomes empty this way is removed too, so `{ user: { email: undefined } }` is no filter at all, and an optional search box needs no special casing:

```ts
// search may be undefined: no title predicate, and the same cached SQL as omitting it
await db.posts.findMany({ where: { orgId, title: { contains: search, mode: 'insensitive' } } });
```

What an emptied `where` then means depends on the method:

- `findMany` and `count` return every row, as with no `where`.
- `findFirst` / `findFirstOrThrow` throw `TURBINE_E003`, so a missing value cannot turn a lookup into "any row".
- Mutations refuse it through the [empty-where guard](#delete--deletemany), including one emptied inside a relation filter: `deleteMany({ where: { user: { email: undefined } } })` throws. The same guard refuses a `where` that is always true, such as `NOT: { OR: [] }`.

An object you write empty is left as written and keeps its own rule (`{ id: {} }` throws, `where: {}` is "no filter" on a read). `data` is pruned differently: a top-level `undefined` field is skipped, and an emptied object stays, because `{}` is a legitimate JSON value.

### Equality

| Operator | Description | Example |
|---|---|---|
| literal | Implicit equality | `where: { email: 'a@b.com' }` |
| `equals` | Explicit equality | `where: { email: { equals: 'a@b.com' } }` |
| `not` | Inequality (or `not: null` for `IS NOT NULL`) | `where: { role: { not: 'admin' } }` |
| `not: { ... }` | Negates an operator object: `NOT (<inner>)` | `where: { title: { not: { contains: 'draft' } } }` |

`not` with an operator object negates it, as in Prisma: `{ not: { lt: 4 } }` compiles to `NOT ("score" < $1)`, and an outer `mode` applies inside. A row whose column is `NULL` matches neither the filter nor its negation (SQL three-valued logic), so add `{ score: null }` under an `OR` if you want those rows.

### Sets

| Operator | Description | Example |
|---|---|---|
| `in` | Match any value in the array | `where: { id: { in: [1, 2, 3] } }` |
| `notIn` | Match none of the values | `where: { role: { notIn: ['banned', 'spam'] } }` |

On every engine, `in` / `notIn` match exactly the rows `equals` / `not` would match for each element, whatever the column type. `mode: 'insensitive'` works on them too, on PostgreSQL and PowDB only; see [String](#string).

Engine limits:

- **MySQL** binds each element as its own placeholder. A list that takes the statement past MySQL's 65,535 placeholders throws `TURBINE_E003`; split it across several queries.
- **SQL Server** takes `bigint` and `Date` elements, and refuses a binary element with `TURBINE_E017`; write that list as `OR` branches.
- **SQLite** takes a `bigint` past 2^53 and binary values in a list.

On MySQL a number or boolean compared with a text column binds as text, so `{ resetToken: 0 }` matches only the text `'0'`.

### Comparison

| Operator | Description | Example |
|---|---|---|
| `gt` | Greater than | `where: { score: { gt: 100 } }` |
| `gte` | Greater than or equal | `where: { score: { gte: 100 } }` |
| `lt` | Less than | `where: { score: { lt: 100 } }` |
| `lte` | Less than or equal | `where: { score: { lte: 100 } }` |

### String

| Operator | Description | Example |
|---|---|---|
| `contains` | Substring match (`LIKE %v%`) | `where: { title: { contains: 'sql' } }` |
| `startsWith` | Prefix match (`LIKE v%`) | `where: { email: { startsWith: 'admin@' } }` |
| `endsWith` | Suffix match (`LIKE %v`) | `where: { email: { endsWith: '@acme.com' } }` |
| `mode: 'insensitive'` | Case-insensitive match. On `contains` / `startsWith` / `endsWith` the `LIKE` becomes `ILIKE` (or the engine's equivalent); on `equals`, `not`, `in` and `notIn` both sides are folded with `LOWER(...)`, so `{ equals: 'ada', mode: 'insensitive' }` matches `Ada` | `where: { title: { contains: 'SQL', mode: 'insensitive' } }` |

LIKE wildcards in user input (`%`, `_`, `\`) are escaped automatically.

Rules for `mode`:

- It lives in the operator object, so a bare string has nowhere to carry it: `{ name: 'ada', mode: 'insensitive' }` is an unknown field.
- String columns only. `mode` beside a non-string operand throws `TURBINE_E003`.
- **On `in` / `notIn` it is PostgreSQL-only among the SQL engines.** The fold must be the same function on the column and on every list element, and of the four SQL dialects only PostgreSQL's list form can lower each element in SQL. Folding the list in JavaScript instead would make `equals` and `in` return different rows for the same operand, since no engine's `LOWER` is JavaScript's. So SQLite, MySQL and SQL Server throw `TURBINE_E017` rather than answer wrongly. PowDB supports it: PowQL's list form takes an expression per element, so the same `lower(...)` applies to the column and to every operand. On the refusing engines, write the list as branches: `{ OR: [{ f: { equals: a, mode: 'insensitive' } }, ...] }`.
- **A plain btree index cannot serve the folded comparison**, so a hot equality lookup that was an index scan becomes a sequential scan once you add `mode`. Add `CREATE INDEX ... ON t (LOWER(col))`, or make the column `citext`.

### Array columns

| Operator | Description | Example |
|---|---|---|
| `has` | Array contains element | `where: { tags: { has: 'sql' } }` |
| `hasEvery` | Array contains every element | `where: { tags: { hasEvery: ['sql', 'pg'] } }` |
| `hasSome` | Array contains at least one element | `where: { tags: { hasSome: ['sql', 'mysql'] } }` |

### Full-text search

| Operator | Description | Example |
|---|---|---|
| `search` | `to_tsvector(col) @@ to_tsquery(query)` | `where: { body: { search: 'postgres & orm' } }` |
| `config` | Text search configuration (default `'english'`) | `where: { body: { search: 'orm', config: 'simple' } }` |

The query string is bound as a parameter and uses `to_tsquery` syntax (`&`, `|`, `!`, `<->`). The `config` name is validated (letters, digits and underscore only) before it reaches the SQL.

### JSON columns (`json` / `jsonb`)

Filter into a JSON document with a `JsonFilter`. `path` drills into nested keys before the test runs; the other keys pick the comparison.

| Operator | Description | Example |
|---|---|---|
| `path` | Drill into nested keys before applying the test | `where: { data: { path: ['meta', 'tier'], equals: 'pro' } }` |
| `equals` with `path` | The JSON value at `path` equals the operand, compared as JSON | `where: { data: { path: ['tier'], equals: 'pro' } }` |
| `equals` without `path` | The whole document equals the operand exactly | `where: { data: { equals: { tier: 'pro' } } }` |
| `contains` | jsonb containment (`@>`): the document holds the operand, maybe among other keys | `where: { data: { contains: { active: true } } }` |
| `hasKey` | Top-level key exists (`?`) | `where: { data: { hasKey: 'meta' } }` |
| `gt` / `gte` / `lt` / `lte` | Range-compare the value at `path` | `where: { data: { path: ['rating'], gte: 4 } }` |
| `stringContains` | Substring match on the text at `path` | `where: { data: { path: ['title'], stringContains: 'orm' } }` |
| `stringStartsWith` / `stringEndsWith` | Prefix / suffix match on the text at `path` | `where: { data: { path: ['slug'], stringStartsWith: 'v2-' } }` |
| `mode` | `'insensitive'` for the three substring operators | `where: { data: { path: ['title'], stringContains: 'ORM', mode: 'insensitive' } }` |

The range operators (`gt` / `gte` / `lt` / `lte`) require `path`. A numeric value casts the extracted text, `(col #>> path)::numeric >= $n`, while a string value compares as text:

```ts
// Products rated 4 or higher, read out of a jsonb column
const topRated = await db.products.findMany({
  where: { data: { path: ['rating'], gte: 4 } },
});
```

> **Note:** A bare `{ gt: 5 }` with no `path` on a jsonb column is the plain column comparison, not a JSON test. Use `path` whenever you mean "the value inside the document."

`stringContains`, `stringStartsWith` and `stringEndsWith` are the JSON versions of `contains`, `startsWith` and `endsWith`, and all three require `path`. They have their own names because on a JSON column `contains` already means whole-document containment (`@>`). The operand is LIKE-escaped, so `%` and `_` match literally.

```ts
// Rows whose jsonb `title` contains "orm", case-insensitively
const matches = await db.docs.findMany({
  where: { data: { path: ['title'], stringContains: 'orm', mode: 'insensitive' } },
});
```

<Callout type="warning">
**Unknown JSON operators are refused.** A key that is not in the table above, and a `path` with no comparison at all, throw `ValidationError` (`TURBINE_E003`). Prisma's spelling `string_contains` is the common way to hit it; the error names the Turbine operator to use instead.
</Callout>

#### `equals` compares JSON values

`equals` compares JSON to JSON, so the operand's JSON type matters:

```ts
// Stored: { n: 5 }, { n: "5" }, { n: null }, and {}
where: { data: { path: ['n'], equals: 5 } }     // only { n: 5 }
where: { data: { path: ['n'], equals: '5' } }   // only { n: "5" }
where: { data: { path: ['n'], equals: null } }  // only { n: null }: a missing key is not JSON null
```

On PostgreSQL the path form compiles to `(col #> $1::text[])::jsonb = $2::jsonb` and binds the operand as JSON text (a `Date` as its ISO string, a `bigint` as a JSON number). MySQL compares `JSON_EXTRACT(col, path) = CAST(? AS JSON)`. Arrays and objects at a path compare as JSON on both. A function, a symbol, a column reference or a non-finite number throws `TURBINE_E003`.

Without a `path`, `equals` is exact equality of the whole document: `"col"::jsonb = $1::jsonb` on PostgreSQL (key order and whitespace do not matter, and a `json` column works too), `col = CAST(? AS JSON)` on MySQL. `{ equals: { plan: 'pro' } }` does **not** match `{ plan: 'pro', seats: 5 }`; use `contains` for that. On MySQL a bare document in a `where` (`{ data: { a: 1 } }`) is compared as a document too.

On PostgreSQL and MySQL, `not: <document>` and `not: { equals: <document> }` mean "not this document". A `not` whose object has only filter-operator keys (`not: { gt: 1 }`, `not: { path: ['a'], equals: 1 }`) throws `TURBINE_E003`, because it would be compared as the literal document `{"gt":1}` and match nearly every row. Write `NOT: { data: { ... } }` to negate a filter, or `not: jsonValue({ gt: 1 })` to compare against a document with those keys.

The other engines cannot compare every shape exactly. They refuse what they cannot compare with `UnsupportedFeatureError` (`TURBINE_E017`) rather than approximate it:

| Engine | Path `equals` | Pathless `equals` |
|---|---|---|
| PostgreSQL, MySQL | every JSON value | exact document equality |
| SQL Server | numbers compare as numbers, strings case-sensitively; arrays and objects `E017` | `E017` |
| SQLite | numbers and strings; `null`, arrays, objects and booleans `E017` (SQLite extracts `true` as `1`) | `E017` |

SQL Server, SQLite and PowDB also refuse a bare document as the value (`{ data: { a: 1 } }`) and `not: <document>` with `TURBINE_E017`, as they refuse a pathless `equals`. On MySQL, SQLite and SQL Server, a path key may hold a backslash, a quote or a newline: it is written as a JSON string literal, so it finds its value.

JSON `equals` changed in 0.90; see [Upgrading to 0.90](/upgrading-to-0-90#pathless-json-equals-compares-the-whole-document).

### Column-to-column comparison

Compare a column against another column of the same table by passing `col('field')` to `equals`, `not`, `gt`, `gte`, `lt` or `lte`. The referenced column is compiled into the SQL; no value is bound:

```ts
import { col } from 'turbine-orm';

// Instances whose published version lags behind the draft
const stale = await db.modelInstances.findMany({
  where: { currentVersionId: { not: col('publishedVersionId') } },
});
// → WHERE "current_version_id" != "published_version_id"
```

`col()` returns a frozen reference carrying a symbol brand. A plain `{ col: 'field' }` object is **not** a reference: it is exactly what `JSON.parse` produces from a request body, so it throws `ValidationError` (`TURBINE_E003`) naming `col()`, and it does not typecheck. Request data therefore cannot name a column.

An unknown referenced field throws `ValidationError` (`TURBINE_E003`), and `mode: 'insensitive'` cannot be combined with a column reference. A reference never identifies a row for `findUnique` / `update` / `delete`. On `json` / `jsonb` columns an object operand is always a JSON value, never a column reference; use `path` filters for JSON tests.

### Ordering by a JSON path

`orderBy` accepts a JSON-path spec on `json` / `jsonb` columns. Pass `type: 'numeric'` to sort numerically; the default compares the extracted value as text:

```ts
const byWeight = await db.blocks.findMany({
  orderBy: { data: { path: ['weight'], direction: 'asc', type: 'numeric' } },
});
// → ORDER BY ("data" #>> $1::text[])::numeric ASC NULLS LAST
```

It works at the top level and inside a `with` relation's `orderBy`. Rows whose document lacks the path sort last in both directions by default, on every engine; pass `nulls: 'first' | 'last'` to override (PostgreSQL and SQLite).

### Ordering by a value from one related row

Order parents by a column, or a JSON path, taken from one row of a to-many relation, chosen by `pick`. The classic shape is "sort by a field inside the newest related row":

```ts
const instances = await db.modelInstances.findMany({
  orderBy: {
    versions: {
      pick: { orderBy: { createdAt: 'desc' } },   // which related row: newest
      by: { field: 'data', path: ['title'] },      // value from that row (or by: 'title' for a plain column)
      direction: 'asc',
    },
  },
});
```

- `pick.orderBy` is required, so the choice is deterministic. `pick.where` filters the related rows first.
- It compiles to a correlated scalar subquery in `ORDER BY`, so it works with both relation-load strategies and the SQL cache.
- Parents with no related rows sort last unless you pass `nulls`.
- `hasMany` relations only, in a query's top-level `orderBy` only (inside a `with` block it throws `TURBINE_E003`), and not combinable with `distinct`.
- Built for PostgreSQL; a plain-column `by` also works on SQLite, MySQL and SQL Server.

**Choosing the plan (`plan: 'lateral'`).** By default the pick compiles as a correlated scalar subquery (`plan: 'subquery'`). On PostgreSQL you can opt into a `LEFT JOIN LATERAL (... LIMIT 1) ON true` instead, which can be faster on large parent sets where the ordering subquery dominates the plan:

```ts
orderBy: {
  versions: {
    pick: { orderBy: { createdAt: 'desc' } },
    by: { field: 'data', path: ['title'] },
    direction: 'asc',
    plan: 'lateral',   // PostgreSQL only; identical results to the default
  },
}
```

The results are identical to the default plan; measure both to decide. The lateral plan is PostgreSQL only and throws on the other engines rather than falling back. It is set per ordering entry, so a query with two picks can mix plans.

### Relation filters

Filter parent rows by predicates on their child rows.

| Operator | Description | Example |
|---|---|---|
| `some` | At least one related row matches | `where: { posts: { some: { published: true } } }` |
| `every` | Every related row matches | `where: { posts: { every: { published: true } } }` |
| `none` | No related row matches | `where: { posts: { none: { published: false } } }` |

Any operator above, JSON filters included, works inside `some` / `every` / `none`. A relation filter takes only `some`, `every`, `none`, `is` and `isNot`, or on a to-one relation a bare where object. Any other key beside them throws `TURBINE_E003` naming it.

- `some`, `every` and `none` take a where object. `null`, a scalar or an array throws `TURBINE_E003` at any depth, global filters and `with` wheres included. Write `some: {}` for "has a related row" and `none: {}` for "has none".
- On a to-one relation, `is` / `isNot` take a where object or `null`; a scalar or an array throws `TURBINE_E003`. `some` / `every` / `none` work on a to-one relation too.
- `is` / `isNot` on a to-many relation throws `TURBINE_E003` naming `some` / `every` / `none`.

```ts
// Users who own at least one product rated 4+
const users = await db.users.findMany({
  where: { products: { some: { data: { path: ['rating'], gte: 4 } } } },
});
```

### Combinators

```ts
where: {
  AND: [{ orgId: 1 }, { role: 'admin' }],
  OR: [{ role: 'owner' }, { role: 'admin' }],
  NOT: { deletedAt: { not: null } },
}
```

`OR` takes an array of where objects. `AND` and `NOT` take one where object or an array of them, and `NOT: [a, b]` means `NOT a AND NOT b`. Anything else in a combinator position (an object for `OR`, `null`, a scalar, an array member that is not an object) throws `ValidationError` ([`TURBINE_E003`](/errors#e003)) naming the fix.

**`OR: []` matches no row**, as in Prisma. `AND: []`, `NOT: {}` and `NOT: []` add no predicate. So a list built from user selections needs a decision about zero selections:

```ts
const picked = selectedRoles.map((role) => ({ role }));
const rows = await db.users.findMany({
  // Zero selections now return no users. Leave OR out to mean "any role".
  where: picked.length > 0 ? { OR: picked } : {},
});
```

The same rules hold in a `groupBy` `having`: `NOT: [a, b]` is `NOT a AND NOT b`, and `NOT: { AND: [a, b] }` is `NOT (a AND b)`.

## Nested `with`

Relations in a `with` clause accept their own `where`, `orderBy`, `limit` / `take`, `offset` / `skip`, `select` / `omit`, and nested `with`.

```ts
const users = await db.users.findMany({
  with: {
    posts: {
      where: { published: true },
      orderBy: { createdAt: 'desc' },
      limit: 10,
      select: { id: true, title: true, createdAt: true },
      with: {
        comments: {
          where: { deletedAt: null },
          orderBy: { createdAt: 'asc' },
          limit: 50,
        },
      },
    },
  },
});
```

Nesting depth is capped at 10; deeper, Turbine throws `CircularRelationError` (`TURBINE_E007`) with the full relation path.

Pagination inside `with` applies **per parent**: `limit: 5, offset: 5` returns posts 6 to 10 of each user. `take` and `skip` work as at the top level, including the refusal of two different values for one bound. It works on the `join` and `batched` strategies alike, and on every engine. `offset` / `skip` on a to-one relation (`belongsTo`, `hasOne`) throws `TURBINE_E003`, since there is nothing to skip.

### Counting related rows, `_count`

Add `_count` to a `with` clause to get the number of related rows without loading them, assembled into a `_count` object on each row:

```ts
// Count every to-many relation of the table
const users = await db.users.findMany({
  with: { _count: true },
});
users[0]._count; // { posts: 12, orgs: 3 }

// Count only the named relations
const authors = await db.users.findMany({
  with: { _count: { posts: true } },
});
authors[0]._count.posts; // 12
```

With `relationLoadStrategy: 'join'`, each counted relation is an inline correlated `COUNT(*)` subquery in the same statement. Under the `'auto'` default, a count whose correlation column has no covering index moves to one grouped `COUNT(*) ... GROUP BY fk` follow-up statement, unless the query is bounded at a single row. The numbers are the same either way; see the [load-strategy rules](/relations#load-strategy-auto-join-batched-flatten).

`_count` coexists with real relation subqueries: `with: { posts: true, _count: { posts: true } }` loads the posts *and* counts them. It applies to `hasMany` and `manyToMany` (through the junction) relations. On a to-one relation it throws `ValidationError` (`TURBINE_E003`), and an unknown relation throws `RelationError` (`TURBINE_E005`). The result type carries `_count` as `{ [relation]: number }`, so `users[0]._count.posts` is typed.

## Transactions

```ts
await db.$transaction(async (tx) => {
  const user = await tx.users.create({
    data: { email: 'new@example.com', name: 'New', orgId: 1 },
  });
  await tx.posts.create({
    data: { userId: user.id, orgId: 1, title: 'Hello', content: '...' },
  });
});
```

`tx` has the same typed table accessors as `db`. A nested `$transaction` call creates a SAVEPOINT. A `tx` used after its transaction settled throws `TURBINE_E003`. A transaction PostgreSQL rolled back (a statement failed and the callback caught the error) rejects instead of reporting a commit. The [Transactions](/transactions) page has the full rules, including `readOnly` and `sessionContext`.

### Isolation levels + timeout

```ts
await db.$transaction(
  async (tx) => {
    // ...
  },
  {
    isolationLevel: 'Serializable',
    timeout: 5000, // ms; on expiry the transaction is rolled back
  },
);
```

Isolation levels: `'ReadUncommitted'`, `'ReadCommitted'`, `'RepeatableRead'`, `'Serializable'`. The name is case-sensitive, and any other value throws `ValidationError` (`TURBINE_E003`).

## Pipeline

Runs independent queries in one database round trip, using PostgreSQL's extended-query pipeline protocol.

```ts
const [user, postCount, recentPosts] = await db.pipeline([
  db.users.buildFindUnique({ where: { id: 1 } }),
  db.posts.buildCount({ where: { orgId: 1 } }),
  db.posts.buildFindMany({ where: { userId: 1 }, limit: 5 }),
]);
```

The `build*` methods return `DeferredQuery` objects (generated SQL, params and a transform) without executing. `pipeline()` takes them as an array or as separate arguments, sends every statement in one TCP flush (parse/bind/execute/sync) and runs each transform on its result.

### Non-transactional pipelines

By default a pipeline runs inside a transaction: any failure rolls back the batch, and so does a transform that rejects its result (an `*OrThrow` miss, an optimistic-lock conflict). A batch that may write therefore takes two round trips, holding its `COMMIT` until every result is checked; a read-only batch takes one. Opt out for error-isolated execution:

```ts
try {
  await db.pipeline(queries, { transactional: false });
} catch (err) {
  if (err instanceof PipelineError) {
    // err.results is a per-query [{status:'ok', value} | {status:'error', error}] array
    // err.failedIndex / err.failedTag identify the first failure
  }
}
```

HTTP and serverless pools that don't support the pipeline protocol fall back to sequential execution. Check at runtime with `db.pipelineSupported()`.

### The full `build*` set

Every query method has a `build*` twin that returns a `DeferredQuery` (`{ sql, params, transform, tag }`) instead of running. There are fifteen, writes included:

| Read | Write |
|---|---|
| `buildFindMany` | `buildCreate` |
| `buildFindUnique` | `buildCreateMany` |
| `buildFindFirst` | `buildUpdate` |
| `buildFindUniqueOrThrow` | `buildUpdateMany` |
| `buildFindFirstOrThrow` | `buildUpsert` |
| `buildCount` | `buildDelete` |
| `buildAggregate` | `buildDeleteMany` |
| `buildGroupBy` | |

Pair them with the array form of `$transaction` when the batch must be atomic:

```ts
// One connection, one BEGIN/COMMIT, all-or-nothing
const [order, items, user] = await db.$transaction([
  db.orders.buildCreate({ data: { userId: 1, total: 4200 } }),
  db.orderItems.buildCreateMany({
    data: [
      { orderId: 1, sku: 'A' },
      { orderId: 1, sku: 'B' },
    ],
  }),
  db.users.buildUpdate({ where: { id: 1 }, data: { orderCount: { increment: 1 } } }),
]);
```

Choosing between the two: `db.pipeline(...)` is for **independent** queries, in one round trip. `db.$transaction([...])` is a real transaction on one connection, sequential unless the driver advertises `supportsPipelining`, and rolls the whole batch back on the first failure.

<Callout type="note" title="Nested writes have no build* twin">
  A `create` or `update` whose `data` contains relation operations opens its own
  transaction to resolve the tree, so it cannot be reduced to a single deferred
  statement. Those calls stay `async` and cannot be batched.
</Callout>

## Client configuration

`TurbineConfig` is the object you pass to `turbine()` / `new TurbineClient()`. The connection fields (`connectionString`, `host`, `port`, `database`, `user`, `password`, `ssl`, `pool`) are covered in [Quick Start](/quickstart) and [Serverless](/serverless). The tuning options:

```ts
const db = turbine({
  connectionString: process.env.DATABASE_URL,
  poolSize: 10,
  idleTimeoutMs: 30_000,
  connectionTimeoutMs: 5_000,
  preparedStatements: true,
  sqlCache: true,
  sqlCacheSize: 1000,
  // Postgres only, opt-in. Unset by default, and Turbine then sends nothing.
  // planCacheMode: 'force_custom_plan',
});
```

| Option | Default | What it does |
|---|---|---|
| `poolSize` | `10` | Maximum pooled connections. pg-style alias: `max`. |
| `idleTimeoutMs` | `30000` | Close a pooled connection after this long idle. pg-style alias: `idleTimeoutMillis`. |
| `connectionTimeoutMs` | `5000` | Give up acquiring a connection after this long, with a `ConnectionError` (`TURBINE_E004`) naming the pool size and the usual cause. pg-style alias: `connectionTimeoutMillis`. |
| `preparedStatements` | `true` for Turbine-owned pools; `false` for external pools and for a connection that names a pooler | Send queries as `{ name, text, values }` so Postgres caches the parse and plan per backend connection. A connection string, `host` or `port` that names a pooler (a `pooler` or `pgbouncer` host, or port 6432 or 6543) defaults to `false`. An explicit `true` there is honored, with a warning printed once per process in every mode. |
| `statementTimeoutMs` | unset (Turbine sends nothing) | **Postgres only.** A server-side ceiling (`statement_timeout`), in milliseconds, on every statement this client's connections run. A statement that runs longer is cancelled by the server and rejects with `TimeoutError` (`outcome: 'not-executed'`). It also bounds what a per-query `timeout` cannot reach, such as a stream's `FETCH`. Sent as a connection parameter on pools Turbine opens, never as a `SET`. `0` disables a timeout the server or role would apply. Must be a non-negative whole number (`TURBINE_E003`); `TURBINE_E017` on other engines. A no-op on an external pool, with a warning printed once per process. A pooler may refuse connection parameters; set it on the role there (`ALTER ROLE app SET statement_timeout = '30s'`). |
| `streamIdleTimeoutMs` | `300000` (five minutes) | Close a cursor stream whose consumer has asked for nothing for this long, and release its connection. `0` disables. A stream call's `idleTimeoutMs` overrides it. See [Abandoned streams close themselves](#abandoned-streams-close-themselves). |
| `sqlComment` | unset | Append [sqlcommenter](/observability#sql-comments-sqlcomment) key/values (static pairs, the model and method, the `$tag` label, per-statement values) to every statement a model call sends. |
| `maxLifetimeSeconds` | `1800` on pools Turbine opens | Close a pooled connection once it is this old, when it is next idle, and open a fresh one on demand. Bounds what a long-lived server session accumulates, and moves connections to a new server after a failover. A checked-out connection is never closed under its holder. `0` keeps connections indefinitely. Ignored on an external pool, with a warning printed once per process. |
| `sqlCache` | `true` | The per-table SQL template cache. `false` turns it off. |
| `sqlCacheSize` | `1000` | How many distinct query shapes each table's LRU keeps. Values are parameterized, so they never fragment the cache. `0` is equivalent to `sqlCache: false`; a negative value falls back to the default. |
| `implicitPkOrdering` | `false` | Order a paginating `findMany` that declares no `orderBy` by the primary key ascending, making its pages [deterministic](#deterministic-pages-the-unordered-pagination-warning). An explicit `orderBy` wins; PK-less tables and `distinct` shapes are untouched. A `cursor` page is [always ordered](#pagination-limit--take-offset--skip-cursor), with or without the flag. |
| `planCacheMode` | unset (Turbine sends nothing) | **Postgres only.** Pin `plan_cache_mode` on every connection this client opens: `'auto'`, `'force_custom_plan'`, `'force_generic_plan'`. The remedy for [the generic-plan cliff](/relations#the-generic-plan-cliff-plancachemode). Any other value throws `ValidationError` at construction; a non-Postgres engine throws `UnsupportedFeatureError` (`TURBINE_E017`). |
| `utcTimestamps` | `true` | Read and write zone-less `timestamp` / `date` columns as UTC rather than in the process's local zone. Process-wide, not per client. See [Zone-less columns](/schema#zone-less-columns-timestamp-and-date-read-as-utc). |
| `temporalInfinity` | `'preserve'` | How a Postgres temporal `infinity` / `-infinity` comes back: `'preserve'` (the round-trip-safe JS numbers `Infinity` / `-Infinity`, so `.toISOString()` throws on those rows) or `'null'` (serializes cleanly, but indistinguishable from a stored `NULL`). Leaving it unset selects `'preserve'` and logs a one-time warning the first time a stored infinity is read. See [`infinity` and `-infinity`](/schema#infinity-and--infinity). |
| `logger` | `console` | Where Turbine's log lines go: an object with optional `debug`, `info`, `warn` and `error` methods, each called with `(message, entry)`. `{}` silences Turbine. See [Log output](/observability#log-output-logger). |
| `diagnostics` | from `NODE_ENV`, read at construction | `'development'` or `'production'`, or an object overriding `advice` and `cacheCheck`. Decides per-query advice and the SQL-cache self-check. See [Diagnostics](/observability#diagnostics-diagnostics). |
| `autoToOneJoinMaxRows` | `1000` | Parent-row ceiling for the [`'auto'` strategy's to-one rule](/relations#load-strategy-auto-join-batched-flatten). A `belongsTo` / `hasOne` include stays in the single-statement join when the query's `limit` bounds the parent set at or under this value, and loads batched when the query is unbounded or bounded above it. Only read under `'auto'`. |

Where a pg-style alias exists, the Turbine name wins when both are set.

`planCacheMode` is a connection parameter, so it cannot say *custom here, `auto` there*. The read arg `forceCustomPlan: true` covers that case: on `findMany` / `findUnique` / `findFirst` / `count` / `aggregate` / `groupBy` it sends that one statement unnamed, so it is planned with the real values on every execution. [The per-query lever](/relations#a-per-query-lever-forcecustomplan) has the mechanics and refusal rules.

### Unknown options warn

Every key on the config object is checked against the config surface. An unrecognized one logs a one-time warning with the nearest real option:

```txt
[turbine] Unknown option "logParams" in the config passed to TurbineClient, it is ignored. Did you mean "logQueryParams"?
```

The suggestion covers plain typos and a guess that leaves out a whole word (`logParams` names the same words as `logQueryParams`). It is a warning, never an error, so an app that passes an option from a newer Turbine keeps running. It fires once per key name per process, in production too, through the client's [`logger`](/observability#log-output-logger) with code `unknown-config-key`. `url` and `schema` never warn, because `turbine.config.*` files carry both for the CLI.

<Callout type="note" title="planCacheMode: when a query gets slower on its sixth execution">
  PostgreSQL switches a **named** prepared statement to a generic plan after
  five executions, and a generic plan is costed without the bound values. A
  predicate whose selectivity swings per value (a `tenant_id` equality on a
  shared table) gets planned for the average value and never reverts.
  `planCacheMode: 'force_custom_plan'` re-plans every execution and removes
  that cliff. Deep `limit` / `offset` pagination is the other common case:
  both are bound as parameters, so a generic plan cannot know the offset is
  deep, and per-query `forceCustomPlan: true` is the narrower fix there.

  Reach for it after measuring, not on principle. [The generic-plan
  cliff](/relations#the-generic-plan-cliff-plancachemode) has the mechanics,
  the diagnosis steps, a before/after and the scope limits; the
  [benchmarks page](/benchmarks) carries the numbers.
</Callout>

<Callout type="warning" title="preparedStatements behind a connection pooler">
  A named statement is prepared on **one backend connection**. Behind a
  transaction-pooling proxy (PgBouncer in `transaction` mode, Supabase's pooler
  port, some serverless poolers) your next query can land on a different
  backend and fail with `prepared statement "..." does not exist`, surfaced as
  `ConnectionError` (`TURBINE_E004`, `sqlstate` 42P05 or 26000).

  That is why the default is `false` for external pools and for a
  Turbine-owned pool whose connection names a pooler (a `pooler` or
  `pgbouncer` host, or port 6432 or 6543). For a pooler Turbine cannot
  recognize, set `preparedStatements: false` yourself, or set
  `TURBINE_DISABLE_PREPARED=1` in a deployment you cannot rebuild. If your
  pooler tracks prepared statements (PgBouncer 1.21+ with
  `max_prepared_statements` above 0), `preparedStatements: true` turns them
  back on. Turbine warns once (`prepared-statements-on-pooler`) when you turn
  them on for a `pg.Pool` whose settings name a pooler, as it does for its
  own pools.

  The named statements are `findMany`, `findUnique`, `findFirst` (and the
  `OrThrow` forms), `count`, `aggregate`, `groupBy`, `update`, `updateMany`,
  `delete` and `deleteMany`, except a statement whose shape the caller writes:
  an `AND` / `OR` array, and a `groupBy` with a JSON-path key or JSON aggregate
  target. `create`, `createMany`, `upsert` and raw SQL are always sent unnamed.
</Callout>

<Callout type="warning" title="Named statements accumulate, and a request body can choose how many">
  A named prepared statement is never deallocated: each pooled connection keeps
  every distinct statement text it has parsed, and its plan memory, for as long
  as the connection lives. That is what makes them fast, and it is safe while
  your code fixes the set of texts. It stops being safe when a **request**
  decides the shape.

  Turbine handles the largest case itself. A `where` (or `having`) with a
  caller-written `AND` / `OR` array writes one parenthesized branch per
  element into the SQL, so a filter built from a UI multi-select creates a new
  statement text per length. Those statements are sent unnamed, with no
  configuration, so they are parsed per execution and never retained.
  `in: [...]` is not this shape: it binds `= ANY($1)`, one parameter whatever
  the list length.

  **The remaining channel is a caller-chosen `select`, `omit` or `with` subset.**
  These change the projection, and so the SQL text, and the builder cannot
  tell a hand-written `select` from one built from `req.query.fields`. `n`
  columns have `2^n` subsets. If you build a projection from user input, map
  it through a fixed allowlist of a few shapes, or set
  `preparedStatements: false` and pay the re-parse.

  A process also names at most 200 distinct statements. Every shape after that
  is sent unnamed, parsed per execution and never kept, so the first shapes a
  process runs, in practice its hot ones, keep their names.

  `db.<table>.cacheStats()` is the cheap way to notice: a `hitRate` near zero
  on a query you believe repeats means its shape is varying.
</Callout>

## Client escape hatches

| Member | Type | What it is for |
|---|---|---|
| `db.table<T>(name)` | `QueryInterface<T>` | Query a table by string name, for tables missing from your generated types. Pass `T` yourself to get typing back; the name is still validated against the schema metadata. |
| `db.pool` | `pg.Pool` | The underlying pool, for anything Turbine does not wrap. |
| `db.schema` | `SchemaMetadata` | The metadata the client was built from. |
| `db.stats` | `{ totalCount, idleCount, waitingCount }` | Pool gauges for a health endpoint. Returns zeros on drivers that do not expose counts, such as Neon HTTP. |
| `db.transaction(fn)` | raw `pg.PoolClient` | The lower-level transaction API. Prefer `$transaction`; use this only to run hand-written SQL on the transaction's own connection. The client is closed once the callback settles, and `release()` on it is refused. |
| `db.disconnect(options?)` / `db.end(options?)` | `Promise<void>`, or `Promise<{ timedOut, forcedConnections }>` with options | The same method. It tears down live `$listen` subscriptions first, then closes the pools Turbine owns. It is a **no-op for the primary pool when you supplied it yourself**, because you own its lifecycle. With `{ timeoutMs }`, connections still checked out at the deadline are cancelled and closed, and the call resolves with how many were forced. The MySQL, SQL Server and PowDB factories take the same option. |
| `db.$ping()` | `Promise<number>` | One `SELECT 1` on the primary. Resolves with the round trip in milliseconds, for a health check. Rejects with the typed connection error when the database cannot be reached. |
| `db.$on(event, fn)` / `db.$off(event, fn)` | `void` | Listen for `'query'` (one event per statement), `'poolError'` (an idle pooled connection failed) or `'connectionLost'` (a checked-out connection failed). The two pool events fire for pools Turbine opens. Any other name throws `TURBINE_E003`. |
| `db.<table>.cacheStats()` | `{ size, hits, misses, hitRate }` | Per-table SQL-template cache counters. A `hitRate` near zero on a repeated query means the args vary in shape, not only in value. |

```ts
// Query a table that isn't in the generated types
type AuditRow = { id: number; action: string; at: Date };
const audit = db.table<AuditRow>('audit_log');
const recent = await audit.findMany({ orderBy: { at: 'desc' }, limit: 20 });

// Check the template cache is doing its job
await db.users.findUnique({ where: { id: 1 } });
await db.users.findUnique({ where: { id: 2 } });
db.users.cacheStats();
// Two calls of the same SHAPE: the first is a miss that stores the template,
// the second is a hit. Counters are per QueryInterface instance, and `db.users`
// returns the same instance every time.
```

## Per-query timeout

Every operation takes `timeout`, in milliseconds: a positive number up to 2,147,483,647, or `0` for no timeout, the same rule as `$transaction`'s `timeout`. Anything else (a negative number, `NaN`, a string) throws `TURBINE_E003`.

```ts
import { TimeoutError } from 'turbine-orm';

try {
  await db.orders.update({ where: { id }, data: { status: 'shipped' }, timeout: 2_000 });
} catch (err) {
  if (err instanceof TimeoutError && err.outcome === 'not-executed') {
    // The statement made no change: safe to retry.
  }
}
```

A `TimeoutError` (`TURBINE_E002`) carries `outcome`, which says whether the statement could have taken effect:

- **`'not-executed'`**: it made no change. On PostgreSQL through a node-postgres pool, outside a transaction, Turbine sends the server a cancel request when the deadline passes and waits up to two seconds for the statement to answer. A confirmed cancel reports this, and so does a deadline that passed while still waiting for a connection, or a write that ran in its own transaction (a chunked `createMany`, a MySQL single-row write) and was rolled back. A retry applies once.
- **`'unknown'`**: the statement may still complete, so a write may have been applied. This is the answer on the other engines and on HTTP-style pools, and when the server did not confirm the cancel in time; Turbine then closes that connection instead of returning it to the pool. Check the database before retrying a write.

If the statement finishes during that wait, its result is returned late rather than reported as a timeout, because a committed write must not invite a retry. A read changes nothing, whatever `outcome` says.

A write that runs several statements (a chunked `createMany`, or a MySQL write and its re-read) shares one deadline across them, so `timeout` bounds the whole call. When the deadline passes, the write is rolled back.

Inside `$transaction` on PostgreSQL, the statement is cancelled on the transaction's connection and the error is `'not-executed'`, but the transaction itself is now rolled back. If the callback catches the error and returns, `$transaction` rejects with `TransactionRolledBackError` ([`TURBINE_E019`](/errors#e019)); in a nested `tx.$transaction` block, only that block rolls back. A transaction's own `timeout` is described under [Transactions](/transactions#timeouts).

## Middleware

`db.$use(fn)` registers a middleware that wraps every query. It can see what is about to run (`params.model`, `params.action`, `params.args`), time it, and transform the result `next()` returns. It cannot change the query: the SQL is compiled from the arguments the caller passed.

```ts
// Query timing
db.$use(async (params, next) => {
  const start = Date.now();
  const result = await next(params);
  console.log(`${params.model}.${params.action} took ${Date.now() - start}ms`);
  return result;
});

// Result transformation, redact a field on the way out
db.$use(async (params, next) => {
  const result = await next(params);
  if (params.model === 'users' && Array.isArray(result)) {
    for (const row of result as { email?: string }[]) row.email = '[redacted]';
  }
  return result;
});
```

> **Warning:** `params.args` is a plain copy of the arguments, so reading it, `JSON.stringify`, `structuredClone` and spreading it all work. Changing the copy does not change the query. If a middleware changes anything under it, or passes `next()` an args object that differs from the caller's, `next()` throws a `TypeError` naming the first path that differs, for example `params.args.where.role`. Assigning `params.args = ...` throws at once. Passing the unchanged copy on, or a structurally equal one, works.

Because middleware cannot rewrite queries, cross-cutting filters like soft deletes belong in a [global filter](/global-filters), an explicit `where`, or a small scoped helper:

```ts
import type { WhereClause } from 'turbine-orm';

// Explicit filter
const users = await db.users.findMany({ where: { deletedAt: null } });

// Scoped helper that always applies the filter
const activeUsers = (where: WhereClause<User> = {}) =>
  db.users.findMany({ where: { ...where, deletedAt: null } });

const rows = await activeUsers({ orgId: 1 });
```

## explain

Every table accessor has `explain(args)`. It compiles the statement `findMany(args)` would run, runs it through the engine's plan explainer, and returns the plan as `string[]` lines. Use it to check that a query hits the index you expect.

```ts
const plan = await db.posts.explain({
  where: { orgId: 7, isPublished: true },
  orderBy: { createdAt: 'desc' },
});
// PostgreSQL: ['Sort  (cost=…)', '  ->  Index Scan using posts_org_id_idx on posts …', …]
```

| Engine | Plan source |
|---|---|
| PostgreSQL, CockroachDB, YugabyteDB | `EXPLAIN` |
| SQLite | `EXPLAIN QUERY PLAN` |
| MySQL | `EXPLAIN` |
| PowDB | its native `explain`: the lowered, executed plan on PowDB 0.14+, with selectivity estimates on 0.15+ |
| SQL Server | no in-band explain; throws `UnsupportedFeatureError` (`TURBINE_E017`) |

Plan text is engine-owned diagnostic output, so match on node names, never on exact layout. Middleware does not run for `explain`.

## Raw SQL

For what the query builder doesn't express (window functions, `WITH RECURSIVE`, lateral joins):

```ts
const stats = await db.raw<{ day: Date; count: number }>`
  SELECT DATE_TRUNC('day', created_at) AS day, COUNT(*)::int AS count
  FROM posts WHERE org_id = ${orgId}
  GROUP BY day ORDER BY day
`;
```

Every `${}` interpolation becomes a bound parameter (`$1, $2, ...`), never text spliced into the SQL.

`db.raw` and `db.sql` take only a real tagged template. An array passed in its place (`db.raw([text])`) throws `ValidationError` (`TURBINE_E003`), because its text would reach the database unescaped. For SQL text built at runtime, use `rawUnsafe` with numbered placeholders:

```ts
const table = 'audit_' + year; // from your own code, never from a request
const rows = await db.rawUnsafe(`SELECT * FROM ${table} WHERE actor_id = $1`, actorId);
```

Nothing in the text passed to `rawUnsafe` is escaped, so it must never contain untrusted input. Values go in the trailing arguments.

Write placeholders as `$1`, `$2` and so on, on every engine. On SQLite, MySQL and SQL Server, Turbine rewrites them to the engine's own form, skipping string literals, quoted identifiers and comments. A `?` placeholder, or a `$n` past the values given, throws `TURBINE_E003`. With no values, the text is sent as written.

On PostgreSQL, a `Date` passed to `raw`, `rawUnsafe` or `sql` binds as its UTC fields under [`utcTimestamps`](/schema#zone-less-columns-timestamp-and-date-read-as-utc), as Turbine's own queries do. An Invalid Date throws `TURBINE_E003`. Raw SQL emits a `$on('query')` event but runs no `$use` middleware.

## Typed raw SQL, `db.sql<T>`

`db.sql<T>` is the typed escape hatch: you supply the row shape and get a thenable query with `.one()` and `.scalar()` helpers. As with `db.raw`, every `${value}` is bound as a `$N` parameter.

```ts
// Awaiting the query returns T[]
const users = await db.sql<{ id: number; name: string }>`
  SELECT id, name FROM users WHERE org_id = ${orgId}
`;
```

`.one()` returns the first row or `null`:

```ts
const user = await db.sql<{ id: number; name: string }>`
  SELECT id, name FROM users WHERE id = ${42}
`.one();
// user is { id: number; name: string } | null
```

`.scalar()` returns the first column of the first row, or `null`. Pass a type argument to override the inferred value type:

```ts
const total = await db.sql<{ count: number }>`
  SELECT COUNT(*)::int AS count FROM users
`.scalar();
// total is number | null

const name = await db.sql<{ name: string }>`
  SELECT name FROM users LIMIT 1
`.scalar<string>();
```
