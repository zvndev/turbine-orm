# The `turbine-orm/cli` module

[The CLI page](/cli) documents the `turbine` **binary**. This page documents the importable module behind it, `turbine-orm/cli`: the `TurbineCliConfig` type, the routines that find and load the config file, and the precedence rules that decide what a command runs against.

Most projects import only the type:

```ts
// turbine.config.ts
import type { TurbineCliConfig } from 'turbine-orm/cli';

const config: TurbineCliConfig = {
  url: process.env.DATABASE_URL,
  out: './generated/turbine',
  schema: 'public',
  migrationsDir: './turbine/migrations',
  seedFile: './turbine/seed.ts',
  schemaFile: './turbine/schema.ts',
};

export default config;
```

The rest of the module lets your own tooling resolve config the same way the CLI does.

<Callout type="note" title="This subpath is config only">
  `turbine-orm/cli` resolves to the config module. It does not export the
  command implementations, the argument parser, or anything that touches your
  database. Importing it has no side effects and needs no connection.
</Callout>

## `TurbineCliConfig`

| Field | Default | Meaning |
|---|---|---|
| `url` | none | Postgres connection string. |
| `out` | `'./generated/turbine'` | Output directory for the generated types and client. |
| `schema` | `'public'` | The Postgres **namespace** to introspect. Not a file path: see the warning below. |
| `include` | `[]` | Tables to include. Empty means all. |
| `exclude` | `[]` | Tables to exclude. |
| `migrationsDir` | `'./turbine/migrations'` | Directory for SQL migration files. |
| `seedFile` | see below | Path to the seed file. The canonical key. |
| `seed` | none | Back-compat alias for `seedFile`. `seedFile` wins when both are set. |
| `schemaFile` | `'./turbine/schema.ts'` | The `defineSchema` file. `turbine push` applies it, and `turbine generate` reads its `pii` / `updatedAt` / `maxLength` / `tsType` declarations. If a file named here or with `--schema-file` is missing, both commands fail; a missing default is skipped. |
| `importExtension` | `'auto'` | Specifier style in the generated `index.ts`: `'js'` (`./types.js`), `'ts'` (`./types.ts`, for Node type stripping), `'none'` (`./types`), or `'auto'`, which detects from your tsconfig and falls back to `'js'`. |
| `columnTypes` | none | `{ 'table.column': 'TypeScript type' }` with database names. Replaces the generated type of each named column; wins over a schema file's `tsType`. See [Typing columns](/cli#typing-columns-columntypes). |
| `keepColumnNames` | `false` | Keep raw database column names (snake_case) as generated field names instead of camelCasing them. |
| `legacyToManyUniques` | `false` | Keep the legacy `hasMany` shape for child relations whose foreign key is unique, instead of introspecting them as one-to-one (`hasOne`). |
| `adapter` | none | A `DatabaseAdapter` for a PG-compatible database with dialect-specific behavior, e.g. `cockroachdb`. **Declared on the type only: the bundled CLI does not read it.** See the note below. |

<Callout type="warning" title="adapter is declared on the type but the bundled CLI ignores it">
  `turbine migrate` does not pass `TurbineCliConfig.adapter` to the migration
  runner, so `adapter: cockroachdb` changes nothing. Migrations take the
  PostgreSQL path, including `pg_try_advisory_lock()`, which CockroachDB does
  not implement. Do not rely on the CLI to hold a cluster-wide migration lock
  on CockroachDB or YugabyteDB. Serialize `turbine migrate up` yourself (one
  runner, in a CI job that cannot overlap), or apply the generated `.sql`
  files with a tool that supports the engine. Setting the field does no harm.
  See [Compatibility](/compatibility).
</Callout>

This module exports `TurbineConfig` as an alias of `TurbineCliConfig`. It is **not** the runtime `TurbineConfig` exported from the package root, which configures a `TurbineClient`.

<Callout type="warning" title="schema is a namespace, schemaFile is a path">
  `schema: './turbine/schema.ts'` makes introspection run
  `WHERE table_schema = './turbine/schema.ts'`, which matches zero tables and
  would generate an empty client. `turbine generate` refuses such a value with
  an error. The check is the exported `looksLikeSchemaFilePath(value)`, which
  flags a path separator or a `.ts` / `.mts` / `.cts` / `.js` / `.mjs` /
  `.cjs` / `.json` extension.
</Callout>

## Finding and loading the config

```ts
import { findConfigFile, loadConfig, loadConfigResult } from 'turbine-orm/cli';
```

Candidates are tried in this order: `turbine.config.ts`, `turbine.config.mts`, `turbine.config.js`, `turbine.config.mjs`. The first one that **imports successfully** wins.

- `findConfigFile(cwd?)` returns the path of the first candidate that exists, or `null`. It imports nothing, so use it for display.
- `loadConfig(cwd?)` returns the config or `{}`. Load failures are swallowed.
- `loadConfigResult(cwd?)` returns `{ config, loadError? }`. Prefer this in tooling.

If a config file exists but throws on import (a syntax error, an ESM/CJS interop failure), `loadConfigResult` tries the lower-priority candidates. If none loads, it returns `config: {}` plus a `loadError` describing the first failure. Resolution still falls through to environment variables and flags, and the caller can report the real problem instead of a misleading "no database URL".

```ts
const { config, loadError } = await loadConfigResult();
if (loadError) {
  console.error(`Failed to load ${loadError.filename}:`, loadError.error);
}
```

`ConfigLoadError` is `{ filename, error }`; `ConfigLoadResult` is `{ config, loadError? }`.

### Module unwrapping

```ts
import { unwrapModuleDefault, unwrapConfigModule } from 'turbine-orm/cli';
```

In a project with `"type": "commonjs"` (the `npm init -y` default), importing `turbine.config.ts` through the tsx loader can produce a **double-wrapped** default: `mod.default` is itself `{ default: config }`. The usual `mod.default ?? mod` then reads every field as `undefined`, and every command fails with a misleading "No database URL provided".

`unwrapModuleDefault(mod)` takes `default` at the top level, then descends through any further **pure** `{ default: ... }` wrappers, with a depth bound so a self-referential object cannot loop. A wrapper is pure only when `default` is its only key besides `__esModule`. No Turbine config field is named `default`, so a real config object is never mistaken for a wrapper. `unwrapConfigModule(mod)` is the config-specific form: it collapses a non-object export to `{}` so resolution can continue.

## `resolveConfig(fileConfig, overrides)`

Merges a loaded config with CLI overrides and environment variables into a fully defaulted `ResolvedConfig`.

```ts
import { resolveConfig, loadConfig } from 'turbine-orm/cli';

const resolved = resolveConfig(await loadConfig(), { url: argv.url, out: argv.out });
```

**Precedence: CLI flags, then environment variables, then the config file, then defaults.** Only `url` reads an environment variable (`DATABASE_URL`), and it reads it **before** the config file. A `DATABASE_URL` in your shell therefore overrides `url` in `turbine.config.ts`, while an `out` in the config file applies whatever the environment holds. An empty or whitespace-only value counts as unset at every step, so an exported but empty `DATABASE_URL=` does not hide the `url` in your config file.

`CliOverrides` covers `url`, `out`, `schema`, `schemaFile`, `include`, `exclude`, `importExtension`, `keepColumnNames` and `legacyToManyUniques`. `migrationsDir` and `seedFile` come from the config file only; no flags set them.

Every `ResolvedConfig` field is non-optional except `seedFile`, which stays `string | undefined` because a project may have no seed file.

## `resolveSeedFile(config, cwd?)`

Resolves the seed file to an absolute path, or `null`.

```ts
import { resolveSeedFile } from 'turbine-orm/cli';

const seed = resolveSeedFile({ seedFile: './turbine/seed.ts' });
```

An explicit value wins **even if the file does not exist yet**. A config that names a seed file should produce a "that file is missing" error, not fall back to some other file that happens to exist. `seedFile` is checked before the `seed` alias. With no explicit value, the candidates are tried in order: `seed.ts`, `seed.js`, `seed.sql`, `turbine/seed.ts`, `turbine/seed.js`, `turbine/seed.sql`.

## `configTemplate(connectionString?)`

Returns the `turbine.config.ts` source that `turbine init` writes. Pass a connection string to inline it, or omit it to get `url: process.env.DATABASE_URL`. `DEFAULT_INIT_SEED_FILE` is the seed path the template points at. It sits next to the schema file, so a new project keeps its Turbine files in one directory.
