# Turbine for AI agents

Turbine is designed so a coding agent can use it correctly on a schema it has never seen. It gives the agent:

- an **installable skill** (`npx turbine skill`) whose every claim is executed against a live database before release;
- a **read-only [MCP server](/mcp)** with eleven tools that ground the agent in your live schema;
- a **deterministic codegen flow** it can run and re-run;
- **fully typed query arguments**, so an invalid query is a compile error it can read;
- **stable error codes** it can branch on instead of parsing prose.

This page shows how to point an agent at Turbine and gives you a snippet to drop into your project.

## Point an agent at Turbine: `llms.txt`

Turbine publishes an [llms.txt](https://turbineorm.dev/llms.txt) at the site root, following the [llms.txt convention](https://llmstxt.org): a short description of the library, the key facts, and a one-line summary of and link to every docs page. A fuller [llms-full.txt](https://turbineorm.dev/llms-full.txt) holds a condensed API reference drawn from these docs.

| File | URL | What it is |
|---|---|---|
| `llms.txt` | [turbineorm.dev/llms.txt](https://turbineorm.dev/llms.txt) | Short index: description, key facts, and links to each docs page. |
| `llms-full.txt` | [turbineorm.dev/llms-full.txt](https://turbineorm.dev/llms-full.txt) | Condensed API reference: reads, writes, WHERE operators, transactions, errors, engines. |

Give the agent one or both URLs, or add them to your project's agent-instructions file (see the snippet below). Both are static text you can fetch, cache and put in context.

## The installable skill

```bash
npx turbine skill
```

This writes a query-writing skill to `.claude/skills/turbine-orm/SKILL.md`. It covers
what an agent gets wrong on an unfamiliar schema: `with` versus Prisma's
`include`, how relation names are derived, what `select` may name, the WHERE
operators, relation filters, per-relation options, `having`, JSON paths, and the
error each mistake produces.

Options for other setups:

| command | what it does |
|---|---|
| `npx turbine skill --print` | writes the skill to stdout, so you can pipe it anywhere |
| `npx turbine skill --agents` | prints a short instructions block for `AGENTS.md` / `CLAUDE.md` |
| `npx turbine skill --dir <path>` | installs under a different skills root |

**Every factual claim in the skill is executed against a live database before
release.** The repository's eval harness runs each claim as a query and fails CI
when an answer changes, so the skill cannot drift from the ORM it describes.

### What it is worth, measured

On a held-out schema the models had never seen, across 240 scored attempts:

| | cold, schema only | + the skill | + a live MCP connection |
|---|---|---|---|
| `claude-sonnet-5` | 73% | **97%** | 93% |
| `claude-haiku-4-5` | 60% | **97%** | 90% |

Run-to-run variance on this harness is about 7 points, so the skill's
contribution is well outside the noise. On both models it matched or beat the
live MCP connection. Twelve of the twenty cold failures were the same mistake, a
relation named inside `select`, which is the fourth thing the skill covers. The
method, raw records and the limits of these numbers are in `evals/` in the
repository.

## The MCP server

For an agent that speaks MCP, `npx turbine mcp` exposes the **live database** through eleven read-only tools. Each runs inside `BEGIN READ ONLY`, and PII-tagged columns are redacted before rows reach the model. The four that matter most on an unfamiliar schema:

- `relation_graph`: every relation name with its cardinality, target and keys. These are the exact names a `with` clause accepts, so the agent reads them instead of guessing from column names.
- `find_join_path`: answers "how do I get from `comments` to `orgs`" with the relation chain **and the `with` clause to write**.
- `table_stats`: the planner's row estimate and the index list, so the agent checks a table's size before writing a query that would scan fifty million rows.
- `explain_error`: maps a Turbine error code to its cause, fix and docs link, without reading the database.

The other seven are `compile_query` (the exact SQL a read query compiles to, without running it), `schema_overview`, `table_detail`, `sample_rows`, `explain_query`, `migrate_status` and `doctor_report`. Setup and the full tool table: [MCP Server](/mcp).

## The deterministic codegen flow

An agent works best when the same commands always produce the same typed surface. Turbine's flow is **introspect → generate → typed client**.

```bash
npx turbine init        # writes turbine.config.ts and a turbine/ directory
npx turbine generate    # introspect the live database, emit a typed client
```

`generate` reads the database (or your code-first `defineSchema`) and writes three files to `generated/turbine/`:

- `types.ts`: entity interfaces and `Create` / `Update` input types
- `metadata.ts`: runtime schema metadata
- `index.ts`: a typed `TurbineClient` subclass with `db.<table>` accessors and a `turbine()` factory

The agent never guesses column names, relation names or types: they are in the emitted `.ts` and stay in step with the database. When the schema changes, the agent re-runs `generate` and the type checker points at every call site that needs updating. For code-first projects the loop is `edit turbine/schema.ts → turbine push → turbine generate` (see [Schema & Migrations](/schema)).

## Why typed query args suit agents

Query arguments are typed against the generated schema, so a wrong query fails at compile time with a message the agent can act on, instead of at runtime in production.

```ts
const users = await db.users.findMany({
  where: { orgId: 1 },
  with: { posts: { with: { comments: { with: { author: true } } } } },
});

users[0].posts[0].comments[0].author.name; // inferred end to end, no manual casts
```

- **Invalid columns, operators and relations are type errors.** A misspelled field in `where`, an operator that does not exist, or an unknown relation in `with` fails to typecheck. An agent that runs `tsc` gets a precise pointer instead of a silently wrong result.
- **`with` results are inferred at any depth.** The agent never annotates nested shapes by hand: `findMany` returns the exact nested type for the `with` clause it passed.
- **Every value is a bound parameter.** User values become `$1, $2, ...` parameters, and `contains` / `startsWith` / `endsWith` escape LIKE wildcards. The typed API has no code path that concatenates a value into SQL, and the raw escape hatches (`db.raw` and `db.sql<T>`) also bind every `${value}` as a parameter.

An agent can propose a query, run the type checker, and know the query is structurally correct before it touches the database.

## Why coded errors suit agents

Every Turbine error extends `TurbineError` and carries a `code` (`TURBINE_E001` through `E020`) that is stable across versions. Agents branch on the class or code instead of scraping a driver's error text.

```ts
import { SerializationFailureError, UniqueConstraintError } from 'turbine-orm';

try {
  await db.orders.create({ data });
} catch (err) {
  if (err instanceof UniqueConstraintError) {
    // E008, duplicate; surface a clean conflict
  } else if (err instanceof SerializationFailureError && err.isRetryable) {
    // E013, retry the transaction; the flag is a typed const, so the compiler knows it is safe
  }
}
```

Retryable failures (`DeadlockError` E012, `SerializationFailureError` E013) expose `isRetryable = true` as a const, so an agent can write a type-checked retry loop. See [Typed Errors](/errors) for the full table.

## Drop-in agent instructions

Paste this into your project's `CLAUDE.md` or `AGENTS.md` so every agent in the repo uses Turbine correctly. Trim it to what your project uses.

```markdown
## Database: Turbine ORM

This project uses turbine-orm (Postgres-first, Prisma-like API). Reference:
https://turbineorm.dev/llms.txt and https://turbineorm.dev/llms-full.txt.

Client
- Import the generated client: `import { turbine } from '@/generated/turbine'`.
- `const db = turbine()` reads DATABASE_URL. Call `db.disconnect()` on shutdown.
- Never hand-write entity types; run `npx turbine generate` after any schema change
  and import types from `generated/turbine`.

Reads
- `db.<table>.findMany({ where, with, orderBy, limit, offset, cursor, select, omit })`.
  `take`/`skip` are accepted as aliases for `limit`/`offset`.
- Nested relations go in `with`, never Prisma's `include`, and never as N+1 loops or
  manual joins. An unrecognized option is IGNORED, so an `include` returns rows with
  the relation missing. `with` results are fully typed at any depth.
- `select` and `omit` name columns only. A relation named in `select` throws (E003);
  relations carry their own nested `select`.
- Under `relationLoadStrategy: 'join'` the whole `with` tree resolves in ONE SQL
  statement (json_agg). The default is `'auto'`, which keeps that plan but may move
  an individual relation (or `_count`) to one flat follow-up statement when the join
  would be slower, e.g. an unindexed correlation column. The returned rows are
  identical either way, so do not assert on statement counts unless the query pins
  a strategy.
- `findUnique` needs a `where` that identifies one row (PK, a unique column, or every
  column of a compound unique) and returns `T | null`; anything else throws E003.
  `findUniqueOrThrow` throws NotFoundError (E001) on a miss. Use `findFirst` for
  "any row matching a filter", with an `orderBy` if which row matters.

Writes
- `create`, `createMany`, `update`, `updateMany`, `delete`, `deleteMany`, `upsert`.
- For counters use atomic operators: `data: { viewCount: { increment: 1 } }`.
- `update`/`delete` with an empty `where` throws ValidationError (E003) by design.
- Relation ops inside `data` (connect/create/disconnect/set/update/upsert) run in one tx.

Safety
- Every value is parameterized ($1, $2, ...); never string-interpolate SQL. Use `db.raw`
  or `db.sql<T>` (both bind `${value}` as params) only when the builder can't express it.
- Wrap multi-step writes in `db.$transaction(async (tx) => { ... })`.

Errors
- Catch typed errors and branch on the class/code (TURBINE_E001..E020), not the message.
- Retry only when `err.isRetryable` is true (DeadlockError E012, SerializationFailureError E013).

Migrations
- Local iteration: edit `turbine/schema.ts` (defineSchema), then `turbine push`, then
  `turbine generate`. Production: SQL migrations via `turbine migrate` (never edit an
  applied migration file, checksums are validated).
```
