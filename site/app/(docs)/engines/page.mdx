# Database Engines

Turbine is built for PostgreSQL. The same typed `findMany` / `with` / `where` / `create` API also runs on SQLite, MySQL 8, SQL Server, local libSQL, Cloudflare D1 and PowDB, and over Neon's WebSocket and HTTP drivers, each behind its own import path.

| Engine | Import | Driver to install | Tested in CI | Refused at connection |
|---|---|---|---|---|
| PostgreSQL | `turbine-orm` | none (`pg` is included) | PostgreSQL 14, 15, 16, 17 and 18 | nothing checked |
| SQLite | `turbine-orm/sqlite` | none (`node:sqlite` is built in) | Node 22 and 24 | Node before 22.5 (no `node:sqlite`) |
| SQLite (better-sqlite3) | `turbine-orm/better-sqlite3` | `better-sqlite3` | better-sqlite3 12.11.1, Node 20 and 24 | nothing checked |
| MySQL | `turbine-orm/mysql` | `mysql2` | the floating `mysql:8` image | MySQL before 8.0, and MariaDB |
| SQL Server | `turbine-orm/mssql` | `mssql` | SQL Server 2022 | SQL Server before 2016 |
| libSQL | `turbine-orm/libsql` | `@libsql/client` | local files, `@libsql/client` 0.18.0 | remote URLs and sync settings |
| Cloudflare D1 | `turbine-orm/d1` | none (the Worker binding) | local workerd through Miniflare | n/a |
| Neon WebSocket | `turbine-orm/neon-ws` | `@neondatabase/serverless` | a local relay to PostgreSQL 14 to 18 | n/a |
| Neon HTTP | `turbine-orm/neon-http` | `@neondatabase/serverless` | a local bridge to PostgreSQL 14 to 18 | n/a |
| PowDB | `turbine-orm/powdb` | `@zvndev/powdb-embedded` or `@zvndev/powdb-client` | embedded, packages 0.20 | a networked server before 0.7.0 |

"Refused at connection" is what the factory checks, not a tested floor: a version between it and the tested one may work, and no CI job shows that it does. The engine drivers are optional peer dependencies, so `npm install turbine-orm` installs only `pg`. Every engine's API except PostgreSQL's is Experimental under the [stability policy](https://github.com/zvndev/turbine-orm/blob/main/STABILITY.md), so a minor release can change it.

## Support tiers

Each tier is computed from test evidence, not chosen. Supported means the core features (typed queries, nested reads, nested writes, transactions, upsert and `createMany`) each run against the real engine in CI on every change. The [engine support matrix](https://github.com/zvndev/turbine-orm/blob/main/docs/engine-support.md) has the rule, every feature row, the versions CI exercises and the tests behind each claim.

## Capability matrix

✗ means the feature throws `UnsupportedFeatureError` ([`TURBINE_E017`](/errors#e017)). n/a means the engine has no such option.

| Feature | PostgreSQL | SQLite | MySQL 8 | SQL Server | PowDB |
|---|:-:|:-:|:-:|:-:|:-:|
| Nested relations (`with`) | ✓ | ✓ | ✓ | ✓ | ✓ ¹ |
| Atomic update operators (`increment`, ...) | ✓ | ✓ | ✓ | ✓ | ✓ |
| Update expressions (`expr`) | ✓ | ✓ | ✓ | ✓ | ✗ |
| Multi-row upsert (`createMany` `onConflict`) | ✓ | ✓ | ✓ ⁷ | ✓ | ✗ |
| Optimistic locking | ✓ | ✓ | ✓ | ✓ | ✓ |
| `$transaction` | ✓ | ✓ ² | ✓ | ✓ | ✓ ³ |
| Nested `tx.$transaction` (savepoints) | ✓ | ✓ | ✓ | ✓ | ✗ |
| Read-only transactions (`readOnly`) | ✓ | ✗ | ✓ | ✗ | ✗ |
| Row locks (`lock`) | all modes | ✗ | `'update'`, `'share'` | ✗ | ✗ |
| `findManyStream` | server cursor | native batches ⁴ | native batches ⁴ | native batches ⁴ | ✗ |
| Cursor pagination (`cursor`) | ✓ | ✓ | ✓ | ✓ | ✗ |
| `mode: 'insensitive'` on `in` / `notIn` | ✓ | ✗ | ✗ | ✗ | ✓ |
| `nulls` placement in `orderBy` | ✓ | ✓ | ✗ | ✗ | `'last'` only |
| `explain()` | ✓ | ✓ | ✓ | ✗ | ✓ |
| `distinct` / `groupBy({ distinctOn })` | ✓ | ✗ | ✗ | ✗ | ✗ |
| Percentiles (`_percentile`) | ✓ | ✗ | ✗ | ✗ | ✗ |
| Full-text `search` filter | ✓ | ✗ | ✗ | ✗ | ✗ |
| Array-column filters (`has`, `hasEvery`, ...) | ✓ | ✗ | ✗ | ✗ | ✗ |
| pgvector distance and KNN ordering | ✓ | ✗ | ✗ | ✗ | ✗ |
| LISTEN/NOTIFY (`$listen` / `$notify`) | ✓ | ✗ | ✗ | ✗ | ✗ |
| RLS `sessionContext` | ✓ | ✗ | ✗ | ✗ | ✗ |
| Read replicas (`replicas`) | ✓ | n/a | n/a | n/a | snapshots ⁵ |
| `turbine` CLI | ✓ | partial ⁶ | partial ⁶ | partial ⁶ | n/a |

¹ One PowQL statement on engine 0.18+. Older engines and many-to-many relations use batched lookups, with the same results.
² SQLite has one connection. An open `$transaction` holds it, and other callers wait up to `busyTimeoutMs`.
³ PowDB has a single writer. Concurrent `$transaction` calls queue and run one at a time.
⁴ Rows are read from the engine in `batchSize` batches as you iterate. SQLite uses a bounded first fetch and then native iteration, which needs Node 22.16+ or 24+, and its stepping is synchronous. Only PostgreSQL holds a server-side cursor. `batchSize` bounds rows, not payload bytes.
⁵ [Read-only snapshots](#read-only-snapshots-and-replicas-powdb--014), routed by hand.
⁶ Project commands (init, generate, migrations and more) exist per engine; Studio, `observe` and `migrate-from-prisma` do not. SQLite supports init, generate and pull, SQL migrations, schema push, seed, status, and read-only doctor and MCP tools, all through `node:sqlite` (a better-sqlite3 database file uses the same commands). Which commands each engine has, and how each is tested, is in the [engine support matrix](https://github.com/zvndev/turbine-orm/blob/main/docs/engine-support.md).
⁷ Uses the row-alias syntax MySQL added in 8.0.19. CI runs the floating `mysql:8` image, so 8.0.19 itself is not tested.

## What is actually Postgres-only

Every row above with ✗ on all other engines is a PostgreSQL feature. Using one elsewhere throws `TURBINE_E017`, never broken SQL.

Some tooling also targets PostgreSQL only, with no capability error:

- The `turbine` CLI's `studio`, `observe` and `migrate-from-prisma` commands. SQLite, MySQL and SQL Server projects have their own subset of the other commands (see ⁶); on SQLite, doctor and MCP are read-only.
- The root `schemaPush` and `schemaDiff` functions. SQLite CLI push uses its own guarded planner. `schemaToSQL` builds DDL for any engine's dialect and opens no connection.

If pgvector, realtime or RLS is core to your app, stay on PostgreSQL. The other engines suit tests, edge demos and existing MySQL or SQL Server deployments.

## Setup

Outside PostgreSQL you can work code-first. SQLite also supports introspection and SQL-first CLI projects. Define the schema with `defineSchema` and turn it into runtime metadata:

```ts
// schema.ts
import { defineSchema, schemaDefToMetadata } from 'turbine-orm';

export const schema = defineSchema({
  users: {
    id: { type: 'serial', primaryKey: true },
    email: { type: 'text', unique: true, notNull: true },
  },
  posts: {
    id: { type: 'serial', primaryKey: true },
    userId: { type: 'bigint', notNull: true, references: 'users.id' },
    title: { type: 'text', notNull: true },
  },
});

export const SCHEMA = schemaDefToMetadata(schema);
```

Each factory takes `(target, schema, options?)` and returns a `TurbineClient`. `options` accepts every client option except the connection settings and `replicas`, plus the engine options listed below. `disconnect()` closes what the factory opened and leaves a pool you passed in open.

The factories return the base client type, so the examples reach tables with `db.table('users')`.

### SQLite

```bash
npm install turbine-orm
```

```ts
import { schemaToSQL } from 'turbine-orm';
import { sqliteDialect, turbineSqlite } from 'turbine-orm/sqlite';
import { schema, SCHEMA } from './schema.js';

// A file path, ':memory:', or an open DatabaseSync handle
const db = turbineSqlite(':memory:', SCHEMA);

for (const statement of schemaToSQL(schema, { dialect: sqliteDialect })) {
  await db.rawUnsafe(statement);
}

const user = await db.table('users').findUnique({ where: { id: 1 }, with: { posts: true } });
```

`turbineSqlite` is synchronous and adds no dependency.

| Option | Default | What it does |
|---|---|---|
| `wal` | `true` | WAL journal mode for file databases. |
| `busyTimeoutMs` | `5000` | How long a statement waits for a lock or for another caller's open transaction. |
| `foreignKeys` | `true` | Turns on `PRAGMA foreign_keys`. |

- A caller still waiting after `busyTimeoutMs` gets a retryable `SerializationFailureError` ([`TURBINE_E013`](/errors#e013)). Inside a `$transaction` callback use `tx`: calling `db` there throws `TURBINE_E017`.
- Columns your schema declares `boolean` or `json` read back as booleans and parsed values on Node 22.16+ or 23.11+. Older Node returns `1` / `0` and JSON text.
- `numeric` reads as a JS number. Integers past `Number.MAX_SAFE_INTEGER` read as strings.
- `mode: 'insensitive'` uses `COLLATE NOCASE`, which folds ASCII only.
- `isolationLevel` is ignored, since SQLite transactions are serializable.

#### Optional better-sqlite3 binding

Install `better-sqlite3@^12.11.1` alongside Turbine, then use the asynchronous
`turbineBetterSqlite3(target, schema, options)` factory from
`turbine-orm/better-sqlite3`. A supplied handle remains caller-owned. Both
bindings share query, transaction, native iterator and value-decoding behavior.
`introspectBetterSqlite3Database(handle, { includeViews: true })` supports the
same filters as `introspectSqliteDatabase`; see [views](/views).

#### Result metadata and limits

Turbine checks once per process whether builtin `all()` keeps a width change
between prepare and the first step, which also happens on the first `SELECT *`
after another connection altered the table. Node 22.16.0 and 24.10.0 native
`all()` drop cells there, so SQL containing `*` uses native iteration on them;
Node 26.12.0 does not, so it keeps `all()`. Node 22.5 to 22.15 read the width
before the first step in every reader (22.5 to 22.12 have no `iterate()`, and
22.13 to 22.15's `iterate()` does the same), so the defect remains there when
the schema changes between prepare and the first step; use Node 22.16 or later
if that can happen while your application runs. Ordinary results are
still collected eagerly. Repeated output names use the final column's value and
decoder.

Whole-document JSON equality/containment and JSON-path equality with null,
arrays, objects or booleans throw E017. Numeric and string path equality remain
available. SQLite has no native array or enum type: schema enums use TEXT plus
CHECK; introspection does not recover enum labels. Native binary JSONB remains
binary. Integers outside the safe JS range return strings.

SQL migration writes and code-first push require builtin authorizer and
transaction-state support (Node >= 24.10). Seed and migration helper handle
contracts target node:sqlite, so a better-sqlite3 handle is not a drop-in target;
use its file through the CLI or an explicit client transaction for seed writes.
The [SQLite support and refusal inventory](https://github.com/zvndev/turbine-orm/blob/main/docs/sqlite-support.md)
lists every E017 family and links its implementation and tests.

### MySQL 8

```bash
npm install turbine-orm mysql2
```

```ts
import { turbineMysql } from 'turbine-orm/mysql';
import { SCHEMA } from './schema.js';

const db = await turbineMysql('mysql://user:pass@localhost:3306/app', SCHEMA);
```

`target` is a connection string, a `mysql2` config object or a `mysql2` pool. A pool you pass in must set `namedPlaceholders: true`. `connectionLimit` (default `10`) sizes a pool the factory builds.

- `createMany` returns `[]`, because MySQL has no `RETURNING`. Query the rows again if you need them. With `onConflict` it returns the written rows.
- `create` reads the new row back by a key it knows: a primary key in `data`, an `AUTO_INCREMENT` id, or a unique key in `data`. Any other server-generated key (a UUID default) throws `TURBINE_E017` before the insert, so pass it in `data`.
- The default collation, `utf8mb4_0900_ai_ci`, ignores case and accents in `=`, unique keys, `groupBy` and `ORDER BY`. Use a binary or `_as_cs` collation where case must count.
- An unconstrained `numeric` is created as `DECIMAL(65,30)` and reads back padded to 30 decimal places.
- `NaN`, `Infinity` and an Invalid Date throw `ValidationError` instead of storing `0`.

### SQL Server

```bash
npm install turbine-orm mssql
```

```ts
import { turbineMssql } from 'turbine-orm/mssql';
import { SCHEMA } from './schema.js';

const db = await turbineMssql('mssql://sa:Passw0rd!@localhost:1433/app', SCHEMA);
```

`target` is a connection string, an `mssql` config object or an `mssql` pool. The `schema` option sets the database schema for introspection and DDL (default `dbo`).

- A `createMany` over 1000 rows or 2098 parameters is split into chunks inside one transaction.
- `numeric` reads as a JS number, because the driver has no string mode for `DECIMAL`. A `UNIQUEIDENTIFIER` reads back in upper case.
- A `json` / `jsonb` column is stored as `NVARCHAR(MAX)` and reads back parsed. Pathless JSON `equals` throws `TURBINE_E017`.
- Back an upsert's conflict target with a real `UNIQUE` index or primary key. `MERGE` alone does not stop two concurrent inserts.

## Engines and transports added in 0.94

Each of these is new in 0.94.0. The tier after each name is its evidence tier from the table above.

### SQLite through better-sqlite3 (Supported)

`await turbineBetterSqlite3('app.db', SCHEMA)` from `turbine-orm/better-sqlite3` runs the same SQLite SQL and client as `turbine-orm/sqlite`, through the `better-sqlite3` package (`npm install better-sqlite3`). A path is closed by `disconnect()`; a handle you pass in stays open. CI runs the binding suite on Node 20 and 24, plus the shared battery and parent-scoped nested writes on Node 24. [Guide](https://github.com/zvndev/turbine-orm/blob/main/docs/sqlite-binding.md).

### libSQL, local files (Deferred)

`await turbineLibsql('file:app.db', SCHEMA)` from `turbine-orm/libsql` runs on a local libSQL file or `:memory:` through `@libsql/client`. Remote URLs, sync and embedded replicas are refused. No further work is planned on it this cycle. [Guide](https://github.com/zvndev/turbine-orm/blob/main/docs/libsql-local.md).

### Cloudflare D1 (Experimental)

`turbineD1(env.DB, SCHEMA)` from `turbine-orm/d1` runs inside a Worker on its `D1Database` binding, with no driver to install. The Worker needs the `nodejs_compat` flag. Nested writes (D1 has no interactive transaction), streams, row locks and `$listen` throw before any statement is prepared. CI runs it in local workerd through Miniflare; hosted D1 is not tested. [Guide](https://github.com/zvndev/turbine-orm/blob/main/docs/d1-binding.md).

### Neon over WebSockets (Experimental)

`await turbineNeonWs({ connection: { connectionString } }, SCHEMA, { sessionMode: 'persistent', lifetime: 'persistent' })` from `turbine-orm/neon-ws` binds a Neon `Pool` or `Client` from `@neondatabase/serverless`. You state whether the endpoint keeps a session (`sessionMode`) and whether connections may outlive one invocation (`lifetime`). CI runs it through a local WebSocket relay to PostgreSQL; hosted Neon is not tested. [Guide](https://github.com/zvndev/turbine-orm/blob/main/docs/neon-websocket.md).

### Neon over HTTP (Experimental)

`turbineNeonHttp(neon(url), SCHEMA)` from `turbine-orm/neon-http` sends each query as one HTTP request, plus native batches. Anything that needs a second request, such as a nested write, throws before it runs. CI runs it through a local HTTP bridge to PostgreSQL; hosted Neon is not tested. [Guide](https://github.com/zvndev/turbine-orm/blob/main/docs/neon-http.md).

## PowDB

PowDB is a single-node database with its own query language, PowQL. It runs in-process (embedded) or as a server (networked), over the same data.

<Callout type="note" title="Maintenance mode">
  The PowDB engine receives bug and data-safety fixes only, no new features.
  See the [stability policy](https://github.com/zvndev/turbine-orm/blob/main/STABILITY.md).
</Callout>

```bash
npm install turbine-orm @zvndev/powdb-embedded   # in-process, no server
npm install turbine-orm @zvndev/powdb-client     # a running powdb-server
```

```ts
import { powqlSchemaDDL, turbinePowDB } from 'turbine-orm/powdb';
import { SCHEMA } from './schema.js';

const db = await turbinePowDB({ embedded: './data' }, SCHEMA);
// or: await turbinePowDB('powdb://127.0.0.1:7070', SCHEMA);

for (const statement of powqlSchemaDDL(SCHEMA)) await db.rawUnsafe(statement);
```

PowDB has no savepoints, row locks, cursors or bulk upsert, so those features throw `TURBINE_E017` (see the matrix). Setup options, version-gated features and the full list of limits are on the [PowDB module page](/powdb).

<a id="read-only-snapshots-and-replicas-powdb--014" />

### Read-only snapshots

PowDB 0.14+ serves a copy of a data directory strictly read-only, to any number of readers:

```ts
const replica = await turbinePowDB({ embedded: './snapshot', readonly: true }, SCHEMA);
// or a powdb-server started with --readonly:
const remote = await turbinePowDB('powdb://replica-host:7070', SCHEMA, { readonly: true });
```

Reads work unchanged. A write throws `ReadOnlyError` ([`TURBINE_E018`](/errors#read-only-refusals)) with `reason: 'snapshot'`, so route it to the primary. The data is as fresh as the last snapshot. See [Read Replicas](/read-replicas).

## Differences you will hit

Some results follow the engine, and no error marks the difference:

| | PostgreSQL | SQLite | MySQL 8 | SQL Server |
|---|---|---|---|---|
| String `=` | case-sensitive | case-sensitive | follows the collation (default ignores case and accents) | follows the collation |
| `contains` / `startsWith` / `endsWith` | case-sensitive | ASCII case-insensitive | follows the collation | follows the collation |
| `NULL` in ascending order | last | first | first | first |
| `numeric` / `decimal` | exact string | JS number | exact string | JS number |
| Pathless JSON `equals` | document equality | `TURBINE_E017` | document equality | `TURBINE_E017` |

These agree on all four SQL engines:

- A value read inside `with` equals the same column read at top level, including `bigint`, `numeric` and binary columns.
- A zone-less `date` reads as UTC midnight. See [Zone-less columns](/schema#zone-less-columns-timestamp-and-date-read-as-utc).
- Integer `divide` truncates, and `_avg` over an integer column returns the full fraction.
- `create`, `update`, `delete` and `upsert` return the full row. MySQL's `createMany` is the exception above.

## Postgres-compatible databases

Databases that speak the PostgreSQL wire protocol (Neon, Supabase, AlloyDB, TimescaleDB, YugabyteDB, CockroachDB) are not separate engines. They use the default `turbine-orm` import, some with a thin adapter; Neon can also use the two transports above. See [Database Compatibility](/compatibility).
