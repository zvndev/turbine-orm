# Global Filters

A global filter is a `WHERE` predicate Turbine merges into **every** query on a table: reads, mutations, and the relation subqueries that target it. Two patterns need it:

- **Soft delete**: hide rows where `deletedAt` is set, everywhere, without adding `where: { deletedAt: null }` to every query.
- **Multi-tenancy**: scope every query to the current tenant, evaluated per request.

You configure global filters once on the client, and Turbine `AND`s them into the compiled `WHERE`. Values are always parameterized.

## Configuration

Pass `globalFilters` to the client, keyed by table accessor (`db.blogPosts`) or by table name (`blog_posts`). Either spelling works. Each value is a `WhereClause`, or a function that returns one:

```ts
import { turbine } from './generated/turbine/index.js';

const db = turbine({
  connectionString: process.env.DATABASE_URL,
  globalFilters: {
    // Soft delete, static filter
    posts: { deletedAt: null },
    users: { deletedAt: null },

    // Multi-tenancy, evaluated per query build
    orders: () => ({ tenantId: currentTenant() }),
  },
});
```

With this in place, `db.posts.findMany()` compiles to `... WHERE "deleted_at" IS NULL`, with no `where` needed.

The map is checked when the client is constructed, because a filter that silently applies to nothing returns the very rows it was meant to hide. Each of these throws `ValidationError` ([`TURBINE_E003`](/errors#e003)) from the constructor, naming the bad key and the closest valid one:

- A key that names no table (a typo, or a table that was renamed).
- Two keys for one table (`blogPosts` and `blog_posts`). Combine them with `AND: [...]`.
- A static filter whose keys name no column or relation of that table.
- A static `AND` / `OR` / `NOT` that cannot be read as written: `OR: { ... }` (an object where an array belongs; write `OR: [{ ... }]`), or a combinator holding a scalar or `null`.
- A static relation filter whose value is not a where object, such as `author: { is: 5 }` or `posts: { some: null }`. These are the same shapes a query refuses (see [Relation filters](/queries#relation-filters)).
- A value that is neither a where object nor a function, including `undefined`.
- Anything a query with that `where` would refuse, because each static filter is compiled once at construction: an operand that does not fit its operator or column, a plain `{ col }` object where `col()` is needed, an operator object with no operator (`{ name: { mode: 'insensitive' } }`), a misspelled column inside a relation filter, or an `undefined` value. The message starts with `globalFilters["<key>"]:`.
- A static filter that reaches its own table through relation filters, such as `users: { posts: { some: {} } }` beside `posts: { author: { is: { active: true } } }`, where each filter applies inside the other's relation filter. The message names the chain.

A broken static filter stops the client from being built, even if the table is never queried.

A static `null` is accepted and means "no filter for this table".

A generated client also catches these at compile time. The generated `turbine()` and constructor take `TypedTurbineConfig`, whose `globalFilters` is typed per table, so a misspelled table or column in a static filter or in a function's return value is a type error. If your generated client predates this, regenerate it.

```ts
const posts = await db.posts.findMany();
// SELECT ... FROM "posts" WHERE "deleted_at" IS NULL

const active = await db.users.findMany({ where: { role: 'admin' } });
// SELECT ... FROM "users" WHERE "role" = $1 AND "deleted_at" IS NULL
```

## Function filters, per-request tenancy

A function filter runs **every time a query is built**, so a closure over per-request state gives you a request-scoped filter. Use it for tenant isolation:

```ts
const db = turbine({
  connectionString: process.env.DATABASE_URL,
  globalFilters: {
    orders: () => ({ tenantId: getCurrentTenantId() }),
  },
});

// Later, inside a request handler where getCurrentTenantId() returns 't-42':
const orders = await db.orders.findMany();
// SELECT ... FROM "orders" WHERE "tenant_id" = $1   -- params: ['t-42']
```

A function filter fails closed. If it returns `undefined`, or a filter holding `undefined` at any depth (`{ tenantId: undefined }` when the request carries no tenant), the query throws `ValidationError` (`TURBINE_E003`) instead of running unfiltered. To apply no filter on purpose, return `null` or `{}`:

```ts
globalFilters: {
  // Throws when no tenant is set, rather than reading every tenant's orders.
  orders: () => ({ tenantId: getCurrentTenantId() }),

  // An admin context opts out explicitly.
  invoices: () => (isAdmin() ? null : { tenantId: getCurrentTenantId() }),
},
```

The filter's **shape** is part of the SQL cache key, and its **values** are collected again on every build. Two requests with different tenant ids reuse the same cached SQL but bind their own parameters. A filter that changes shape (`{ deletedAt: null }` on one call, `{ tenantId: 't' }` on the next) gets a separate cache entry for each shape.

## Filters flow into relations

Global filters apply to **relation subqueries** too. A filter on `posts` restricts `posts` wherever it appears, including when they are loaded through a parent's `with` clause.

```ts
// globalFilters: { posts: { deletedAt: null } }
const users = await db.users.findMany({
  with: { posts: true },
});
// The correlated posts subquery ANDs "deleted_at" IS NULL -
// soft-deleted posts never appear under any user.
```

A target-table filter is applied to:

- The `with` relation subquery, under both the default `join` strategy and the `batched` strategy
- Relation filters: `some`, `every`, `none` and belongsTo `is`
- Relation `_count` and relation `orderBy: { posts: { _count: 'desc' } }`

So with a soft-delete filter on `posts`, a user's post `_count` counts only live posts, and `where: { posts: { some: {...} } }` matches only live posts.

A filter can itself hold a relation filter, such as `posts: { author: { is: { active: true } } }`. The `users` filter then applies inside it, as it does inside any relation filter. Function filters that reach each other this way, or a function filter that reaches its own table, apply once per chain: while a table's filter is being compiled, a relation that leads back to that table reads its rows unfiltered, which ends the chain. Static filters that form such a cycle are refused when the client is built (see above).

## Mutations and the empty-where guard

Global filters apply to `update`, `updateMany`, `delete`, `deleteMany` and the conflict `UPDATE` of `upsert`. `create` and `createMany` are **never** filtered: an insert has nothing to scope.

The conflict update of `upsert` needs an engine that can put a predicate on it. PostgreSQL and SQLite emit `ON CONFLICT … DO UPDATE … WHERE`. MySQL's `ON DUPLICATE KEY UPDATE`, SQL Server's `MERGE` and PowDB's `upsert` cannot carry the filter there. On those engines an `upsert` on a filtered table runs as a filtered lookup, then an update or an insert, in one transaction. Another tenant's row is invisible to the lookup and is never updated.

A [batched](/queries#pipeline) `buildUpsert` on a filtered table is refused on those engines with `UnsupportedFeatureError` (`TURBINE_E017`), because a batched statement has no round trip for the lookup. Pass `skipGlobalFilters: UNSAFE` when the upsert is meant to reach every row.

A global filter does **not** satisfy the [empty-where guard](/queries#delete--deletemany). The guard checks the `where` you pass, so an unqualified mass mutation is still refused even when a filter is configured:

```ts
// globalFilters: { users: { deletedAt: null } }
await db.users.deleteMany({ where: {} });
// ❌ ValidationError (TURBINE_E003), the filter does NOT make this safe.

await db.users.deleteMany({ where: { orgId: 1 } });
// ✅ Deletes org-1 users, AND-merged with "deleted_at" IS NULL.
```

The filter still compiles into the `WHERE`, but it does not turn `{}` into an allowed statement.

## Opting out, `skipGlobalFilters`

Any read or mutation accepts `skipGlobalFilters` to bypass filters for that call. It is a **privilege option**: only the `UNSAFE` symbol turns it on.

```ts
import { UNSAFE } from 'turbine-orm';

// See a soft-deleted row (admin tooling): skip every filter on this call
const all = await db.posts.findMany({ skipGlobalFilters: UNSAFE });

// Skip only the `posts` filter, keep others. The array LEADS with the sentinel.
const some = await db.users.findMany({
  with: { posts: true },
  skipGlobalFilters: [UNSAFE, 'posts'],
});
```

Each entry after `UNSAFE` names a table, by table name (`blog_posts`) or by client accessor (`blogPosts`); both skip the same filter. An entry that names no table would skip nothing, so it throws `ValidationError` (`TURBINE_E003`) suggesting the nearest table name. `[UNSAFE]` with no table after it throws for the same reason. Pass `UNSAFE` alone to skip every filter.

`skipGlobalFilters: true` and `skipGlobalFilters: ['posts']` throw `ValidationError` ([`TURBINE_E003`](/errors)). See [Privilege options](#privilege-options-and-the-unsafe-symbol) below for why, and for how to upgrade if you pass `true` today.

## Privilege options and the `UNSAFE` symbol

Three query options remove a safety boundary instead of changing a result: `skipGlobalFilters` (drops the tenant or soft-delete predicate), [`includePii`](/queries#pii-fields-includepii) (drops the PII projection) and `allowFullTableScan` (drops the empty-`where` guard on a mutation). Each one is enabled **only** by a symbol exported from the package:

```ts
import { UNSAFE } from 'turbine-orm';
```

### Why a symbol and not `true`

All three are ordinary siblings of `where` on the same options object, and a common handler spreads a request body into it:

```ts
// The shape this closes: a request body spread straight into query args.
app.get('/users', (req, res) => db.users.findMany({ ...req.body }));
```

If these options took `true`, a client posting `{"where":{"name":"x"},"skipGlobalFilters":true}` would get the same statement **minus the tenant predicate**: the multi-tenancy boundary, removed over the wire by the user it exists to contain. `includePii: true` would unlock the PII projection the same way, and `allowFullTableScan: true` would disarm the guard that stops an unqualified `UPDATE` or `DELETE`.

A `boolean` type plus a warning in the docs does not fix this. It is a mass-assignment shape, and mass assignment happens because nobody listed the keys. `JSON.parse` cannot produce a symbol, and neither can a query string, a form body or a `structuredClone` of parsed input. No untrusted-data path can put `UNSAFE` on an args object, so the escalation is impossible, not merely discouraged.

The array form gets the same check, because `{"skipGlobalFilters":["users"]}` is the same breach with one extra step. `[UNSAFE, 'posts']` is accepted; `['posts']` is not.

<Callout type="note" title="Symbol.for, not Symbol()">
  `UNSAFE` is registered as `Symbol.for('turbine-orm.UNSAFE')`. Turbine ships
  ESM and CJS builds, and a project can import `UNSAFE` from one copy while the
  query interface it calls came from the other. A plain `Symbol()` would be a
  different value in each copy, and every privileged call would throw. The
  global registry makes the two copies agree. Application code can reach
  `Symbol.for` too, but that weakens nothing: the attacker's channel is parsed
  data, which cannot carry a symbol either way.
</Callout>

### Upgrading from `true`

Passing `true` to any of these three options throws. Change each call site:

| Before | After |
|---|---|
| `skipGlobalFilters: true` | `skipGlobalFilters: UNSAFE` |
| `skipGlobalFilters: ['posts']` | `skipGlobalFilters: [UNSAFE, 'posts']` |
| `includePii: true` | `includePii: UNSAFE` |
| `allowFullTableScan: true` | `allowFullTableScan: UNSAFE` |

**TypeScript finds every one of them for you.** The option types are `Unsafe`, so each row of that table is a compile error before it is a runtime error. Type-check the project, and the compiler lists every call site to change.

That includes the boolean shapes: `allowFullTableScan: false` does **not** typecheck, and neither does `allowFullTableScan: someFeatureFlag`. A conditional call site adds the key or leaves it out:

```ts
await db.sessions.deleteMany({
  where: {},
  ...(purgeEverything ? { allowFullTableScan: UNSAFE } : {}),
});
```

Two rules decide what happens at *runtime*, which is what an untyped call site hits (plain JavaScript, or args that arrive as `any` from a boundary):

- **`false`, `null` and `undefined` are accepted and mean "not enabled".** They never throw, because none of them *asks* for the privilege. This is a courtesy to untyped callers. In TypeScript the type already rules them out.
- **Everything else, `true` included, throws.** Ignoring a stale `true` would trade an escalation bug for a silent failure: your admin tool would quietly stop seeing soft-deleted rows, or return objects with the PII columns missing, with no signal anywhere. The error names the option and the import, and ends with the line to grep for in an incident: *"If you did not write this option, an untrusted object was spread into these query args."*

The same rule applies through [`turbine-orm/prisma-compat`](/migrate-from-prisma), which forwards these three options unchanged and leaves the check to the core.
