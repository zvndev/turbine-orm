# Read Replicas

Configure one or more read replicas and Turbine spreads read-only queries across them round-robin, while every write stays on the primary. It takes one config field, with no changes at query sites and no separate client.

```ts
import { turbine } from './generated/turbine/index.js';

const db = turbine({
  connectionString: process.env.DATABASE_URL,          // primary
  replicas: [
    process.env.REPLICA_URL_1,
    process.env.REPLICA_URL_2,
  ],
});
```

Reads now rotate across the two replicas, and writes go to the primary.

## What routes where

The split is by operation, not by table. Read-only operations issued **outside a transaction** go to a replica; everything else uses the primary.

| Goes to a replica | Always uses the primary |
|---|---|
| `findMany`, `findFirst`, `findUnique` | `create`, `createMany` |
| `findFirstOrThrow`, `findUniqueOrThrow` | `update`, `updateMany`, `delete`, `deleteMany`, `upsert` |
| `count`, `aggregate`, `groupBy` | Everything inside a `$transaction` body (reads included) |
| `findManyStream`, `findManyStreamBatches` | `pipeline`, `raw`, `sql` |
| | `$listen` / `$notify`, observability flushes |

Reads inside a transaction stay on the primary, because a transaction is a single connection. Splitting it across pools would break its consistency guarantees.

## Replica entries, strings vs pools

Each entry in `replicas` is either a connection string or an external pool, and the two have different lifecycles:

- **Connection string**: Turbine creates and owns a `pg.Pool` for it, with the same pool tuning and one-time type-parser registration as the primary. `disconnect()` closes it.
- **`PgCompatPool`** (Neon, Vercel Postgres, a shared `pg.Pool`): Turbine registers no type parsers and never ends it. You own its lifecycle, as with the [external-pool contract](/serverless) for the primary.

Omitting `replicas`, or passing `[]`, keeps the default single-pool path: no proxy and no routing overhead.

## Replication lag, reading your own writes

Replicas are eventually consistent. A row you just wrote on the primary may not have reached a replica, so a read routed there can miss it. When you need to read your own writes, pin the read to the primary with `$primary()`:

```ts
const created = await db.orders.create({ data: { total: 100 } });

// This read might hit a lagging replica and not see `created`:
const maybeStale = await db.orders.findUnique({ where: { id: created.id } });

// Force the primary, guaranteed to see the write:
const fresh = await db.$primary().orders.findUnique({ where: { id: created.id } });
```

`$primary()` returns a view of the client, with the same schema and config, that sends every operation, reads included, to the primary. The instance is cached, so calling it repeatedly is cheap. With no replicas configured, `$primary()` returns the client itself.

> **Note:** Turbine does not detect lag or wait for a replica to catch up. Send reads that must see a recent write through `$primary()`, or run them in the same `$transaction` as the write.

## PowDB: snapshot serving as the replica

The `replicas` config above is Postgres-only. PowDB (≥ 0.14) has its own replica model: **read-only snapshot serving**. A restored backup or checkpointed copy of the data directory is served strictly read-only, either by `powdb-server --readonly` or in-process with `turbinePowDB({ embedded: dir, readonly: true }, schema)`, to any number of concurrent readers.

You route by hand, and the errors tell you when a write went to the wrong place. Any write against the snapshot throws `ReadOnlyError` (`TURBINE_E018`) with `reason: 'snapshot'`, so your application can catch it and send the write to the primary. `readonly: true` on the Turbine client refuses the write locally, with no round-trip. The data is as fresh as your last snapshot: this is snapshot serving, not streaming replication, so treat it like a cache tier that updates on your backup schedule. See [PowDB read-only snapshots](/engines#read-only-snapshots-and-replicas-powdb--014) and [`ReadOnlyError`](/errors#read-only-refusals).

## Interaction with global filters

Read routing is independent of [global filters](/global-filters). A filtered read sent to a replica carries the same compiled `WHERE` it would on the primary, so soft-delete and tenancy filters apply the same way wherever the query runs.
