# Bounded local D1 application replay

This unshipped example implements a finite order application, durable outbox, polling consumer checkpoints, and an idempotent local destination. It uses a caller-supplied D1 binding. It adds no library API or dependency. Local Miniflare/workerd evidence does not certify hosted replication, session consistency, provider durability, or a hosted service SLA.

The application is [application.ts](../examples/d1-durable-replay/application.ts). The finite [demo](../examples/d1-durable-replay/demo.ts) accepts a binding and can be rerun. Call `initialize(binding)` once before admitting application operations. Setup establishes the lazy local binding with a read, then delegates only its fixed immutable migration plan to the existing public `migrateD1`. The helper is never used as a general application transaction API. All writers must follow this application protocol; administrative mutation of its five tables is outside the contract.

## Append and reconciliation

A command has a tenant key, stable event ID, order ID, quantity, amount, occurrence time, nullable title, and bytes. Every command property, the bytes, and operation options are captured before the first await. Keys are 1 to 64 ASCII key characters. A title is at most 4,096 UTF-8 bytes and a body at most 16,384 bytes. The captured canonical JSON array is below 64 KiB. Quantity is nonnegative int64 decimal TEXT; amount is nonnegative fixed scale 12 decimal TEXT with at most 30 integer digits; occurrence time is valid UTC text with exactly six fractional digits. These fields never pass through a floating point database number or a JavaScript Date representation. The Date check validates the calendar at millisecond resolution while retaining all six original fractional digits. Title null and empty text remain distinct. Body bytes are lowercase hexadecimal inside canonical TEXT. This is an explicit application representation, not a claim that D1 natively transports arbitrary bigint, decimal, or microsecond date values.

An optimistic read supplies a tenant's expected committed position. A single native D1 batch initializes the tenant if absent, asserts the exact expected head and absent event ID, inserts the business row and outbox row, updates the head, and reads back confirmation. A false guard evaluates invalid JSON inside SQLite, forcing rollback of the entire native batch. There is no optimistic `max(id)` allocation or shared global sequence. Positions are contiguous per tenant, bounded at 1,000,000, and have no global ordering meaning. Each order ID belongs to one creation event; this finite example does not implement arbitrary order updates.

An identical stable tenant/event ID accepts only byte-for-byte identical captured input. A changed field conflicts. A concurrent stale writer is rejected by the native guard or native unique constraints without a partial business effect, event, or position advance. SQL failure is atomic at the native engine; the application's observation of every post-dispatch exception, falsy exception, malformed response, or lost response is conservatively `UnknownOutcome`. A confirmation decoder failure is also unknown. It must never be reported as a confirmed rollback.

After uncertainty, use `reconcile(tenant, originalCommand)` to inspect stable ID/history. A matching present event establishes that creation. Absence is only a read observation: it does not prove that an outstanding dispatched batch will not later commit, nor does it certify hosted read consistency. Do not blindly retry. First settle or independently establish the disposition of outstanding dispatch, then reconcile using an appropriate authoritative binding. The native fixture loses an actual response after committing and reconciles the same full command. No cancellation can retract that commit.

## Delivery and acknowledgement

`deliver(tenant, consumer, callback, {limit})` reads the next contiguous prefix, invokes the callback outside any native batch, then atomically asserts the checkpoint still equals the original position and the source prefix exists before updating it. A stale acknowledgement cannot regress or jump over an undelivered prefix. The callback receives its own decoded objects, bytes, and array; private primitive acknowledgement state never aliases those objects. Changing the callback's position, command, bytes, or array cannot change the acknowledged range.

D1 has no interactive callback transaction or lock held across arbitrary asynchronous code. Two independent app instances may concurrently deliver the same prefix. Delivery is at least once. Real destination idempotency is mandatory. `applyDestination` illustrates an atomic, guarded destination keyed by tenant, consumer, and stable event ID, with complete captured value comparison and a unique position. Use a separate destination facade in the callback because callback reentry into its source facade is refused. An external system must implement equivalent idempotency itself. There is no exactly-once external-effect promise, LISTEN/NOTIFY, or CDC claim.

Any callback failure, including `false`, `0`, empty text, null, or undefined, prevents acknowledgement and preserves its original failure value. Cancellation or deadline before acknowledgement leaves the checkpoint unchanged. A late callback may still finish external effects; its late success is never acknowledged by the timed-out delivery. The caller must reconcile those external effects by its idempotency key. A dispatched acknowledgement can commit despite cancellation or a lost response; inspect the persisted checkpoint to reconcile it. The application never treats an unknown acknowledgement as a confirmed unchanged checkpoint.

## Bounds and ownership

Each append batch has six statements, destination batch three, and acknowledgement batch four, all below eight. The separate setup helper uses its own fixed migration batch and existing migration admission contract; call it before opening application traffic. Delivery admits 1 to 32 events, default 16. Each operation has a finite integer deadline of 1 to 10,000 ms, default 2,000. At most eight active operations and sixteen unsettled native/read/callback promises are admitted per facade. Reaching a bound fails closed, including when caller option getters synchronously start other operations. A facade allows only one delivery at a time. While a callback remains unsettled, its facade refuses reentry. Independent facades provide concurrency; admission is per facade, not a provider-wide quota.

`close(timeoutMs = 100)` seals admission immediately and waits a bounded interval, then returns `{settled, unsettled, active}`. Repeated close calls can observe later settlement. Close never calls binding disposal, runtime disposal, or an invented connection method. It does not cancel D1 batch work. An unresolved or ignored-cancellation batch remains tracked even after the caller's operation rejects, and close reports it honestly. The binding remains caller-owned and usable after close. Reads can also remain unsettled after their deadlines. A permanently unresolved promise can continue to consume admission capacity; process lifetime and runtime ownership remain the caller's responsibility.

## Run and evidence

Use the public schema definition in [schema.ts](../examples/d1-durable-replay/schema.ts) at generation time with `generateD1Files` from `turbine-orm/d1/generate`. It describes the canonical TEXT envelope and safe integer position. The emitted typed `replayEvents` and `replayOrders` query consumers use public `turbineD1` APIs, retain required fields and selected-result typing, and run against actual D1. Generated consumers do not claim that the envelope has SQL-native decimal or timestamp semantics.

The explicit native fixture is [run.mjs](../src/test/fixtures/d1-durable-replay/run.mjs). Set `D1_REPLAY_ROOT` to a fresh output directory (the default is under the OS temp directory), `D1_REPLAY_ARCHIVE` to the package archive, `D1_REPLAY_SHA256` to its SHA256 and `D1_REPLAY_NPM` to npm-cli.js. Provide exact `node22` and `node24` binaries in that root. The fixture installs the supplied archive, generates with full tooling, compiles strict ESM/CJS consumers with `skipLibCheck:false`, runs them on real local D1, compiles application and generated consumers with official Worker ambient types and ES2023 globals, executes that output, and reopens retained databases in separate processes. Required pins are Node 22.16.0 / 24.10.0, Miniflare 4.20260730.0 and workerd 1.20260730.1. A new `D1_REPLAY_ATTEMPT` preserves previous logs and selects a fresh persistence path.

Public service ports 59911 and 59912 are checked before starting and bind only loopback. The lifecycle helpers record internal runtime ports and process generations. The cleanup audit checks PID/start time, groups, paths, ports and open database descriptors. Closed database files remain on disk for inspection. These checks cover local D1 behavior and cleanup; they do not establish hosted runtime or performance guarantees.
