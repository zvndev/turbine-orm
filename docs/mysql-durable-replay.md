# Bounded MySQL order replay

This is a finite application example, not CDC, exactly-once delivery, a new library API, or a change to `liveQuery`. Poll `consumeBatch` a finite number of times and reconcile by reopening the same database. See `examples/mysql-durable-replay` and the executable installed-consumer fixture in `src/test/fixtures/mysql-durable-replay`.

## Native contract (published before implementation)

The fixed tables use InnoDB. An append inserts/locks the tenant stream row before any duplicate lookup or position read. The transaction allocates its next signed bigint position and writes both the order and immutable outbox event. Rollback releases the position. Same-tenant allocation therefore follows lock/commit serialization; tenants have independent sequences and there is no global order. Neither AUTO_INCREMENT nor MAX(id) is a commit-order oracle. Deadlocks and lock timeouts fail the operation; the caller can retry the identical captured command after reconciliation.

The key is `(tenant,eventId)`. Only exact equality of every command field and byte accepts reuse. Input properties are read once and bytes copied synchronously before admission. Quantity and positions fit nonnegative signed BIGINT. Decimal and canonical UTC microsecond timestamp values deliberately use bounded ASCII text columns: their representation, including decimal trailing zeroes, is an application contract, not a generic numeric/timestamp codec guarantee. UTF-8 text, bytes, null and every event field are replayed exactly. Combined title/body admission is at most 65536 bytes.

Each consumer locks `(tenant,consumer)` before reading an ascending batch of at most 32 events. Competing instances serialize on that row. Callback rows and buffers are copies; the final acknowledgement position is private. Checkpoint and delivery are at least once: a callback may perform its effect and then fail, be cancelled, lose its COMMIT response, or die before the checkpoint commits. `deliverToInbox` demonstrates a separately committed destination receipt plus business projection in one transaction keyed by tenant/consumer/event ID. After locking the destination projection row, a current locking read checks the inbox receipt. This observes a competing committed receipt even if earlier metadata reads established an older REPEATABLE-READ snapshot. A replay compares the full original payload before accepting that receipt. Real remote destinations must supply equivalent durable idempotency.

All callback failures, including `throw undefined`, null, false, zero and empty string, reject without acknowledgement. Abort/deadline before acknowledgement prevents COMMIT. A dispatched COMMIT whose response is lost is uncertain even if rollback is subsequently attempted. Reopen and reconcile via the stable event ID or checkpoint; never label such a result acknowledged rollback success. No writes are automatically retried by this example. Turbine may retry failed checkout/BEGIN before entering the effect callback.

## Bounds and resource ownership

Use a caller-owned mysql2 pool with a driver-recognized UTF8MB4 collation, named placeholders, big number strings, no custom typeCast/row arrays/multiple statements, 1..8 connections, `waitForConnections:false`, numeric loopback host or Unix socket, and `connectTimeout` 1..1500ms. The application validates these settings and never changes pool or session defaults. Every native lease must retain the UTF-8 client encoder and a UTF8MB4 configuration. Every checked-out session must retain utf8mb4 for character_set_client, character_set_connection and character_set_results; incompatible encodings, including SET NAMES latin1 or NULL result encoding, are refused before application effects. Caller settings are not repaired or mutated. Sessions must have autocommit enabled, REPEATABLE-READ isolation, InnoDB row lock timeout 1..2 seconds, metadata lock timeout 1..3 seconds, and SELECT max_execution_time 1..2500ms. The server must use InnoDB by default, `innodb_flush_log_at_trx_commit=1`, binary logging and `sync_binlog=1`. Every existing application table is checked for InnoDB. Deployment still depends on the filesystem and hardware honoring durable writes.

There are at most eight admitted operations and eight unsettled callbacks and eight unsettled driver SQL promises per application, 32 events per batch, 1..2000ms for the whole callback batch, 1..3000ms per SQL call and 1..10000ms per operation. Numbers must be finite safe integers. Pool acquisition has a 1500ms waiting deadline; late acquisitions are released and retained until settled. The required nonqueued pool and native connect timeout bound its pending work. SQL call cancellation/deadline destroys only the leased connection's native socket with an error, then removes that lease from the pool. This uses mysql2's exposed native connection/socket; the strict native controls include a paused COM_STMT_PREPARE response so an Execute timer that has not started cannot strand close(). This is socket termination, not a claim that a JavaScript race cancels a server statement or proves a dispatched write rolled back. Server lock/SELECT limits are separate native safeguards; write uncertainty survives socket loss. The app owns all settlement observers and discards destroyed leases instead of returning them for reuse.

Callbacks receive an abort signal. Only their await is raced; an ignoring callback remains counted until settlement, cannot acknowledge later, and does not block close. JavaScript synchronous code cannot be preempted. Callbacks must propagate the signal to their own bounded I/O and must not start unbounded detached work. Same-consumer callback reentry is refused across copies and ESM/CJS in one Node realm using a shared AsyncLocalStorage registry and server UUID/database/tenant/consumer identity. Close from this app's callback context is also refused. Other processes serialize through the database locks. Close seals admission synchronously, aborts active work, waits for owned client SQL/acquisition promise settlement, and never ends the caller pool. Cancelled callbacks may outlive close under the explicit eight-callback cap. Server work may remain until a native limit or disconnect is observed; close is not a server rollback acknowledgement. mysql2 command timeouts keep native driver promise settlement finite, independently of the abort race.

## Qualification

The native fixture uses owned MySQL 8.4 services in ordinary and NO_BACKSLASH_ESCAPES modes. It checks exact Node 22.16.0 and 24.10.0, installed ESM/CJS, strict and generated consumers against the unchanged normal archive. Current installed mysql2 3.24.6 is separate from source-lock 3.24.5. The mysql2 3.0 floor's Buffer limitation remains; this example does not certify that floor. This is local functional evidence, with no timing, performance, support expansion or hosted-provider claim.
